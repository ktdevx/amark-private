# Gap Analysis: block-parser

要件（`requirements.md`、未承認）と、いまのコード（project-foundation、unicode-tables、syntax-tree が実装済み）の差を調べた。設計の判断はここでは下さず、選択肢と、設計で調べることを並べる。

## 1. 現状

### 使える部品

| 部品 | 場所 | block-parser での使い道 |
|------|------|------------------------|
| 確保関数の抽象、あふれない加算と乗算 | `src/alloc.h` | 作業用メモリ、大きさの計算 |
| アリーナ | `src/arena.h` | 文書のアリーナ（定義の表、行の記録）。個別の解放も巻き戻しもない |
| 可変長の配列（スタックを兼ねる） | `src/array.h` | 開いているブロックのスタック、行の記録 |
| 行の索引 | `src/line_index.h` | 行の分割。内容の全体について、文書が作って持つ |
| UTF-8 の検査・デコード・置換 | `src/utf8.h` | 解析する範囲の検査、ラベルのデコード |
| case folding | `src/unicode.h` | ラベルの正規化（1 つのコードポイントから最大 3 つ） |
| 設定の解決 | `src/config_internal.h` | `amark_config_resolve` が検査と既定値の適用を 1 回で行う |
| 文書 | `src/document.h` | `amark_document_create`、`amark_document_node_count`、内容と行の索引の取得 |
| 木を作る操作 | `src/tree_internal.h` | 足す、前に差し込む、包む、範囲を変える、種類を変える、取り除く、属性を設定する |
| 不変条件の検査 | `src/tree_check.h` | テストで、作った木を確かめる |
| 数えて失敗する確保関数 | `tests/support/test_alloc.h` | 確保の失敗の注入 |

### 守る決まり

- モジュールは `src/<name>.c` と `src/<name>.h` の組。`src/CMakeLists.txt` の `AMARK_SOURCES` に 1 行足す。
- 内部の関数も `amark_` で始める。1 つのファイルだけで使う関数は `static`。
- 単体テストは `tests/unit/test_<module>.c`、公開 API だけのテストは `tests/public/`。`tests/CMakeLists.txt` に 1 行ずつ登録する。
- 公開する関数を足したら、`tests/checks/exported_symbols.txt` に名前を足す（`checks.exports` が完全な一致を確かめる）。
- `checks.objects` が、可変の静的データと、`abort`・`exit`・`longjmp`・`assert` の参照を禁じる。ポインタを含む `const` の表も、可変のデータとして数えられる。
- `amark.h` は、いま `amark_version_string` だけを宣言している。解析の入口はここか、新しい公開ヘッダに足す。`tests/public/header_cxx.cpp` が、C++ としての取り込みを確かめる。

## 3. 主な差

### 差 1：「置き換えて続ける」設定で、不正なバイト列をその場で読む（Constraint）
- 要件 2.8 は、置き換えた写しを作らず、範囲を元の内容のオフセットで表すことを求める。
- `amark_utf8_decode` は、検査を通ったバイト列だけを受け付ける（それ以外の結果は定めていない）。`amark_utf8_replace` は写しを作る関数なので、この要件には使えない。
- `amark_utf8_inspect` は、不正なバイト列の極大の部分の長さを返す。これを使えば「不正なら U+FFFD として 1 文字進む」デコードを作れる。
- ブロックの構造は ASCII の文字だけで決まる。コードポイントが要るのは、ラベルの正規化（case folding）と、ラベルの 999 文字の数え方だけである。
- 選択肢：
  - block-parser の中に、ラベル用の寛容なデコードを置く。
  - `utf8` モジュールに「不正なら U+FFFD を返す」デコードを足す（project-foundation の変更になる）。inline-parser と source-text も同じものを使うので、共有できる。
- U+0000 も同じ箇所で U+FFFD として扱う（要件 14.4）。

### 差 2：作業用メモリの置き場（Constraint）
- アリーナは個別の解放も巻き戻しも持たない。開いているブロックのスタックなどを文書のアリーナに置くと、文書が解放されるまで残り、要件 4.5 に合わない。
- 選択肢：
  - 解析の間だけの 2 つ目のアリーナを、同じ確保関数で作り、戻る前に解放する。
  - 作業用の配列を `amark_malloc` で直接確保する（伸ばす処理を自分で書くことになる）。
- `amark_array_t` は伸びるたびに古い場所をアリーナに残す。作業用のアリーナなら、戻るときにまとめて消える。

### 差 3：定義の表と行の記録を、文書から引けるようにする（Constraint）
- 要件 14.10 と 15.7 は、表と記録が文書の解放まで使え、文書の解放でともに解放されることを求める。inline-parser と source-text は、文書からこれらを引く。
- `struct amark_document` には、解析器のデータを置く場所がない。レイアウトは syntax-tree が持ち、内部 API の変更は syntax-tree の見直しの対象になる。
- 選択肢：
  - `struct amark_document` に、block-parser の構造体へのポインタを 1 つ足す（syntax-tree の小さな変更。本体は文書のアリーナに置く）。
  - `struct amark_document` に、定義の表と行の記録の項目をそのまま足す（syntax-tree が block-parser の型を知ることになり、依存の向きに反する）。
  - 文書とは別の構造体を返す（解放が 2 つになり、「資源の持ち主は文書」の決まりに反する）。

### 差 4：インラインに渡す内容の範囲の置き場（Missing）
- 段落には属性がない。見出しの属性は、レベルと書き方だけである。内容の範囲を置く場所がない。
- 選択肢：
  - block-parser の側に、ノードの ID をキーとする表を持つ（差 3 と同じ場所に置ける）。
  - 段落の内容の範囲は、ノードの範囲と行の記録から求める（段落はノードの範囲を内容に合わせれば足りる）。ATX 見出しだけ、内容の範囲を別に持つ。
  - syntax-tree の属性に内容の範囲を足す（公開しない項目を属性に持つことになる）。
- 要件 6.2 は、段落のノードの範囲に行末の空白を含める。内容の範囲（要件 16.2）は含めない。この 2 つは終わりが違うので、段落でも、ノードの範囲だけからは内容の範囲が決まらない。

### 差 5：範囲を延ばす回数（Constraint）
- `amark_tree_set_range` は、呼ぶたびに行番号を二分探索で求め直す。
- 行を読むたびに、開いているコンテナのすべての範囲を延ばすと、深さ D の入れ子で 1 行あたり D 回の更新になる。
- 選択肢：範囲の終わりは、ブロックを閉じるときに 1 回だけ設定する。その間、子の範囲が親の外に出るが、内部 API はこれを許している（不変条件の検査は、解析が終わってから通ればよい）。

### 差 6：定義の表のハッシュ（Unknown）
- グローバルな状態を持てず、結果は決定的でなければならないので、実行のたびに変わる種は使えない。
- 種が固定だと、ハッシュが衝突するラベルを大量に並べた入力で、検索が遅くなりうる（要件 14.9 は平均の時間、要件 18.1 は全体の線形を求める）。
- 選択肢：固定のハッシュ関数と、衝突に強い構造（たとえば、衝突した鎖を正規化したラベルの順に保つ）。または、すべての定義を集めてから整列して二分探索にする（決定的で、最悪でも N log N）。
- 正規化したラベルの文字列をどこに持つかも決める。原文の複製ではなく、畳み込んだ結果なので、文書のアリーナに置ける。大きさは、ラベルの長さの合計の定数倍に収まる（1 つのコードポイントが最大 3 つになる）。

### 差 7：spec.txt の例のテスト（Unknown）
- リポジトリに spec.txt がない。例を取り出すスクリプトと HTML 出力は、spec-conformance の範囲である。
- 要件 19.1 は、13 の節の例について、ブロックの構造が期待どおりであることを求める。HTML とは比べられないので、期待する木を別の形で書く必要がある。
- 選択肢：
  - 期待する木を、テストのコードに手で書く（種類・入れ子・属性を文字列にして比べる補助を、テストの側に作る）。
  - spec.txt をリポジトリに置き、ブロックの節の例を取り出して、期待する木の表し方に変換したデータを生成する（spec-conformance と重なる）。
- どの例を対象にするか（節のすべての例か、ブロックだけで結果が決まる例か）を、設計で数えて決める。

## 4. 実装の進め方の選択肢

### Option A：既存のモジュールを広げる
- 解析の入口を `document.c` に、ブロックの規則を `tree.c` の近くに足す。
- ✅ ファイルが増えない。
- ❌ syntax-tree は「解析の規則を知らない」という決まり（syntax-tree の要件 12.8）に反する。採れない。

### Option B：新しいモジュールだけで作る
- 解析の入口、行の走査、ブロックの規則、リンク参照定義、定義の表、行の記録を、すべて新しいファイルに置く。既存のファイルは、`AMARK_SOURCES`、公開ヘッダ、公開シンボルの一覧、テストの登録だけを変える。
- 定義の表と行の記録は、文書とは別の構造体で持つことになる。
- ✅ 上流の spec に手を入れない。
- ❌ 差 3 を、文書の外の構造体で解くことになり、「資源の持ち主は文書」に合わせにくい。差 1 のデコードが、block-parser、inline-parser、source-text に重複しうる。

### Option C：新しいモジュールを中心に、上流を最小限だけ広げる
- ブロックの解析は新しいモジュールに置く。ファイルの分け方は、brief の Boundary Candidates に沿って、たとえば次のようにする。
  - 解析の入口と設定の適用
  - 行の走査とコンテナの照合、リーフの開始と終了
  - リンク参照定義の構文
  - ラベルの正規化と定義の表
  - 行の記録
- 上流への変更は、次の 2 つに絞る。
  - `struct amark_document` に、解析器のデータへのポインタを 1 つ足す（差 3）。
  - `utf8` に、不正なバイト列を U+FFFD として読むデコードを足す（差 1）。
- ✅ 文書が持ち主のままで、下流は文書から表と記録を引ける。デコードを 3 つの spec で共有できる。
- ❌ 実装済みの 2 つの spec（syntax-tree、project-foundation）の設計と要件の文書を、合わせて直す必要がある。syntax-tree の「内部 API の契約の変更」は、下流の見直しの対象である（下流はまだ着手していないので、影響は文書だけ）。

## 5. 規模とリスク

- **Effort: L（1〜2 週間）**。ブロックの規則が多く（コンテナ、リスト、7 種類の HTML ブロック、リンク参照定義）、範囲と行の記録を、行ごとに正しく保つ必要がある。テストの量も多い（13 の節の例）。
- **Risk: Medium**。方式は cmark で確立していて、木の操作もそろっている。不確かなのは、範囲と行の記録の細部（タブの一部の消費、遅延継続行、定義を取り出した後の段落）、定義の表の最悪の場合の時間、例のテストの作り方である。

## 6. 設計への申し送り

### 決めること
- 上流への変更を許すか（Option B か C か）。許すなら、syntax-tree と project-foundation の文書の直し方。
- 作業用メモリの置き場（差 2）。
- 内容の範囲の置き場（差 4）。
- 範囲を設定する時点（差 5）。
- 解析の入口の名前と引数、宣言を置くヘッダ。失敗したときに、位置（不正な UTF-8 のオフセットなど）を返すかどうか。
- 方言の箇所の形（要件 17）。ブロックの種類ごとの「開始」「継続」「閉じる」を、表で引く形にするか、分岐で書くか。表にする場合、関数ポインタの表は `checks.objects` に通らないことがある（ポインタを含む const の表）ので、確かめる。

### Research Needed
- cmark の `blocks.c` の流れ（コンテナの照合、`last_line_blank` によるタイトとルーズの判定、`partially_consumed_tab`）を確かめ、範囲と行の記録に必要な情報が、どの時点で分かるかを整理する。
- CommonMark 0.31.2 の、範囲に関わる細かい場合を例で確かめる。
  - 定義を取り出した後に段落が残らない Setext 見出し
  - 空の項目と、最初の行が空の項目
  - コンテナの中の、閉じないフェンスのコードブロックの終わりの空行
  - タブがプレフィックスの境をまたぐ場合（spec.txt の Tabs の節）
- ラベルの「999 文字」の数え方（コードポイントで数える。角括弧の内側で、正規化の前）を、仕様の文言で確かめる。
- 定義の表の方式（差 6）と、病的な入力での時間。
- 10 万段のリストの入力の作り方（1 行に印を並べる形で、入力の長さを段数に比例させる）。
- 例のテストの作り方（差 7）と、spec-conformance との分担。
- 行の記録の大きさ（1 行あたりのバイト数）と、要件 18.2（メモリは内容の長さにほぼ比例）との関係。短い行が大量にある入力で、行の索引と合わせてどれだけになるか。

# Research & Design Decisions

## Summary
- **Feature**: `block-parser`
- **Discovery Scope**: Complex Integration（新しい機能で、実装済みの 3 つの spec の部品に乗る。外部の依存は足さない。調査は、CommonMark 0.31.2 の spec.txt、cmark 0.31.1 の `blocks.c`、既存の内部 API に絞った）
- **Key Findings**:
  - cmark は、行ごとに「開いているブロックとの照合」「新しいブロックの開始」「行の追加」の 3 段階で進む。この流れは、明示的なスタックにそのまま直せる。
  - cmark には、深いリストの後に空行が続く入力で時間が 2 乗になるのを防ぐ対策がある（リストに「前の行も空行だった」の印を持ち、照合を打ち切る）。同じ対策が要る。
  - cmark のタイトとルーズの判定は、閉じたノードに残した印（`last_line_blank`）を、リストを閉じるときに木をたどって読む。印の付き方を追うと、スタックの要素の印だけで同じ結果を出せる。
  - リーフのノードを閉じるときに作れば、リンク参照定義の取り出しで、ノードを取り除く操作も、前に差し込む操作も要らない。
  - 定義だけでできた段落の後の Setext の下線について、cmark と commonmark.js は、段落を空のまま開いておく（下線の行が `-` 1 つのとき、空のリスト項目ではなく、段落になる）。spec.txt に例はないが、2 つの参照実装に合わせる。
  - spec.txt の、ブロックに関わる 13 の節の例は 295 個である（例 1〜11 と 43〜326）。

## Research Log

### cmark の行の処理
- **Context**: 流れと、範囲・行の記録に要る情報が分かる時点を確かめる。
- **Sources Consulted**: cmark 0.31.1 `src/blocks.c`（`S_process_line`、`check_open_blocks`、`open_new_blocks`、`add_text_to_container`、`finalize`、`S_advance_offset`、`parse_list_marker`）
- **Findings**:
  - 行の位置は、バイトの `offset` と、タブを考えた `column` の組で持つ。桁数で進めてタブの途中で止まると、`partially_consumed_tab` が立ち、`offset` はタブに留まる。行を内容に足すとき、そのタブを残りの桁数の空白に置き換える。
  - 開始の判定の順は、ブロッククォート、ATX、フェンス、HTML、Setext、テーマの区切り、リスト項目、インデントされたコードである。
  - リスト項目の `padding` は、印の幅と、その後の空白（1〜4 桁）の和。5 桁以上か、印の後が空白だけなら、印の幅 + 1。
  - HTML ブロックは、開始の行でプレフィックスの後から足す（インデントを含む）。
  - フェンスの中の行は、開始のフェンスのインデントの桁数まで、空白を除く。
  - 遅延継続行の条件：いちばん内側が段落で、すべてが一致したわけではなく、新しいブロックが開かず、空行でない。
  - 範囲の終わり（`end_line`、`end_column`）は、`finalize` で設定する。
- **Implications**: 行の記録の `pad` は、cmark の「タブを空白に置き換える」をそのまま表す。`content_start` はタブの位置、`pad` は置き換える空白の数とする。

### 空行と、深いリスト
- **Context**: 時間が入力の長さにほぼ比例する（要件 18.1）ことを、病的な入力でも守る。
- **Sources Consulted**: `check_open_blocks` の `CMARK_NODE__LIST_LAST_LINE_BLANK` の箇所
- **Findings**:
  - リスト項目は、子があれば、空行で必ず続く。字下げを消費しない。このため、N 段のリストの後の空行は、1 行ごとに N 個の要素を照合する。
  - cmark は、リストで空行が 2 回続いたら（字下げが 0 のとき）、照合を打ち切る。打ち切った行は、いちばん内側がコードブロックか HTML ブロックなら、内容に足す。
  - 字下げが 0 でない空行（空白だけの行）は、最初のリスト項目が空白をすべて消費するので、その内側のリストで打ち切りの条件に合う。
  - ブロッククォートの中のリストでも、`>` の後が空白だけなら、同じ箇所で打ち切られる。
- **Implications**: 打ち切りの条件は「行の全体が空行」ではなく、「リストの要素のところで、行の残りが空白だけ」とする。打ち切った行のコードブロックの `content_start` は、字下げの桁の合計から求める。

### タイトとルーズの印
- **Context**: cmark はノードに印を持つ。syntax-tree のノードには、その場所がない。
- **Sources Consulted**: `add_text_to_container` の `S_set_last_line_blank`、`finalize` の `CMARK_NODE_LIST` の枝、`S_ends_with_blank_line`
- **Findings**:
  - 空行のとき、いちばん内側の一致した要素 C と、C の最後の子に印が付く。C の祖先の印は消える。C がブロッククォート、フェンスのコード、開始の行の空の項目のときは、C 自身には付かない。
  - 空行でないとき、C と祖先の印は消える。
  - リストを閉じるとき、(a) 次の項目がある項目に印がある、(b) 次の兄弟があるか、項目に次の項目がある子が「空行で終わる」、のどちらかでルーズになる。「空行で終わる」は、リストとリスト項目では、最後の子へ降りて調べる。
  - C の最後の子が、閉じたリストであることはない。リストが閉じるのは、同じ親に別の子が足されるときだけで、そのときは、その子が最後の子になる。
- **Implications**:
  - 「空行で終わる」の値は、子が閉じるときに親へ伝えれば、降りて調べる必要がない。
  - (a) と (b) は、「次の項目が足されるとき」と「次の子が足されるとき」に、直前のものの値を見れば判定できる。
  - 項目自身の印が立っていて、最後の子の値が立っていない場合は、子があるかぎり起きない（C に印を付けるとき、最後の子にも付けるため）。設計では、念のため両方を見る。

### リンク参照定義の取り出しの時間
- **Context**: 段落を閉じるたびに定義を読む。失敗する読み方を繰り返して、時間が 2 乗にならないかを確かめる。
- **Sources Consulted**: spec.txt 4.7 節、`resolve_reference_link_definitions`
- **Findings**:
  - ラベルは 999 文字で打ち切れる。dest は行をまたがない。
  - title は行をまたぐ。閉じる区切りが段落の終わりまで見つからないと、段落の終わりまで読む。
  - その場合、title が dest の次の行で始まっていれば、title のない定義になり、次の行（title の始まりの行）は `[` で始まらないので、取り出しはそこで終わる。
- **Implications**: 段落の終わりまで読む失敗は、1 つの段落で数回までである。取り出しの時間は、段落の長さに比例する。

### 定義だけの段落と Setext の下線
- **Context**: 要件 9.5 の「下線の行を、仕様に従って別のブロックとして解析する」の中身を決める。
- **Sources Consulted**: `open_new_blocks` の Setext の枝、commonmark.js の `blockStarts` の Setext の関数、spec.txt の例 215 の前後
- **Findings**:
  - 2 つの実装とも、内容が残らなければ見出しにせず、段落を開いたまま、残りの開始の判定を続ける。段落が開いているので、「段落を中断する」規則が当てはまる。
  - `===` は、どの開始にもならないので、空の段落の最初の行になる。`---` は、テーマの区切りになる。`-` 1 つは、空のリスト項目が段落を中断できないので、段落の行になる。
- **Implications**: 段落の要素は、「内容が空」の状態を持てるようにする。

### spec.txt の例
- **Context**: 要件 19.1 の対象を数える。
- **Sources Consulted**: commonmark-spec の `0.31.2` のタグの `spec.txt`
- **Findings**: Tabs 11、Thematic breaks 19、ATX headings 18、Setext headings 27、Indented code blocks 12、Fenced code blocks 29、HTML blocks 44、Link reference definitions 27、Paragraphs 8、Blank lines 1、Block quotes 25、List items 48、Lists 26。合わせて 295。
- **Implications**: 3 つのテストのファイルに分ける。期待する木は、1 行の文字列で手書きする。HTML から機械的に作ると、定義のノード、見出しの書き方、HTML ブロックとインラインの HTML の区別が出ないので、手書きにする。

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| 行ごとの 3 段階とスタック | cmark と同じ流れを、明示的なスタックで行う | spec.txt に合わせやすい。再帰がない | 状態が多い（行の位置、スタック、印） | 採用 |
| 2 回の走査 | 先にコンテナの構造だけを決め、次にリーフを決める | 役割が分かれる | 遅延継続行は、段落が開いているかどうかで決まるので、2 つを分けられない | 不採用 |

| 上流を最小限だけ広げる（gap の Option C） | 文書にポインタを 1 つ足す。`utf8` にデコードを足す | 文書が持ち主のまま。デコードを下流と共有できる | 上流の文書の更新が要る | 採用 |

## Design Decisions

### Decision: リーフのノードは閉じるときに作る
- **Context**: 段落は、閉じるときに、0 個以上の定義と、0 個か 1 個の段落（または見出し）になる。
- **Alternatives Considered**:
  1. 開くときに段落のノードを作り、閉じるときに、定義を前に差し込み、空なら取り除く
  2. リーフは、閉じるときに、決まった範囲で作る
- **Selected Approach**: 2。コンテナだけ、開くときに作る。
- **Rationale**: 取り除く操作が要らないので、作ったノードの数が、返す木のノードの数と等しくなる（要件 3.5 と 3.6 が、同じ数で満たせる）。段落から Setext 見出しへの変更も、種類を変える操作なしで済む。
- **Trade-offs**: リーフの深さとノードの数の上限は、要素を積むときと、閉じるときの 2 か所で検査することになる。
- **Follow-up**: ノードの ID が文書の順になることを、テストで確かめる。

### Decision: 定義の表は整列と二分探索
- **Context**: 種を固定したハッシュは、衝突を狙った入力に弱い。種を実行ごとに変えると、決定性に反する。
- **Alternatives Considered**:
  1. 固定のハッシュ関数のハッシュ表
  2. 整列した配列と二分探索（cmark の `references.c` と同じ考え方）
- **Selected Approach**: 2。整列は、再帰のない併合整列を自分で書く。
- **Rationale**: 最悪の場合でも N log N で、決定的である。標準の `qsort` は、最悪の場合の時間と、同じ値の順が実装によって違う。
- **Trade-offs**: 検索が log N になる。要件 14.9 を、これに合わせて直した。
- **Follow-up**: 数万個の定義で、時間が問題にならないことを確かめる。

### Decision: 正規化したラベルを保存しない
- **Context**: 保存すると、原文の写しに近いものを文書に持つことになり、検索のときにも作業用のメモリが要る。
- **Selected Approach**: 正規化を、コードポイントを 1 つずつ返す読み手にする。比較は、2 つの読み手を並べて進める。
- **Rationale**: 検索がメモリを確保しないので、inline-parser の検索は失敗しない。UTF-8 への書き出しも要らない。
- **Trade-offs**: 比較のたびに正規化し直す。ラベルは 999 文字までなので、上限がある。

### Decision: 内容の範囲は一覧で持つ
- **Context**: 段落と見出しには、内容の範囲を置く属性がない。
- **Alternatives Considered**:
  1. syntax-tree の属性に足す
  2. 解析のデータに、ノードの ID と範囲の一覧を持つ
- **Selected Approach**: 2。一覧は、閉じた順（文書の順）に並ぶ。
- **Rationale**: inline-parser は、木をたどらずに、一覧を前から順に処理できる。公開の属性を増やさない。

### Decision: 要件の 2 か所を直した
- **Context**: 設計の調査で、要件と合わない点が 2 つ見つかった。
- **Selected Approach**:
  - 6.4：リスト項目の終了を「最後の空行でない行」から「印のある行の終わりと、最後の子の終了の、後ろのほう」に直した。閉じないフェンスのコードブロックは、後ろの空行を内容に含むので、元の文言では、子の範囲が親の外に出る。
  - 14.9：定義の表の時間を、「平均でラベルの長さに比例」から「最悪の場合でも N log N と log N」に直した。
- **Rationale**: どちらも、製品が保証する性質（木の不変条件、病的な入力に強い）に合わせるための、局所的な修正である。

### Synthesis
- **一般化**：行の記録は、RefDef、ラベルの正規化、inline-parser、source-text が、同じ形で使う。「行をまたぐときに、次の行の `content_start` へ進む」という 1 つの決まりで、プレフィックスとインデントの扱いをすべてまかなう。
- **作るか、使うか**：ブロックの解析は、既存のライブラリを使えない（原文を複製しない木と、範囲の決まりが独自のため）。整列も、決定性と最悪の場合の時間のために、自分で書く。
- **単純化**：ハッシュ表、正規化したラベルの保存、閉じたノードの印の表、ノードを取り除く操作、関数ポインタの表を、いずれも持たない。`label` と `definition` は、1 つのモジュールにまとめた。

### Decision: 「子がある」は、開いたブロックの数で判定する（設計のレビューで追加）
- **Context**: リーフのノードを閉じるときに作るので、開いている段落は、木の上ではまだ子でない。cmark の「項目に子があれば、空行で続く」を木の子で判定すると、`- a`、空行、`  b` の入力で、項目が空行で閉じてしまう。タイトとルーズの「最後の子」も同じである。
- **Selected Approach**: コンテナの要素に、内側で開いたブロックの数（`child_count`）と、「最後の子の値」を持つ。空行の印は、これから閉じる要素があればその要素に、なければ「最後の子の値」に付ける。
- **定義だけの段落**: cmark は、定義だけの段落を取り除くので、その後は項目に子がないことになる。ただし cmark 自身も、空行の打ち切りのために、2 行目以降の空行では項目を閉じない。仕様の文言（この項目は空行で始まっていない）に合わせ、定義だけの段落も数える。
- **Follow-up**: 空行の打ち切りの確かめ方を直した。空白だけの行でも打ち切りは起きるので、「空行 1 行」と「空行を増やしたもの」で木を比べる。

## Risks & Mitigations
- タイトとルーズの規則を、cmark と違う形で持つ — spec.txt の Lists と List items の全例（74 個）で確かめる。
- 空行の打ち切りが、木を変えてしまう — 打ち切りが起きる入力と起きない入力で、木が同じことを確かめる。
- 例を手で写すときの写し間違い — 例の番号を添え、レビューで spec.txt と突き合わせる。spec-conformance が全例を HTML と比べるので、最終的にはそこで見つかる。
- spec.txt の例は CC BY-SA 4.0 である — 例を写したテストのファイルに、出どころを書く。spec.txt そのものを置くかどうかは、spec-conformance で決める。
- 上流の 2 つの spec の文書が、実装とずれる — 追加を反映する作業を、タスクに含める。
