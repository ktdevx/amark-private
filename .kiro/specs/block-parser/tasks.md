## Implementation Notes
- 1.2: clang の ASan のランタイムがこのコンテナにないため、サニタイザの構成は GCC（`-DAMARK_SANITIZE=ON -DCMAKE_C_COMPILER=gcc`）で確かめる。
- 1.3: `amark_test_dump_blocks(doc, buf, size)`（`tests/support/tree_dump.h`、`amark_test_support` に含まれる）。設定されていない属性は `none`、種類のないリストは `(list)`、短い名前のない種類は `(?)`、info が書かれていれば空でも `info` と書く。
- 2.1: 解析のデータを作るときの行の内容の終わりは、`src/parse_data.c` の static な `init_records` が範囲の中のバイトだけで求める（依存の向きを守るため line.c を呼ばない）。2.2 の `amark_line_bounds` は、これと同じ `content_end` を返す必要がある（CR と LF の間で切れる範囲でも）。
- 2.2: `src/line.c` は行の開始位置を O(1) で得るため `line_index` の `line_starts` と `length` を直接読む（行の索引に O(1) の取得関数がないため。上流に足すなら置き換える）。行末記号の判定は `init_records` と 2 か所にあり、`bounds_agree_with_initial_records_for_every_range` で一致を固定している。
- 3.3: HTML の型 7 は spec.txt の文言どおり、名前が pre・script・style・textarea の開始タグを外す（`<pre/>` は 0、`</pre>` は 7）。cmark と commonmark.js はこれを外さないが、spec.txt の例はこの違いによらない。
- 4.1: ラベルの走査と比較は、行末記号の次の行へ進むとき、その行の記録の `content_start` まで飛ぶ。作った直後の記録は「行の内容の終わり」なので、書いていない行は内容ごと飛ばされる。ブロックの解析は、ラベルを読む前に段落の各行の記録を書く必要がある。解析のデータがないときは、行末記号だけを飛ばす。
- 5.1: 囲まない dest の丸括弧の入れ子には上限を設けない（spec.txt と design.md にないため。cmark は 32 段）。`amark_refdef_parse` の `last_line` は定義の最後の行、`end` はその行の内容の終わり（後ろの空白を含む）。続きは `last_line + 1` 行の `content_start` から読む。
- 6.1: `amark_line_pos_find_nonspace` は同じ行で前の結果を使い、`first_nonspace <= offset` のときだけ走査し直す（深い入れ子でも 1 行が線形になるため。レビューの第 1 回で指摘）。テストのため、行の位置の型と `amark_line_pos_init` / `_find_nonspace` / `_advance` を `src/block.h` に出した（内部、公開しない）。スタックの要素には `child_count`、`ends_blank`、`last_child_blank`、`blank_run`、`loose`、`all_matched` があるが、空行の印と `loose` を設定するのは 8.3。CommonMark のほかの種類の `switch` の枝は空なので、7.x と 8.x で埋める。
- 7.1: `start_block` の先頭の `if (indent >= CODE_INDENT || blank) return;` は、1〜6 の開始だけに合う。7.2（インデントされたコードは 4 桁以上）と 8.2（リスト項目もインデントが 3 桁以下。8.2 の注記を参照）で、各判定の条件に分ける。スタックで HEADING として開く見出しは ATX だけで、`close_block` は書き方を ATX に固定している。Setext を要素にするなら、要素に書き方の項目を足す。新しいリーフのテストは `test_block.c` の `block_leaves` スイートにあり、`amark_parse` と `amark_test_dump_blocks` で確かめる。
- 7.2: 【設計の穴・上流で決める】閉じていないフェンスのコードブロックが長さ 0 の行で終わると、範囲の終わりはその行の開始と同じになる。例えば `"```\na\n\n"` は 0..6 になり、終了行（syntax-tree では `end - 1` を含む行）が 2 になる。このため、行番号だけで内容を読む下流は最後の空行を落とす。これは design.md の LineRecords の「リーフに属する行は開始行から終了行まで」と矛盾する。7.3 の HTML ブロック 1〜5 が閉じずに空行で終わる場合も同じになる。いまは設計の範囲の決まりを文字どおりに守り、テスト `unclosed_fence_closes_at_the_end_of_the_range` でこの動作を固定している。案は 3 つある。(a) 範囲の終わりを空行の行末記号の後にする。(b) 下流が `end` から最後の行を求める契約にする。(c) 最後の行を明示する項目を足す。インデントされたコードは `last_nonblank_end` で終わるので影響しない。
- 7.3: 8.1 と 8.2 で次のテストを足す。型 7 の HTML が遅延継続行では段落を中断しない場合（`> a\n<span>`）と、プレフィックスがタブの途中で終わる HTML の行（記録の pad が 0 でない）。HTML の終了条件は開始の行でも探す（`<!-->` はその行で閉じる。cmark と同じ）。
- 7.4: Setext の判定（開始の判定 5）で段落から定義を取り出し、内容が残らなければ、段落に `emptied` を付けて開いたままにし、その行で別の開始を試す。開始がなければ、その行が段落の最初の行になる。`emptied` はその行を越えて残らない。定義のノードは、段落を閉じるときと Setext の判定のときにしか作らないので、ID は文書の順になる。Setext の例 92、93、94、99、101 はコンテナが要るので、8.1 と 8.2 で確かめる。
- 8.2: 設計の「7 は、インデントが 3 桁以下のとき、または、いちばん内側がリストのときに調べる」という文は不正確だった。この文のままでは、仕様の例 312 の `    - e` が項目になってしまうため、実装はインデントが 3 桁以下のときだけ調べる（cmark も同じ条件に `indent < 4` を持つ）。design.md の該当の文も直した。`- - - … a` のような行でテーマの区切りの判定が 2 乗の時間にならないように、`block_parser_t.break_kill`（cmark の `thematic_break_kill_pos` と同じ考え）を足した。リストは開くときに TIGHT にし、ルーズの判定と閉じるときの設定し直しは 8.3 で行う。`content_indent` は 8.4 で設定する。深いリストの後に空行が続くと、1 行あたり深さに比例する時間がかかる。これは 8.4 の打ち切りで解く。
- 8.3: 【利用者に伝える】定義だけの段落も項目の子に数えるため（設計の `child_count` の決まり）、`- [a]: /u\n\n  b` はルーズになる。cmark と commonmark.js ではタイトになる。spec.txt の例はこの違いによらない。テスト `definitions_count_as_children_of_an_item` で固定している。また、`block_parser_t.blank_mark` を足した。これは `ends_blank` を立てうる要素の添字で、一致した要素の印を O(1) で消すためにある（設計の「一致した要素をすべて消す」と同じ結果になる）。空白だけの行が空の項目を続けるのは cmark と同じで、commonmark.js とは違う。
- 8.4: 設計の「残っている要素は空行で必ず続く」は、空白だけの行で続いた子のないリスト項目には成り立たなかった（反例：`"-\n  \n\n  a"`）。このため `blank_run_continues` を足し、いちばん内側が子のない項目のときは、行の残りの桁が `content_indent` の差以上のときだけ打ち切る。design.md も直した。`content_indent` はすべての要素が親から引き継ぎ、リスト項目は自分の `marker_offset + padding` を足す。打ち切る行では `note_blank_line` を呼ばないが、印は同じ値になる。打ち切りの有無で木・範囲・行の記録が同じことを、乱数の文書 120 万件で確かめた（テストの外）。
- 9.1: spec.txt の例のテストは、`{番号, 入力, 期待する木}` の表を節ごとのテストにし、`check_examples` で確かめる。期待する木は、spec の HTML から作ったもので、解析器の出力からは作らない（生成のスクリプトはリポジトリに入れない）。見出しの書き方と、リストの印・区切りは、入力の書き方から決める。例の番号は spec.txt の先頭から数える。
