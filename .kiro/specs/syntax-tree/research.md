# Research & Design Decisions

## Summary
- **Feature**: `syntax-tree`
- **Discovery Scope**: New Feature（木も公開 API もない状態からの新規作成。メモリと行番号は project-foundation の部品に乗る。外部の依存は足さないので、調査は既存のコードとの接続に絞った）
- **Key Findings**:
  - `amark_array_t` は、伸びるときに要素を新しい場所へ写す。ノードを指すポインタは木を作っている間に無効になるので、ノードの識別は添字（32 ビットの ID）で行う。公開 API も、ポインタではなく「文書とノードの ID」の組を受け取る形にする。
  - 内部の `amark_error_t`（`src/error.h`）は `NONE`・`NOMEM`・`OVERFLOW` の 3 つで、要件 10 の 4 つの失敗と合わない。この型を公開ヘッダへ移して値を 5 つに広げ、ライブラリ全体で 1 つのエラーの型にする。`OVERFLOW` は `LIMIT_EXCEEDED` に名前を変える。
  - 行番号を範囲から定める（要件 7.3）には、行の索引が要る。行の索引を作るには内容のバイト列が要るので、文書を作る関数は内容のバイト列も受け取る。これに合わせて要件 7.1 の文言を「内容（バイト列とその長さ）」に直した。
  - `checks.objects` は可変の静的データを禁じ、`abort` の参照も禁じる。このため `assert` は使えない。内部 API の誤用は事前条件として文書に書き、木の正しさは検査の関数で確かめる。
  - 確保関数の型（`amark_allocator_t` など）は、いま内部ヘッダ `src/alloc.h` にある。設定で公開するので、型の定義だけを公開ヘッダへ移す。

## Research Log

### project-foundation の部品との接続
- **Context**: ノードの配列、文書の解放、行番号をどの部品で実現するかを決める。
- **Sources Consulted**: `src/alloc.h`、`src/arena.h`、`src/array.h`、`src/line_index.h`、`src/error.h`、`tests/support/test_alloc.h`
- **Findings**:
  - アリーナは個別の解放を持たず、`amark_arena_deinit` がブロックを 1 つずつ確保関数に返す。再帰はない。
  - `amark_array_t` は容量を 2 倍にして伸び、古い場所はアリーナに残る。残る量の合計は、最後の容量とほぼ同じである。
  - `amark_line_index_build` はバイト列を 2 回走査して表を作る。`amark_line_index_line_at` は二分探索で、最初の行を 1 とする。長さに等しいオフセットも受け付ける。
  - 配列とアリーナの失敗は `NOMEM` か `OVERFLOW` である。
- **Implications**:
  - 文書は「確保関数で確保した本体 1 つ」と「その中のアリーナ」で作る。解放は、アリーナの解放と本体の解放の 2 段階で済む。
  - ノードを足すたびに二分探索を 2 回行う。全体では「ノードの数 × log（行の数）」で、ほぼ線形の範囲に収まる。
  - 行の索引は内容の全体について作る。解析する範囲が内容のごく一部でも、内容の長さに比例する時間がかかる。行番号を内容の先頭から数える（要件 2.4）以上、避けられない。

### 既存の検査との関係
- **Context**: 新しいモジュールが、リポジトリの検査に通る形になっているかを確かめる。
- **Sources Consulted**: `tests/CMakeLists.txt`、`tests/checks/`、`.kiro/specs/unicode-tables/research.md`
- **Findings**:
  - `checks.exports` は、動的ライブラリの公開シンボルが `tests/checks/exported_symbols.txt` と完全に一致することを確かめる。
  - `checks.objects` は、可変の静的データと、`abort`・`exit`・`longjmp` の参照を禁じる。ポインタを含む `const` の表も可変のデータとして数えられる。
  - 公開ヘッダは `include/amark/` をディレクトリごとインストールするので、ヘッダを足してもインストールの規則は変えなくてよい。
- **Implications**:
  - 公開する関数を足すたびに、一覧に名前を足す。
  - 種類の名前の表のような、ポインタを含む表は作らない。種類がブロックかインラインかの判定は、ID の範囲の比較で行う。

### 参考にした実装の木の形
- **Context**: 平坦な配列の木と、解析器が要る操作を見積もる。
- **Sources Consulted**: cmark の `node.h`・`inlines.c`・`blocks.c`（記憶にある構成。今回は取得していない）
- **Findings**:
  - cmark はノードを個別に確保し、ポインタで前後の兄弟・親・最初と最後の子をつなぐ。
  - インラインの解析では、区切りのテキストを取り除き、区切りの間の兄弟を強調やリンクのノードの子に移す操作が頻繁に起きる。
  - ブロックの解析では、開いているブロックの終わりが行を読むたびに延び、段落が Setext 見出しに変わることがある。
- **Implications**: 内部 API は「足す・前に差し込む・範囲を変える・種類を変える・取り除く・包む」を、木の大きさによらない時間で行えるようにする。そのために、内部では「前の兄弟」と「最後の子」の添字も持つ（公開はしない）。

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|--------|-------------|-----------|---------------------|-------|
| ID と文書の組 | 公開 API は `(文書, ノードの ID)` を受け取る。ID は 32 ビットの添字 | 配列が動いても ID は変わらない。ABI に構造体が出ない。不正な ID を範囲の比較で弾ける | 関数の引数が 1 つ増える | 採用 |
| ノードへのポインタ | `const amark_node_t *` を返す | 引数が 1 つで済む | 親や兄弟を引くのに配列の先頭が要る。各ノードに文書へのポインタを持たせると 8 バイト増える。作っている間はポインタが動く | 不採用 |
| 値の構造体のハンドル | `{文書, 添字}` の構造体を値で返す | 引数が 1 つで済む | 構造体のレイアウトが ABI に出る | 不採用 |

## Design Decisions

### Decision: エラーの型は 1 つにまとめる
- **Context**: 内部の部品は `amark_error_t`（`NONE`・`NOMEM`・`OVERFLOW`）を返す。公開 API は、要件 10 の「成功と 4 つの失敗」を返さなければならない。
- **Alternatives Considered**:
  1. 内部の型はそのままにし、公開の型 `amark_status_t` と変換の関数を別に作る
  2. `amark_error_t` を公開の型に広げ、内部の部品も同じ型を返す。`OVERFLOW` は `LIMIT_EXCEEDED` に名前を変える
- **Selected Approach**: 2。最初の設計は 1 だったが、レビューで 2 に改めた。
- **Rationale**: project-foundation は全体の共通の部品なので、エラーの型もそこで 1 つに決めるのが筋である。型が 2 つあると、後続の解析器が部品を呼ぶたびに変換することになり、変換のモジュールも要る。あふれは「実装が表せる大きさを超えた」ことなので、資源の上限の超過と意味が合う。
- **Trade-offs**: project-foundation のコードと設計書に、名前の置き換えが入る。動作は変わらず、メモリ不足とあふれの区別も残る。
- **Follow-up**: 置き換えの後、project-foundation と unicode-tables の単体テストがそのまま通ることを確かめる。

### Decision: ノードの ID は 0 を「ノードがない」、1 を根とする
- **Context**: 要件 4.3 の「ノードがない」ことを表す値と、根の ID を決める。
- **Alternatives Considered**:
  1. 0 を根、`UINT32_MAX` を「ない」とする
  2. 0 を「ない」、1 を根とし、配列の 0 番を使わない
- **Selected Approach**: 2。配列の 0 番は使わない要素として置く。
- **Rationale**: 0 で初期化した変数がそのまま「ない」になる。根の ID が定数になる。
- **Trade-offs**: 要素 1 つ分のメモリを使う。
- **Follow-up**: なし。

### Decision: 属性は別の配列に置く
- **Context**: 属性を持つ種類は少なく、最も大きい属性（リンク参照定義の 3 つの範囲）は 48 バイトを超える。
- **Alternatives Considered**:
  1. ノードの中に共用体で持つ
  2. 属性の配列を別に持ち、ノードは添字を持つ
- **Selected Approach**: 2。属性の要素は種類ごとの構造体の共用体とする。
- **Rationale**: 文書の大半を占めるテキストや段落のノードが小さくなる。
- **Trade-offs**: 属性の読み出しに参照が 1 回増える。
- **Follow-up**: なし。

### Decision: 公開の属性は、項目ごとの関数で返す
- **Context**: 属性を構造体で返すと、項目を足すたびに ABI が変わる。
- **Alternatives Considered**:
  1. 種類ごとの構造体に書き出す関数
  2. 項目ごとの関数。種類が合わないときは「ない」を表す値（0）か `false` を返す
- **Selected Approach**: 2。列挙はすべて 0 を「ない」とする。
- **Rationale**: 項目を足しても既存の関数が変わらない。種類が合わない呼び出しの結果が自然に決まる（要件 4.6）。
- **Trade-offs**: 関数の数が多い（属性だけで 19 個）。
- **Follow-up**: 公開シンボルの一覧に漏れがないことを `checks.exports` で確かめる。

### Decision: 設定は公開の構造体とし、先頭に版を持たせる（libgit2 の方式）
- **Context**: 設定は利用者が項目を書き込むものなので、中身の見えないハンドルにすると確保と解放が要る。一方で、後から項目を足せるようにしたい。
- **Alternatives Considered**:
  1. 中身の見えないハンドルと、項目ごとの設定の関数（libcurl、SQLite）
  2. 公開の構造体。先頭の `struct_size` を `amark_config_init` が書き込む（初めに採った案）
  3. 公開の構造体。先頭の `version` に、利用者のヘッダの `AMARK_CONFIG_VERSION` を入れる。初期化子 `AMARK_CONFIG_INIT` と、版を引数に取る `amark_config_init`（libgit2 の `GIT_*_OPTIONS_INIT` と `git_*_options_init`）
  4. 利用者が `struct_size = sizeof(...)` を自分で書く（Win32 の `cbSize`）、または関数にサイズを渡す（Linux の `clone3`、`openat2`）
- **Selected Approach**: 3。検査は、`version` がライブラリの知っている版でなければ設定の誤りとする。`amark_config_init` は、知らない版なら何も書かずに失敗する。
- **Rationale**: 確保が要らない。版の値が利用者のコンパイルで決まるので、版の合わないヘッダで作った設定を検査で弾ける。案 2 は、`sizeof` をライブラリの中で評価するので、init を呼んだ設定では検査が必ず通り、古いヘッダで小さく確保した設定に新しい大きさで書き込んでしまう（実装の後に見つかり、案 3 に改めた）。案 4 より、書き忘れが起きにくく、既定の値を 1 か所で決められる。
- **Trade-offs**: 利用者は `AMARK_CONFIG_INIT` か `amark_config_init` を必ず使わなければならない。項目を足すたびに、版とマクロを同時に直す。steering（`tech.md`）の「構造体のレイアウトは公開しない」とは合わない例外のままである。
- **Follow-up**: 項目を足す版では、版から構造体の大きさを引く表を持ち、古い版も受け付けるように init と検査を広げる。

### Decision: 診断と範囲は、固定した公開の構造体とする
- **Context**: 診断（4 項目）と範囲（2 項目）を返す形を決める。
- **Selected Approach**: `amark_range_t` と `amark_diagnostic_t` を公開の構造体とし、呼び出した側の変数に書き出す。項目は足さない。
- **Rationale**: brief が「公開する型」として挙げている。項目が少なく、意味が固まっている。
- **Trade-offs**: 項目を足すときは、別の関数を足すことになる。

### Decision: 取り除いたノードの要素は再利用しない
- **Context**: ノードを取り除いた後の配列の要素をどう扱うか。
- **Alternatives Considered**:
  1. 空きのリストにつないで再利用する
  2. そのまま残す（どこからもつながらない）
- **Selected Approach**: 2。取り除いたノードの種類を 0 にする。
- **Rationale**: 単純で、ID が別のノードを指すようになる事故がない。取り除くのは区切りのテキストなどで、数は入力の長さに比例する範囲に収まる。
- **Trade-offs**: メモリが残る。文書の「作ったノードの数」は取り除いたものも数える。
- **Follow-up**: block-parser がノードの数の上限を検査するときは、この数を使う（上限は資源の保護が目的なので、取り除いたものも数えてよい）。

### Decision: 内部 API は範囲の正しさを検査しない
- **Context**: ブロックの終わりは行を読むたびに延びるので、子を足す時点では、親の範囲がまだ子を含んでいないことがある。
- **Selected Approach**: 内部 API は、つながりと行番号だけを正しく保つ。範囲・入れ子・属性の条件は、検査の関数で確かめる。
- **Rationale**: 足すたびに検査すると、解析器が自然な順序で木を作れない。
- **Trade-offs**: 誤りは、検査の関数を呼ぶまで見つからない。
- **Follow-up**: 解析器の単体テストは、解析のたびに検査の関数を呼ぶ。

### Synthesis の結果
- **一般化**: 方言の種類のノードは、CommonMark の種類のノードと同じ要素と同じ操作で扱う。違いは、ブロックかインラインかを ID から決められないので、作るときに指定することだけである。
- **Build vs. Adopt**: 木の入れ物として使える C99 のライブラリで、確保関数を差し替えられ、原文を複製しないものはない。project-foundation の配列とアリーナの上に作る。
- **単純化**:
  - 「最後の子」と「前の兄弟」をたどる公開の関数は作らない（要件にない）。
  - 種類の名前を返す関数、エラーの説明を返す関数は作らない（要件にない）。
  - 文書の本体とノードの定義を 1 つの内部ヘッダにまとめ、モジュールは「文書」「木を作る」「読み出す」「検査する」「設定」の 5 つにとどめる。
  - エラーの型を 1 つにまとめ、変換のモジュールをなくした。

## Risks & Mitigations
- 作っている間に配列が動くので、内部でノードへのポインタを持ち越すと壊れる — 内部 API は ID だけを受け渡しし、ポインタは 1 つの関数の中で、配列に足した後に取り直す。ASan の構成で確かめる。
- 取り除いた部分木の中のリンク参照定義を、リンクが指したままになりうる — 検査の関数は、参照先が範囲の中にあり、種類がリンク参照定義であることだけを確かめる。部分木ごと取り除いた場合の参照は、取り除く側（解析器）の責任とする。
- 設定の `version` を初期化し忘れる — 0 は版として使わないので、0 で埋めた設定は検査が設定の誤りを返す。公開ヘッダの注釈と README の例で `AMARK_CONFIG_INIT` か `amark_config_init` を必ず使うことを示す。
- 確保関数の型とエラーの型を公開ヘッダへ移し、`OVERFLOW` の名前を変えるので、project-foundation のコードに触れる — 型の定義の移動と名前の置き換えだけで、関数と動作は変えない。既存の単体テストがそのまま通ることを確かめる。
