# Requirements Document

## Project Description (Input)
**誰が困っているか**：amark を自分のプロジェクトに組み込む利用者と、インラインの解析結果を使う下流の spec（dialect-extension、spec-conformance）の開発者。

**現在の状況**：block-parser は、段落や見出しの内容の範囲と、リンク参照定義の表（正規化したラベルをキーとする）を用意する。しかし、その内容に含まれるインライン構造を CommonMark 0.31.2 の規則どおりに解析する部分がない。強調の区切りの扱いや、リンクの括弧の対応は、素朴に書くと時間が入力の 2 乗になったり、再帰が深くなったりしやすい。

**何を変えるか**：
- 次の要素を解析し、syntax-tree の内部 API でノードとして木に加える。ノードは範囲だけを持ち、原文を複製しない。
  - コードスパン：バッククォートの列の長さが一致するものを探す。探索は線形の時間で行う。
  - バックスラッシュのエスケープ
  - 文字参照：実体名、10 進、16 進
  - リンクと画像：インライン、完全参照、省略参照、ショートカット。参照は定義の表で解決する。dest と title の範囲、参照先の定義を属性として持つ。
  - オートリンク：URI とメールアドレス
  - 生の HTML：開始タグ、終了タグ、コメント、処理命令、宣言、CDATA
  - 強調と強い強調：区切りのスタックの方式と、3 の倍数の規則。句読点と空白の判定には unicode-tables を使う。
  - ハードな改行とソフトな改行
  - テキスト
- 病的な入力（ネストした括弧、大量の区切り、閉じないコードスパンなど）でも、時間がほぼ線形で、再帰を使わない。
- インラインの単体テストを用意する。
- 方言の差し込み口（インラインの起動文字、区切りの種類）を、設計の段階で確保しておく。

**方針**：cmark の区切りのスタックと括弧のスタックの方式に従い、`openers_bottom` などの下限の表で時間を線形に保つ。コードスパンは、バッククォートの列の長さごとに最後に見た位置を記録して線形にする。境界の候補は、字句の走査（起動文字の表）、区切りの処理（強調）、括弧の処理（リンクと画像、参照の解決）。

**範囲外**：エスケープと文字参照を文字に戻した値を作ること（source-text）、方言の公開 API（dialect-extension）、GFM の取り消し線や拡張オートリンク（後の段階）、URL の正規化やパーセントエンコード（出力する側の責任。テスト用の HTML 出力では spec-conformance が扱う）。

**制約**：再帰を使わない。時間は入力の長さにほぼ比例する。原文を複製しない。対象は CommonMark 0.31.2。上流は block-parser（内容の範囲、定義の表、ラベルの正規化）、syntax-tree、unicode-tables。
