# Research & Design Decisions

## Gap Analysis（実装の差の分析）

- **対象**：`source-text`（requirements.md、要件 1〜13）
- **調べたもの**：`include/amark/`、`src/`、`tests/`、block-parser・inline-parser・syntax-tree・unicode-tables の requirements.md と実装
- **方法**：要件ごとに、既存のコードで使えるものと、足りないものを対応させた。外部の依存はないので、外部の調査は行っていない。

### 1. 現在の状態

#### 使える部品

| 部品 | 場所 | source-text での使い道 |
|---|---|---|
| 行の記録（`content_start`、`pad`） | `src/line.h`、`src/parse_data.h` | プレフィックスとインデントを除く。タブの残りの桁を補う。行番号から一定の時間で引ける。 |
| 行の境（`start`、`content_end`、`end`） | `amark_line_bounds`（`src/line.h`） | 行の内容の終わりと、行末記号の終わりを得る。3 種類の行末記号と、範囲の端で切れる場合を、ここが 1 か所で扱っている。 |
| カーソル | `src/cursor.h` | 範囲の中の「行の内容」だけを順に読む。コードスパンの中身、title、複数の行にわたるインラインに合う。 |
| 実体名の参照 | `amark_entity_lookup`（`src/entity.h`） | 名前から、1 つまたは 2 つのコードポイントの UTF-8（1〜6 バイト）を得る。確保しない。 |
| 文字参照の認識 | `amark_inline_scan_entity`（`src/inline_scan.h`） | 構文（10 進 1〜7 桁、16 進 1〜6 桁、表にある名前、`;`）を認識する。値は返さない。 |
| 不正なバイト列の読み方 | `amark_utf8_decode_lossy`（`src/utf8.h`） | 極大の部分 1 つを U+FFFD として読む。解析と同じ区切り方になる。U+0000 は U+0000 のまま返す。 |
| 閉じるフェンスの判定 | `amark_scan_close_fence`（`src/scan.h`） | コードブロックの最後の行が、閉じるフェンスかを確かめる。 |
| 属性の範囲 | `amark_link_destination`、`amark_link_title`、`amark_definition_*`、`amark_code_block_info`（`include/amark/tree.h`） | dest、title、info の範囲。「書かれていない」は false、「書かれているが空」は true で長さ 0。要件 7 の 11 の区別と同じ形である。 |
| 確保関数 | `doc->allocator`、`amark_malloc`、`amark_free`、`amark_size_add`（`src/alloc.h`） | 確保関数で作る文字列と、その解放。大きさの計算のあふれの検査。 |
| 内容 | `amark_document_content`（`src/document.h`） | 文書が内容の位置と長さを持っている。原文のバイト列の取り出しは、これと範囲だけでできる。 |
| テストの支援 | `tests/support/test_alloc.h`、`tree_dump.h` | 確保を数え、指定した回で失敗させる。 |

#### 守る決まり

- 公開ヘッダは `include/amark/` に置き、`amark.h` から取り込む。関数に `AMARK_API` を付ける。`tests/checks/exported_symbols.txt` と `tests/public/header_cxx.cpp` を合わせる。
- モジュールは `src/<name>.c` と内部ヘッダの組にし、`src/CMakeLists.txt` の `AMARK_SOURCES` に 1 行足す。公開ヘッダと同じ名前になるときは、内部ヘッダに `_internal` を付ける。
- 単体テストは `tests/unit/test_<module>.c`、公開 API だけのテストは `tests/public/` に置く。
- 依存の向き：文字列の取り出しは、ブロックの解析（行の記録）、構文木、Unicode の表に依存する。インラインの解析には依存しない（structure.md の図）。
- たどる API は、文書を変えず、確保せず、失敗を固定の値で返す（`bool` と `*out`）。エラーの種類は `amark_error_t` の 5 つである。

### 2. 要件と既存の部品の対応

| 要件 | 使える部品 | 差 |
|---|---|---|
| 1 原文のバイト列 | `amark_node_range`、`amark_document_content` | **Missing**：公開の関数だけがない。実装は小さい。 |
| 2 論理的な文字列 | 行の記録、行の境 | **Missing**：行をつなぐ処理。**Constraint**：カーソルは `pad` を見ず、行末記号で終わる範囲を扱えない（下の 3.1）。 |
| 3 コードブロックの中身 | 行の記録、`amark_scan_close_fence` | **Missing**：コードの行の範囲を決める処理。**Constraint**：閉じるフェンスの有無が属性にない（下の 3.2）。 |
| 4 コードスパンの中身 | カーソル | **Missing**：バッククォートの列を除く処理、行末記号を空白にする処理、前後の空白 1 つの除去。inline-parser は範囲だけを定めている（その要件 6 の 7）。 |
| 5 文字に戻す決まり | `amark_entity_lookup`、`amark_inline_scan_entity` | **Missing**：値を作る処理（数値の計算、不正な値の U+FFFD、UTF-8 の符号化）。構文の認識は、inline-parser と同じ規則を 2 か所に持たない形にしたい（下の 3.3）。 |
| 6 テキストなどの値 | ノードの範囲、種類 | **Missing**：種類ごとの振り分け。 |
| 7 dest と title | 属性の範囲、カーソル | **Missing**：範囲に要件 5 を適用する処理。**Constraint**：属性の範囲の開始行を引く時間（下の 3.4）。 |
| 8 info | `amark_code_block_info` | **Missing**：同上。info は 1 行の中なので、行をまたぐ処理は要らない。 |
| 9 文字の扱い | `amark_utf8_decode_lossy` | **Missing**：出力のときの置き換え。**Constraint**：文書は UTF-8 の扱いの設定を持たない（下の 3.5）。 |
| 10 結果の受け渡し | `doc->allocator`、`amark_malloc` | **Missing**：バッファに書く仕組みと、文字列の確保と解放。この形の API は、既存のコードに例がない（下の 3.6）。 |
| 11 答えられない呼び出しと失敗 | `amark_error_t`、たどる API の `bool` | **Constraint**：`amark_error_t` に「答えられない」と「バッファに収まらない」にあたる値がない（下の 3.6）。 |
| 12 共通の性質 | 既存の検査（`CheckExports.cmake`、`CheckObjects.cmake`） | **Constraint**：解析データのない文書の扱い（下の 3.7）。時間の決まり（下の 3.4）。 |
| 13 単体テスト | `test_alloc.h`、`tests/unit/test_spec_*.c` | **Missing**：テスト。**Unknown**：spec.txt の例をどう持つか（下の 3.8）。 |

### 3. 設計で決めること（制約と不明な点）

#### 3.1 カーソルは、そのままでは論理的な文字列に使えない
- カーソルは `pad` を見ない。段落と見出しの行では `pad` が常に 0 なので、インラインの解析では困らなかった（`paragraph_add_line` が、最初の空白でないバイトまで進めてから記録する）。`pad` が 0 でなくなるのは、コードブロックと HTML ブロックの行だけである。
- カーソルの位置は、行の内容の中か、その終わりに限られる。行末記号の直後で終わる範囲（ハードな改行とソフトな改行のノード、最後の行の長さが 0 のコードブロックと HTML ブロック）は、前提を満たさない。
- カーソルの前提には「範囲は、ブロックの解析が用意したインラインの内容」とある。実際の動作は、行の記録が書かれた範囲なら同じである。
- inline-parser の research.md は「source-text もカーソルを要する見込み。そのときに、まとめるかを改めて決める」としている。

#### 3.2 閉じるフェンスの有無が、属性にない
- 要件 3 の 2 は、閉じるフェンスの行を結果から除くことを求める。コードブロックの属性は、書き方、フェンスの文字、開始のフェンスの長さ、info だけである。
- 最後の行を調べ直して判定できる。ブロックの解析は、閉じるフェンスの行の記録を、最初の空白でないバイト（`pad` は 0）にする。コードの行でインデントが残るときは、記録の位置のバイトが空白かタブになる。そのため「記録の位置のバイトがフェンスの文字で、そこからの `amark_scan_close_fence` が開始のフェンスの長さ以上」なら閉じるフェンスである、と判定できる見込みである。
- 開始行と終了行が同じ（開始のフェンスの行だけ）のときは、コードの行がない。この場合を先に除く。
- **Research Needed**：上の判定が、すべての場合（開始のフェンスのインデントが 1〜3、コンテナの中、タブ、最後の行の長さが 0）で正しいことを、設計で確かめる。確かめられなければ、block-parser に「閉じるフェンスがある」という属性を足す案になる（上流の変更）。

#### 3.3 文字参照の構文の規則を、2 か所に持たない
- `amark_inline_scan_entity` は、カーソルを進めて真偽を返すだけで、値を返さない。source-text が構文を自分で読み直すと、同じ規則（桁の数、`;`、名前の文字）が 2 か所になる。
- 依存の向きでは、文字列の取り出しは、インラインの解析に依存しない。`inline_scan.c` の関数を呼ぶと、この向きに反する。

#### 3.4 属性の範囲の開始行を引く時間
- ノードは開始行と終了行を持つので、ノードの範囲の最初の行は、一定の時間で得られる。
- dest と title の範囲は、行を持たない。行の索引（`amark_line_index_line_at`）は 2 分探索で、時間は行の数の対数に比例する。
- 要件 12 の 1 は「行の数によらない」としている。ノードの開始行から行を順に進めれば行の数によらないが、時間は、読む範囲ではなく、ノードの範囲の長さに比例する（長いリンクのテキストの後ろの dest など）。
- info は、ノードの開始行にあるので、問題がない。
- **要件の見直しの候補**：要件 12 の 1 を「読む範囲の長さと、行の数の対数に比例する」に緩めるか、ノードの範囲の長さまでを認めるか。設計の前に決めたい。

#### 3.5 文書は、UTF-8 の扱いの設定を持たない
- 解析の設定の `utf8_mode` は、`amark_parse` の中だけで使われ、文書に残らない。
- 「エラーにする」設定で解析した文書は、解析する範囲が正しい UTF-8 である。そのため、常に `amark_utf8_decode_lossy` と同じ読み方で出力すれば、どちらの設定でも要件 9 の 2 と 5 を満たす。設定を文書に残す必要はない見込みである。
- U+0000 の置き換えは、`amark_utf8_decode_lossy` が行わないので、出力する側で行う。

#### 3.6 結果の返し方に、既存の例がない
- たどる API は、`bool` と `*out` で答え、失敗しない。source-text は、成功、「答えられない」、「バッファに収まらない」、メモリ不足、資源の上限の超過の 5 つを区別して返す（要件 11 の 5）。
- `amark_error_t` の値は固定で、「答えられない」と「バッファに収まらない」にあたるものがない。
- 確保した文字列を利用者が解放する形は、structure.md の「個別に解放するものを作らない」の例外になる。文書のアリーナに置く案は、文書を変えるので、要件 12 の 5 と 6（状態を残さない、同時に読める）に反する。設計で採るなら、structure.md に例外を書き足す。
- 要件 12 の 6 は、確保関数が同時に呼ばれてよいことを前提にしている。この前提は、`include/amark/allocator.h` の説明にも書く必要がある。

#### 3.7 解析データのない文書
- 行の記録は、解析データ（`doc->parse_data`）にある。内部 API で直接作った文書（syntax-tree の単体テストなど）は、解析データを持たない。`amark_line_get` は、そのとき false を返す。
- 公開 API から得られる文書は、必ず `amark_parse` が作るので、利用者には起きない。ただし、内部の関数としては、未定義の動作にせず、決まった値を返す必要がある。

#### 3.8 単体テストでの spec.txt の例
- 既存の `tests/unit/test_spec_*.c` は、例を C の文字列として持ち、木の構造（`tree_dump`）を比べている。値（エスケープを戻した文字列）は比べていない。
- 要件 13 の 1 は、値を「HTML のエスケープとパーセントエンコードを施す前の文字列」と比べることを求める。期待する値を、例ごとに手で書くことになる。
- **Research Needed**：対象の 10 の節の例の数と、期待する値の書き方（節ごとのファイルにするか、種類ごとにするか）。

### 4. 実装の方式の候補

#### Option A：既存のモジュールを広げる
- カーソルに `pad` と行末記号の扱いを足す。`inline_scan.c` の文字参照の認識を、値も返すように広げる。公開の関数は `tree.c` に足す。
- ✅ 新しいファイルが少ない。構文の規則が 1 か所のままになる。
- ❌ 文字列の取り出しが、インラインの解析（`inline_scan.c`）に依存し、structure.md の依存の向きに反する。
- ❌ カーソルの前提（位置は行の内容の中）を変えるので、インラインの解析とそのテストに影響する。`tree.c` は「解析の規則を知らない」という決まり（syntax-tree の要件 12 の 8）に反する。

#### Option B：新しいモジュールを作る
- 公開ヘッダ（`include/amark/text.h` など）と、`src/` の新しいモジュールを作る。行をつなぐ処理、文字に戻す処理、受け渡しを、すべて新しく書く。行の記録と行の境は、`line.h` の関数で直接読む。
- ✅ 依存の向きを守る。既存のコードとテストを変えない。責任がはっきり分かれる。
- ❌ 文字参照の構文の規則が、`inline_scan.c` と 2 か所になる。食い違いは、テストでしか見つけられない。

#### Option C：組み合わせる
- 文字参照の「認識して値を返す」関数を、下の層（`entity.c` か新しい小さなモジュール）に移し、`inline_scan.c` と source-text の両方がそれを呼ぶ。`amark_inline_scan_entity` は、その関数を呼ぶ薄い関数にする。
- 行をつなぐ処理と受け渡しは、新しいモジュールに書く。カーソルは変えない（必要なら、コードスパンの中身と title を読むのに、そのまま使う）。
- ✅ 構文の規則が 1 か所になり、依存の向きも守る。インラインの解析の動作は変わらない。
- ❌ inline-parser のコードに、小さな書き換えが入る（既存のテストで確かめられる）。新しいモジュールの中の分け方（行をつなぐ、文字に戻す、受け渡す）を、設計で決める必要がある。

### 5. 工数とリスク

- **工数：M（3〜7 日）**。処理そのものは、1 回の走査で済む素直なものである。量が多いのは、種類ごとの決まりと、境の場合のテスト（spec.txt の 10 の節、3 種類の行末記号、コンテナ、タブ、確保の失敗の注入）である。
- **リスク：Medium**。未知の技術はない。ただし、公開 API の形（結果の返し方）に既存の例がなく、ABI として後から変えにくい。閉じるフェンスの判定（3.2）と、時間の決まり（3.4）に、確かめることが残る。

### 6. 設計への申し送り

- **方式**：Option C が、依存の向きと「規則は 1 か所」の両方を満たす。採るかどうかは設計で決める。
- **設計の前に決めたいこと**：
  - 要件 12 の 1 の時間の決まりを、属性の範囲（dest と title）についてどうするか（3.4）。
- **設計で決めること**：
  - 公開 API の形。戻り値で 5 つの結果をどう区別するか。`amark_error_t` に値を足すか、別の型を作るか（3.6）。
  - 確保した文字列の解放の関数と、structure.md の例外の書き方（3.6）。
  - 行をつなぐ処理を、カーソルとは別に作るか、カーソルを広げるか（3.1）。
  - 解析データのない文書で返す値（3.7）。
- **Research Needed**：
  - 閉じるフェンスの判定が、すべての場合で正しいこと（3.2）。
  - spec.txt の対象の節の例の数と、期待する値の持ち方（3.8）。
  - 後の段階の候補（markdown-writer、source-edit）を、この spec の API の上に、本体の設計を変えずに足せること（roadmap.md の Future Phases が求める確認）。
