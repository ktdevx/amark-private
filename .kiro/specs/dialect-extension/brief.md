# Brief: dialect-extension

## Problem
GFM の表・取り消し線・タスクリスト・脚注などの方言を、本体のコードを変えずに足せるようにしたい。しかし方言の規則が不正な結果（範囲が親の外にある、兄弟と重なる、原文の順でない、など）を返すと、木の不変条件が壊れる。

## Current State
block-parser と inline-parser は、差し込み口の位置を設計の段階で確保している。この spec では、それを公開 API として仕上げる。

## Desired Outcome
- 方言（拡張の集合）を表す公開 API がある。規則は次の差し込み口に登録する。
  - ブロック：新しいブロックの開始、継続の判定、閉じるときの処理（段落を表に変える、など）
  - インライン：起動文字と、区切りの種類（取り消し線の `~` など）
  - 後処理：木ができた後に、ノードを加えたり種類を変えたりする（タスクリストの印など）
- 方言は、独自のノードの種類と属性を登録できる。
- 規則が返した結果を本体が検査する。不正なら、その結果を採用せずに診断を出し、木を壊さない。解析はそのまま続ける。
- テスト用の小さな方言で、各差し込み口と検査が動くことを確かめる。
- 方言は状態を持たないか、文書ごとの状態だけを持つ。同じ方言を、並行する別々の解析で使える。

## Approach
方言は、規則の関数ポインタと、規則が使うデータをまとめた const な構造体の集合とする。本体は決まった時点で規則を呼び、返された範囲と構造を、syntax-tree の不変条件の検査で確かめてから採用する。

## Scope
- **In**:
  - 方言の公開 API と差し込み口の契約
  - 独自のノードの種類と属性の登録
  - 規則が返した結果の検査と診断
  - テスト用の方言と、そのテスト
- **Out**:
  - GFM の各拡張の実装（後の段階で別の spec にする）
  - 規則を設定で変えること（タブ幅などは変えられない）

## Boundary Candidates
- 方言の登録の API
- 規則を呼び出す契約（入力、返り値、所有権）
- 結果の検査と診断

## Out of Boundary
- CommonMark の規則そのもの（block-parser、inline-parser）

## Upstream / Downstream
- **Upstream**: block-parser、inline-parser、syntax-tree
- **Downstream**: 後の段階の GFM の spec（表、取り消し線、タスクリスト、脚注、拡張オートリンク）

## Existing Spec Touchpoints
- **Extends**: なし
- **Adjacent**: block-parser、inline-parser（差し込み口を確保する箇所）、syntax-tree（方言のノードの種類）

## Constraints
- 方言を使わないとき（CommonMark だけのとき）、結果と性能に影響しない。
- 規則が不正な結果を返しても、本体が壊れない。診断を出し、木を正しく保つ。
- 再帰を使わない。時間がほぼ線形であることを、方言の側でも損なわない設計にする。
