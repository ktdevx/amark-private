- [ ] 1. ビルドとインストールの基盤
- [x] 1.1 プロジェクトの定義、オプション、共通のコンパイル設定を用意する
  - プロジェクトの名前を `Amark`、版を 0.1.0 とし、版をこの 1 か所だけで定義する。CMake 3.21 より古い版では、必要な版を示して構成を止める
  - テストのビルド、警告のエラー化、サニタイザ、インストールの 4 つのオプションを、設計の表の既定値で定義する（テストとインストールは最上位のときだけ既定で有効、警告のエラー化とサニタイザは既定で無効）
  - amark のターゲットに共通の設定（拡張なしの C99、シンボルを既定で隠す、多めの警告、オプションに応じた警告のエラー化）を 1 つの関数で与えられるようにする
  - サニタイザのオプションを有効にすると、GCC と Clang ではアドレスと未定義動作の検査をコンパイルとリンクに加え、それ以外のコンパイラでは理由を示して構成を止める
  - 最上位のときは、実行ファイルと DLL の出力先を 1 つのディレクトリにそろえる。ビルドのディレクトリを無視する `.gitignore` と、MIT の全文と「The Amark Authors」の著作権表示を書いた LICENSE を置く
  - この spec で足すソースとビルドの設定には、すべて design の RepoDocs に示した 2 行の著作権表示を先頭に付ける
  - ライブラリのソースのディレクトリはまだ加えない（1.2 で加える）。共通のコンパイル設定とサニタイザの指定が実際に効くことは、1.2 以降のビルドで確かめる
  - 完了の状態：テストを無効にした構成が通り、キャッシュに 4 つのオプションが設計どおりの既定値で現れる。サニタイザのオプションを GCC と Clang 以外のコンパイラで有効にしたときに構成を止める分岐は、手元の Linux では動かせないので、CMake のコードを読んで確かめ、実際の動作は CI の MSVC の構成で確かめる

- [ ] 3. 失敗の種類と確保関数の抽象
- [x] 3.1 失敗の種類と、確保関数の抽象を実装する
  - 内部の部品が返す失敗の種類として、成功、メモリ不足、大きさのあふれの 3 つを定める
  - 確保関数が指定されていなければ標準の `malloc` と `free` を使い、指定されていればその関数の組と文脈の値だけを使う。文脈の値は変えずに毎回渡す
  - 確保は、確保関数の失敗をメモリ不足として返し、要素の数と大きさの積があふれるときは確保関数を呼ばずにあふれとして返す。大きさ 0 の要求は 1 バイトとして扱う。NULL の解放は何もしない
  - 大きさの加算と乗算を、あふれを検出して知らせる形で提供する
  - 標準の `malloc` と `free` を呼ぶのはこのモジュールだけにし、可変の静的な状態、`abort`・`exit`・`longjmp`、再帰、`assert` を使わない
  - 完了の状態：テスト用の静的ライブラリにこのモジュールが加わり、警告なしにビルドできる
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5, 6.6, 6.7, 12.1, 12.2, 12.4, 12.5, 12.6, 12.7_

- [x] 3.2 数え、失敗させるテスト用の確保関数と、確保関数の抽象の単体テストを作る
  - テスト用の確保関数は、確保と解放の回数、解放されていないかたまりの数、文脈の値の食い違いの回数を数え、指定した回の確保を失敗させる。内部の関数のテストから使えるテスト専用のライブラリにする
  - 確保関数の抽象について、既定の確保関数での確保と解放、指定した確保関数だけが呼ばれること、文脈の値がそのまま渡ること、確保関数の失敗、積のあふれで確保関数が呼ばれないこと、NULL の解放、加算と乗算の境界を確かめる
  - 内部の関数のテストを登録する関数（2.1）に、このテスト用のライブラリへのリンクを加える。このテストが、その関数の最初の実際の使用になる
  - 後続のテストが使う「失敗させる回を 1 から順に増やし、毎回の後始末のあとに未解放が 0 であることを確かめる」繰り返しの書き方を、このテストで示す
  - 完了の状態：確保関数の抽象の単体テストが、静的と動的の両方の構成で通る
  - _Requirements: 6.1, 6.2, 6.3, 6.4, 6.5, 6.6, 6.7, 12.9, 12.10_

- [x] 4. アリーナを実装し、単体テストで確かめる
  - 確保関数から得たかたまりを単方向のリストで持ち、要求をかたまりから整列した位置で切り出す。整列は C99 で使える最も厳しい型の整列とする
  - かたまりの大きさは 4096 バイトから始めて 2 倍ずつ増やし、1 MiB で止める。次のかたまりより大きい要求には専用のかたまりを得て、現在のかたまりの残りは使い続ける
  - 大きさの計算にはあふれの検出を使い、あふれや確保関数の失敗のときは状態を変えず、それまでに返したメモリを有効なままにする
  - 解放は繰り返しでリストをたどり、確保関数から得たすべてのかたまりを返す。2 回続けて解放しても安全で、初期化の直後と同じ状態に戻る
  - 単体テストで、整列、小さな確保 10,000 回での確保関数の呼び出しの少なさ、内容が保たれること、1 MiB を超える確保、途中の失敗の注入、あふれ、解放後の未解放 0 を確かめる
  - 完了の状態：アリーナの単体テストが、静的と動的の両方の構成で通り、失敗の注入の繰り返しのすべての回で未解放が 0 になる

- [ ] 5.3 (P) UTF-8 の検査とデコードを実装し、単体テストで確かめる

  - 検査は、最短でない符号化、サロゲート、U+10FFFF を超える値、途中で切れた列、先頭のない継続バイト、0xC0・0xC1・0xF5〜0xFF を不正とし、最初の不正な列のオフセットを返す。U+0000 と U+FEFF は正しく、長さ 0 も正しい。確保はしない
  - デコードは、検査済みのバイト列の文字の先頭から、コードポイントとバイト数を返し、範囲の外を読まない
  - 単体テストで、1〜4 バイトの各範囲の境界、U+0000 と U+FEFF、不正の各種類での不正な位置、デコードの値と長さを確かめる

## Implementation Notes
- 1.1: `BUILD_SHARED_LIBS` は `option()` にしない（サブプロジェクトでキャッシュを汚さないため）。サニタイザの指定はルートのディレクトリの範囲で効く。
- 1.2: `AMARK_SOURCES` は `src/CMakeLists.txt` の局所変数なので、`amark_testing`（2.1）も同じファイルで定義する。生成ヘッダ `export.h` には著作権表示がないので、6.3 の検査はリポジトリに置いたファイルだけを対象にする。
- 1.3: Ninja などのシングル構成のジェネレータで `CMAKE_BUILD_TYPE` が空のまま `cmake --install --config <cfg>` を実行すると、構成ごとの `AmarkTargets-*.cmake` が置かれず `find_package` が失敗する。README、CI、利用側の手順では、構成のときに `-DCMAKE_BUILD_TYPE=<cfg>` を渡す（マルチ構成では無視される）。
- 2.1: 登録の関数は `amark_add_unit_test(<name> SOURCES <src>... [LIBRARIES <lib>...])` と `amark_add_public_test(<name> SOURCES <src>...)` の形で呼ぶ。libm は検出で必要なときだけリンクする。手元の Clang には ASan の実行時ライブラリ（libclang-rt-18-dev）を入れた。
- 2.2: C++ はテストの構成でだけ有効にする。サニタイザの構成では C と C++ のコンパイラを同じ系統にそろえる（CI では `CMAKE_C_COMPILER` と `CMAKE_CXX_COMPILER` の両方を指定する）。
- 3.1: 確保関数の抽象のファイル名は `src/alloc.h` と `src/alloc.c`。`amark_malloc_array` はあふれのときも `*out` を NULL にする。
- 3.2: 失敗の注入の繰り返しは `tests/unit/test_alloc.c` の `failure_injection_loop` を手本にする。テストで確保したものは静的な fixture の変数に置き、teardown で解放してから `live == 0` と `ctx_mismatch == 0` を確かめる（`NAOS_REQUIRE` は longjmp で抜けるため）。
- 4: アリーナのテストは、確保した範囲の全体に書き込んでから内容を確かめる（書かないと範囲の外への書き込みを見逃す）。境界の値（ちょうど収まる大きさ、1 つ上の大きさ）を必ず試す。
