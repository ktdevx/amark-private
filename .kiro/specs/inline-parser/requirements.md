# Requirements Document

## Project Description (Input)
**誰が困っているか**：amark を自分のプロジェクトに組み込む利用者と、インラインの解析結果を使う下流の spec（dialect-extension、spec-conformance）の開発者。

**現在の状況**：block-parser は、段落や見出しの内容の範囲と、リンク参照定義の表（正規化したラベルをキーとする）を用意する。しかし、その内容に含まれるインライン構造を CommonMark 0.31.2 の規則どおりに解析する部分がない。強調の区切りの扱いや、リンクの括弧の対応は、素朴に書くと時間が入力の 2 乗になったり、再帰が深くなったりしやすい。

**何を変えるか**：
- 次の要素を解析し、syntax-tree の内部 API でノードとして木に加える。ノードは範囲だけを持ち、原文を複製しない。
  - コードスパン：バッククォートの列の長さが一致するものを探す。探索は線形の時間で行う。
  - バックスラッシュのエスケープ
  - 文字参照：実体名、10 進、16 進
  - リンクと画像：インライン、完全参照、省略参照、ショートカット。参照は定義の表で解決する。dest と title の範囲、参照先の定義を属性として持つ。
  - オートリンク：URI とメールアドレス
  - 生の HTML：開始タグ、終了タグ、コメント、処理命令、宣言、CDATA
  - 強調と強い強調：区切りのスタックの方式と、3 の倍数の規則。句読点と空白の判定には unicode-tables を使う。
  - ハードな改行とソフトな改行
  - テキスト
- 病的な入力（ネストした括弧、大量の区切り、閉じないコードスパンなど）でも、時間がほぼ線形で、再帰を使わない。
- インラインの単体テストを用意する。
- 方言の差し込み口（インラインの起動文字、区切りの種類）を、設計の段階で確保しておく。

**方針**：cmark の区切りのスタックと括弧のスタックの方式に従い、`openers_bottom` などの下限の表で時間を線形に保つ。コードスパンは、バッククォートの列の長さごとに最後に見た位置を記録して線形にする。境界の候補は、字句の走査（起動文字の表）、区切りの処理（強調）、括弧の処理（リンクと画像、参照の解決）。

**範囲外**：エスケープと文字参照を文字に戻した値を作ること（source-text）、方言の公開 API（dialect-extension）、GFM の取り消し線や拡張オートリンク（後の段階）、URL の正規化やパーセントエンコード（出力する側の責任。テスト用の HTML 出力では spec-conformance が扱う）。

**制約**：再帰を使わない。時間は入力の長さにほぼ比例する。原文を複製しない。対象は CommonMark 0.31.2。上流は block-parser（内容の範囲、定義の表、ラベルの正規化）、syntax-tree、unicode-tables。

## Introduction
inline-parser は、CommonMark 0.31.2 のインライン構造の解析を作る。block-parser まででは、解析の入口が返す文書はブロックのノードだけを持ち、段落と見出しの中身（強調、リンク、コードスパンなど）は、利用者が自分で解析しなければならない。この spec で、利用者は解析の入口から、ブロックとインラインの両方を持つ木を受け取れるようになる。

この spec は、次の 4 つを用意する。

1. **インラインの解析**：段落と見出しの内容を解析し、インラインのノード（テキスト、コードスパン、強調、強い強調、リンク、画像、オートリンク、生の HTML、ハードな改行、ソフトな改行、バックスラッシュのエスケープ、文字参照）を、範囲と属性とともに木に加える。
2. **参照の解決**：参照の形式のリンクと画像を、block-parser の定義の表で解決し、参照先のリンク参照定義を属性にする。
3. **解析の入口への統合**：解析の入口が、ブロックの解析に続けてインラインの解析を行う。資源の上限と失敗の扱いは、ブロックと同じ決まりに従う。
4. **方言の規則を呼ぶ箇所**：インラインの起動文字と区切りの種類を、方言が足せる箇所を確保する。

この文書で「利用者」は amark を自分のプロジェクトに組み込む人、「下流の開発者」は dialect-extension、source-text、spec-conformance を開発する人を指す。「内容」「解析する範囲」「文書」「行末記号」「プレフィックス」「深さ」は、block-parser の requirements.md と同じ意味で使う。「空白」は、断らない限りスペース（U+0020）とタブ（U+0009）を指す。「内容の範囲」は、block-parser が段落と見出しのそれぞれについて用意する、インラインとして解析する部分の範囲を指す。「行の内容」は、内容の範囲のうち、各行で、行の記録が「内容が始まる位置」とする位置から後ろの部分を指す（コンテナのプレフィックスと、段落の続きの行の先頭の空白を含まない）。「区切りの列」は、連続する `*` または連続する `_` の並びを指す。

## Boundary Context
- **In scope**:
  - 段落と見出し（ATX と Setext）の内容の範囲を、インラインとして解析すること
  - インラインの 12 種類のノードを作り、範囲と属性を定めること
  - 参照の形式のリンクと画像を、定義の表で解決すること
  - 解析の入口に、インラインの解析を足すこと。入れ子の深さとノードの数の上限を、インラインのノードにも適用すること。
  - 病的な入力でも、時間をほぼ線形に保ち、再帰を使わないこと
  - 方言の規則を呼ぶ箇所（インラインの起動文字、区切りの種類）を確保すること
  - 上の各項目の単体テスト。spec.txt のインラインに関わる節の例を含む。
- **Out of scope**:
  - バックスラッシュのエスケープと文字参照を、文字に戻した値を作ること。dest・title・コードスパンの中身などの、意味上の値を得ること（source-text）。この spec は、範囲と種類だけを定める。
  - URL の正規化とパーセントエンコード、HTML のエスケープ、画像の代替テキストの組み立て（出力する側の責任。テスト用の HTML 出力では spec-conformance が扱う）
  - 方言を定義して規則を登録する公開 API、規則を呼び出す契約、規則が返した結果の検査と診断（dialect-extension）
  - GFM の取り消し線、拡張オートリンクなどの拡張（後の段階）
  - spec.txt の全例を HTML と比べて確かめること、全体の性質の総合のテスト（spec-conformance）
  - コードブロック、HTML ブロック、リンク参照定義の中身を、インラインとして解析すること（これらの中身は解析しない）
  - 構文の規則を設定で変えること
- **Adjacent expectations**:
  - block-parser の「インラインの解析に渡す内容」「行の記録」「定義の表」「ラベルの正規化」を使う。プレフィックスとインデントの規則、ラベルの正規化の手順を、この spec は自分で持たない。
  - syntax-tree の内部 API だけで木を作る。利用者は、インラインのノードとその属性を、syntax-tree のたどる API で読む。
  - unicode-tables の句読点の判定と空白の判定を、強調の区切りの判定に使う。実体名の参照を、文字参照の認識に使う。
  - 不正な UTF-8 を「置き換えて続ける」設定のとき、内容の中の不正なバイト列を、この spec が自分で U+FFFD として読む。置き換えた写しは作らない。
  - source-text は、この spec が定める範囲（テキスト、コードスパン、dest、title など）から、意味上の値を作る。この spec と source-text は、同じ範囲を読むが、互いに依存しない。
  - dialect-extension は、この spec が確保した箇所に、方言の規則の呼び出しを足す。この spec の時点では、設定の方言の項目は解析の結果に影響しない。
  - spec-conformance は、この spec の木と source-text から HTML を作り、spec.txt の全例と比べる。

## Requirements

### Requirement 1: 解析の入口への統合
**Objective:** As a 利用者, I want 解析の入口を 1 回呼ぶだけで、ブロックとインラインの両方を持つ木を受け取りたい, so that 段落や見出しの中身を自分で解析しなくて済む

#### Acceptance Criteria
1. When 解析の入口が呼ばれる, the 解析の入口 shall ブロックの解析に続けてインラインの解析を行い、成功したときに、ブロックとインラインの両方のノードを持つ文書を渡す
2. The インラインの解析 shall 段落と見出し（ATX と Setext）のすべてについて、その内容の範囲をインラインとして解析し、できたノードを、その段落または見出しの子にする
3. The インラインの解析 shall コードブロック、HTML ブロック、テーマの区切り、リンク参照定義のノードに、子を作らない
4. When 内容の範囲の長さが 0 である, the インラインの解析 shall その見出しに子を作らない
5. The インラインの解析 shall 内容の範囲の外のバイトを、インラインとして解釈しない
6. The インラインの解析 shall ブロックのノードの種類、範囲、属性、並びを変えない
7. The インラインの解析 shall どの内容の範囲も、その中身にかかわらずノードの並びにし、Markdown の構文を理由に失敗しない
8. The 解析の入口 shall 成功して返す文書の木を、syntax-tree の不変条件がすべて成り立つものにする
9. The インラインの解析 shall インラインのノードとその属性を、syntax-tree のたどる API でそのまま読めるものにする
10. The インラインの解析 shall 内容のバイト列を変更せず、複製しない

### Requirement 2: インラインのノードの範囲
**Objective:** As a 利用者, I want 各インラインのノードの範囲が、決まった規則で原文に対応してほしい, so that 範囲を使って原文を調べたり、一部だけを置き換えたりできる

#### Acceptance Criteria
1. The インラインの解析 shall インラインのノードの範囲を、その構造を作る最初のバイト（開く区切りを含む）から、最後のバイト（閉じる区切りを含む）の直後までとする
2. The インラインの解析 shall 段落または見出しの直接の子の範囲を、その内容の範囲の内側にし、原文の順に、重ならないように並べる
3. The インラインの解析 shall 内容の範囲のうち、行の内容にあたるすべてのバイトを、段落または見出しの直接の子のどれか 1 つの範囲に含める
4. The インラインの解析 shall 子を持つインラインのノード（強調、強い強調、リンク、画像）の子の範囲を、親の範囲の内側にし、親の区切りにあたるバイトを子の範囲に含めない
5. The インラインの解析 shall 複数の行にわたるインラインのノードの範囲に、途中の行末記号と、次の行のプレフィックスと先頭の空白を含める
6. The インラインの解析 shall テキスト、ハードな改行、ソフトな改行、バックスラッシュのエスケープ、文字参照、コードスパン、オートリンク、生の HTML のノードに、子を作らない
7. The インラインの解析 shall どの範囲も、UTF-8 の文字の途中と、行末記号の組（CR と LF）の途中で区切らない

### Requirement 3: テキスト
**Objective:** As a 利用者, I want ほかのどの構造にもならない部分が、テキストとして得られてほしい, so that 本文の文字の部分を、ほかの構造と区別して扱える

#### Acceptance Criteria
1. When 行の内容に、ほかのインラインの構造にならないバイトの並びがある, the インラインの解析 shall それをテキストのノードにする
2. The インラインの解析 shall 構造の一部にならなかった起動文字と区切り（対応する相手のない `*`、`_`、`` ` ``、`[`、`]`、`!`、`<`、`&`、`\` など）を、テキストにする
3. The インラインの解析 shall 同じ親の下で、同じ行の中で隣り合うテキストを、1 つのテキストのノードにまとめる
4. The インラインの解析 shall テキストのノードの範囲を、1 つの行の中に収め、行末記号と、次の行のプレフィックスを含めない
5. The インラインの解析 shall 行末記号の直前に連続する空白を、その行のテキストのノードの範囲に含めない
6. The インラインの解析 shall 長さ 0 のテキストのノードを作らない
7. The インラインの解析 shall テキストの中の U+0000 と、U+FFFD として扱う不正なバイト列を、ほかの文字と同じくテキストの範囲に含める

### Requirement 4: バックスラッシュのエスケープ
**Objective:** As a 利用者, I want バックスラッシュのエスケープが、ノードとして得られてほしい, so that エスケープされた文字と、構文として働く文字を区別できる

#### Acceptance Criteria
1. When バックスラッシュの直後に ASCII の句読点が続く, the インラインの解析 shall その 2 バイトを、バックスラッシュのエスケープのノードにする
2. The インラインの解析 shall エスケープされた文字を、インラインの構造の起動文字としても区切りとしても扱わない
3. If バックスラッシュの直後が、ASCII の句読点でも行末記号でもない, then the インラインの解析 shall そのバックスラッシュをテキストにする
4. If バックスラッシュが内容の範囲の最後のバイトである, then the インラインの解析 shall そのバックスラッシュをテキストにする
5. The インラインの解析 shall コードスパン、オートリンク、生の HTML の中のバックスラッシュを、エスケープとして扱わない
6. The インラインの解析 shall リンクと画像の dest と title の中のバックスラッシュのエスケープを、区切り（括弧と引用符）の対応の判定に使い、その部分にノードを作らない

### Requirement 5: 文字参照
**Objective:** As a 利用者, I want 実体名と数値の文字参照が、ノードとして得られてほしい, so that 参照の位置を、原文を読み直さずに知ることができる

#### Acceptance Criteria
1. When `&`、unicode-tables の実体名の参照で見つかる名前、`;` がこの順に並ぶ, the インラインの解析 shall `&` から `;` までを、文字参照のノードにする
2. When `&#`、1 から 7 桁の 10 進の数字、`;` がこの順に並ぶ, the インラインの解析 shall `&` から `;` までを、文字参照のノードにする
3. When `&#x` または `&#X`、1 から 6 桁の 16 進の数字、`;` がこの順に並ぶ, the インラインの解析 shall `&` から `;` までを、文字参照のノードにする
4. The インラインの解析 shall 数値の文字参照を、その値が有効なコードポイントでなくても（0、サロゲート、U+10FFFF より大きい値）、文字参照のノードにする
5. If `&` で始まる並びが、1 から 3 のどれにも合わない（`;` がない、名前が実体名の表にない、桁が多すぎる、など）, then the インラインの解析 shall その `&` をテキストにする
6. The インラインの解析 shall 文字参照が表す文字を、インラインの構造の起動文字、区切り、空白として扱わない
7. The インラインの解析 shall コードスパン、オートリンク、生の HTML の中の `&` を、文字参照として扱わない
8. The インラインの解析 shall リンクと画像の dest と title の中の文字参照に、ノードを作らない

### Requirement 6: コードスパン
**Objective:** As a 利用者, I want コードスパンが、仕様どおりの対応で得られてほしい, so that コードの部分を、ほかの構文として解釈せずに扱える

#### Acceptance Criteria
1. When バッククォートの列の後ろに、同じ長さのバッククォートの列がある, the インラインの解析 shall 開く列の最初から、その後ろで最初に現れる同じ長さの列の最後までを、コードスパンのノードにする
2. The インラインの解析 shall バッククォートの列の長さを、前後がバッククォートでない、連続するバッククォートの数として数える
3. If バッククォートの列の後ろに、同じ長さの列がない, then the インラインの解析 shall その列の全体をテキストにする
4. The インラインの解析 shall コードスパンの中身を、ほかのインラインの構造として解釈しない
5. The インラインの解析 shall 複数の行にわたるコードスパンを認識し、閉じる列を探すときに、行の内容だけを読む（次の行のプレフィックスの中のバッククォートを、列として数えない）
6. If バッククォートの列がバックスラッシュでエスケープされている, then the インラインの解析 shall エスケープされた 1 つを除いた残りのバッククォートを、列として扱う
7. The インラインの解析 shall コードスパンの中身の前後の空白の除去と、行末記号の空白への変換を行わない（範囲だけを定める）

### Requirement 7: 強調と強い強調
**Objective:** As a 利用者, I want 強調と強い強調が、仕様の 17 の規則どおりに得られてほしい, so that `*` と `_` の込み入った並びでも、参照実装と同じ構造になる

#### Acceptance Criteria
1. The インラインの解析 shall 区切りの列が左側か右側か（left-flanking、right-flanking）を、CommonMark 0.31.2 の定義（6.2 節）に従い、列の前後の文字が Unicode の空白か Unicode の句読点かで判定する。判定には unicode-tables の関数を使う。
2. The インラインの解析 shall 内容の範囲の先頭と末尾、および行末記号を、区切りの列の判定で空白として扱う
3. The インラインの解析 shall 区切りの列が強調を開けるか閉じられるかを、CommonMark 0.31.2 の規則 1 から 8 に従って決める。`_` については、語の中での制限を含む。
4. When 開ける区切りの列と、閉じられる同じ文字の区切りの列が、CommonMark 0.31.2 の規則に従って対応する, the インラインの解析 shall 対応する区切りと、その間の内容を、強調（区切り 1 つずつ）または強い強調（区切り 2 つずつ）のノードにし、間の内容をその子にする
5. If 開ける列と閉じる列の一方が、開けることも閉じることもできる列で、2 つの列の長さの和が 3 の倍数であり、両方の長さがともに 3 の倍数ではない, then the インラインの解析 shall その 2 つを対応させない（規則 9 と 10）
6. When 区切りの対応に複数の解釈がある, the インラインの解析 shall CommonMark 0.31.2 の規則 11 から 17 に従って 1 つに決める。強い強調を優先し、重なる場合は先に閉じるほうを、同じ位置で閉じる場合は短いほうを採る。
7. The インラインの解析 shall 強調と強い強調の範囲を、使った開く区切りの最初のバイトから、使った閉じる区切りの最後のバイトの直後までとする
8. When 区切りの列の一部だけが強調に使われる, the インラインの解析 shall 残りの区切りを、テキストにするか、別の強調の区切りとして使う
9. The インラインの解析 shall 強調と強い強調の入れ子を、深さによらず、同じ規則で扱う
10. The インラインの解析 shall 複数の行にわたる強調と強い強調を認識する
11. The インラインの解析 shall リンクのテキストの内側の区切りを、その外側の区切りと対応させない

### Requirement 8: インラインの形式のリンク
**Objective:** As a 利用者, I want インラインの形式のリンクが、dest と title の範囲とともに得られてほしい, so that リンク先と題を、原文を読み直さずに扱える

#### Acceptance Criteria
1. When リンクのテキスト（`[` と、対応する `]`）の直後に、CommonMark 0.31.2 の規則（6.3 節）に合う `(`、省略できる dest、省略できる title、`)` が続く, the インラインの解析 shall `[` から `)` までをリンクのノードにし、形式をインラインに設定し、リンクのテキストの中のインラインをその子にする
2. The インラインの解析 shall dest の範囲を設定する。山括弧で囲む書き方では山括弧の内側を、囲まない書き方ではその全体を範囲とする。
3. The インラインの解析 shall title の範囲を、引用符または丸括弧の内側として設定する
4. If dest または title が書かれていない, then the インラインの解析 shall それを「書かれていない」として設定する
5. When dest が `<>` である、または title の区切りの内側が空である, the インラインの解析 shall それを「書かれているが空である」として設定する
6. The インラインの解析 shall 山括弧で囲まない dest について、仕様の規則（空白と制御文字を含まない、丸括弧はエスケープされているか対応している）を適用し、丸括弧の対応を、入れ子が 32 段までの範囲で判定する。エスケープされていない開く丸括弧が 33 段目の入れ子になる並びは、dest として認めない（仕様が認める実装の上限で、参照実装と同じ値である）。
7. The インラインの解析 shall 複数の行にわたる title と、dest の前後と title の後の行末記号（それぞれ 1 つまで）を、仕様の規則に従って認識し、その途中で、行の内容だけを読む
8. If `[` と対応する `]` の後ろが、インラインの形式の規則に合わない, then the インラインの解析 shall 参照の形式（Requirement 9）として解釈できるかを確かめ、できなければ括弧をテキストにする
9. The インラインの解析 shall リンクのテキストの中の角括弧を、エスケープされているか、対応している場合に限って認める
10. The インラインの解析 shall リンクの中にリンクを作らない。リンクのテキストの中に別のリンクができるときは、内側をリンクにし、外側の括弧をテキストにする。

### Requirement 9: 参照の形式のリンクと参照の解決
**Objective:** As a 利用者, I want 参照の形式のリンクが、参照先の定義とともに得られてほしい, so that ラベルを自分で正規化して定義を探さなくて済む

#### Acceptance Criteria
1. When リンクのテキストの直後にリンクのラベル（`[label]`）が続き、そのラベルに一致する定義が定義の表にある, the インラインの解析 shall 最初の `[` から、ラベルの `]` までをリンクのノードにし、形式を完全参照に設定する
2. When リンクのテキストの直後に `[]` が続き、リンクのテキストをラベルとして一致する定義がある, the インラインの解析 shall 最初の `[` から `[]` の `]` までをリンクのノードにし、形式を省略参照に設定する
3. When リンクのテキストの後ろに `[]` もラベルも続かず、リンクのテキストをラベルとして一致する定義がある, the インラインの解析 shall `[` から `]` までをリンクのノードにし、形式をショートカットに設定する
4. The インラインの解析 shall 参照の形式のリンクのノードに、参照先のリンク参照定義のノードを設定し、dest と title の範囲を設定しない
5. The インラインの解析 shall ラベルの一致を、block-parser のラベルの正規化と定義の表で判定する。正規化したラベルが同じ定義が複数あるときは、原文で最初の定義を参照先にする。
6. The インラインの解析 shall 文書の中のどこにある定義も（リンクより後ろにある定義、別のコンテナの中の定義を含む）、参照先にできる
7. If 一致する定義がない, then the インラインの解析 shall リンクのノードを作らず、括弧をテキストにする。完全参照のラベルに一致する定義がないときは、そのラベルを、それ自身がリンクのテキストになれるものとして、解析を続ける。
8. If ラベルが 999 文字を超える、エスケープされていない角括弧を含む、または空白と行末記号でない文字を 1 つも含まない, then the インラインの解析 shall それをリンクのラベルとして扱わない
9. The インラインの解析 shall ラベルの一致を、ラベルに書かれたとおりの文字で判定し、ラベルの中のインラインの構造（強調、エスケープ、文字参照など）を解釈した結果では判定しない
10. When リンクのテキストの後ろが、インラインの形式にも、完全参照と省略参照にも解釈できる, the インラインの解析 shall CommonMark 0.31.2 の優先の順（インライン、完全参照と省略参照、ショートカット）に従う
11. The インラインの解析 shall リンクのテキストとラベルの間に、空白と行末記号を認めない
12. The インラインの解析 shall 複数の行にわたるラベルを認識し、その中のプレフィックスをラベルの内容として扱わない
13. The インラインの解析 shall 参照の形式のリンクでも、リンクのテキストの中のインラインを、そのノードの子にする

### Requirement 10: 画像
**Objective:** As a 利用者, I want 画像が、リンクと同じ形式と属性で得られてほしい, so that リンクと画像を、同じ方法で扱える

#### Acceptance Criteria
1. When `![` で始まり、その後ろがリンクと同じ規則（インライン、完全参照、省略参照、ショートカット）に合う, the インラインの解析 shall `!` から、その形式の最後のバイトまでを画像のノードにする
2. The インラインの解析 shall 画像のノードに、リンクと同じ決まり（Requirement 8 と 9）で、形式、dest と title の範囲、または参照先を設定する
3. The インラインの解析 shall 画像の説明（`![` と `]` の間）の中のインラインを、画像のノードの子にする
4. The インラインの解析 shall 画像の説明の中に、リンクと画像を作れるようにし、リンクのテキストの中に、画像を作れるようにする
5. If `![` の後ろが、どの形式の規則にも合わない, then the インラインの解析 shall その `!` と `[` をテキストにする
6. If `!` の直後が `[` でない, then the インラインの解析 shall その `!` をテキストにする
7. The インラインの解析 shall 画像の入れ子を、深さによらず、同じ規則で扱う

### Requirement 11: オートリンク
**Objective:** As a 利用者, I want 山括弧で囲んだ URI とメールアドレスが、オートリンクとして得られてほしい, so that 書かれたままのリンクを、種別とともに扱える

#### Acceptance Criteria
1. When `<`、CommonMark 0.31.2 の絶対 URI の規則（6.4 節。2 から 32 文字のスキーム、`:`、空白と `<` と `>` と制御文字を含まない並び）に合う並び、`>` がこの順に並ぶ, the インラインの解析 shall `<` から `>` までをオートリンクのノードにし、種別を URI に設定する
2. When `<`、CommonMark 0.31.2 のメールアドレスの規則（6.4 節）に合う並び、`>` がこの順に並ぶ, the インラインの解析 shall `<` から `>` までをオートリンクのノードにし、種別をメールアドレスに設定する
3. If `<` で始まる並びが、オートリンクにも生の HTML にも合わない, then the インラインの解析 shall その `<` をテキストにする
4. The インラインの解析 shall オートリンクを、1 つの行の中だけで認識する
5. The インラインの解析 shall オートリンクの中身を、ほかのインラインの構造として解釈しない

### Requirement 12: 生の HTML
**Objective:** As a 利用者, I want インラインの HTML のタグが、生の HTML として得られてほしい, so that HTML の部分を、Markdown として解釈せずに扱える

#### Acceptance Criteria
1. When CommonMark 0.31.2 の規則（6.6 節）に合う開始タグ、終了タグ、コメント、処理命令、宣言、CDATA セクションのどれかが現れる, the インラインの解析 shall その最初の `<` から最後の `>` までを、生の HTML のノードにする
2. The インラインの解析 shall コメントについて、0.31.2 の規則（`<!-->` と `<!--->` をコメントとする。そのほかは `<!--` から最初の `-->` まで）に従う
3. The インラインの解析 shall 複数の行にわたる生の HTML（属性の間、コメント、処理命令、宣言、CDATA セクションの中で改行するもの）を認識し、その途中で、行の内容だけを読む
4. The インラインの解析 shall 生の HTML の中身を、ほかのインラインの構造として解釈しない
5. If `<` で始まる並びが、6.6 節のどの規則にも合わない（閉じない、属性の書き方が合わない、など）, then the インラインの解析 shall それを生の HTML にしない
6. When `<` で始まる並びが、オートリンクと生の HTML の両方に解釈できる, the インラインの解析 shall オートリンクにする

### Requirement 13: ハードな改行とソフトな改行
**Objective:** As a 利用者, I want 内容の途中の行の境目が、2 種類の改行のノードとして得られてほしい, so that 意図された改行と、ただの折り返しを区別できる

#### Acceptance Criteria
1. When 内容の途中の行末記号の直前に、スペースが 2 つ以上続く, the インラインの解析 shall ハードな改行のノードを作る
2. When 内容の途中の行末記号の直前に、エスケープされていないバックスラッシュがある, the インラインの解析 shall ハードな改行のノードを作り、その範囲をバックスラッシュから行末記号の終わりまでとする
3. When 内容の途中の行末記号が、1 と 2 のどちらにも合わない, the インラインの解析 shall ソフトな改行のノードを作る
4. The インラインの解析 shall 1 と 3 の改行のノードの範囲を、行末記号の直前に連続する空白の最初のバイト（空白がなければ行末記号）から、行末記号の終わりまでとする
5. The インラインの解析 shall 改行のノードの範囲に、次の行のプレフィックスと先頭の空白を含めない
6. The インラインの解析 shall 改行のノードを、その行末記号を含む最も内側のノード（強調、強い強調、リンク、画像、または段落）の子にする
7. The インラインの解析 shall コードスパン、生の HTML、リンクと画像の title、完全参照のラベル（リンクのテキストに続く `[label]`）の中の行末記号について、改行のノードを作らない
8. The インラインの解析 shall 行末記号の種類（LF、CR、CR と LF の組）によらず、同じ規則で改行のノードを作る
9. The インラインの解析 shall 内容の範囲の末尾に、改行のノードを作らない（内容の範囲は行末の空白と行末記号を含まず、末尾のバックスラッシュはテキストになる）

### Requirement 14: 構造の優先の順
**Objective:** As a 利用者, I want 構造が重なるときに、仕様の定める優先の順で 1 つに決まってほしい, so that どの入力でも、参照実装と同じ木になる

#### Acceptance Criteria
1. The インラインの解析 shall コードスパン、オートリンク、生の HTML を、リンクの括弧と強調の区切りより強く結び付ける。これらの中の `]`、`*`、`_` を、括弧や区切りとして扱わない。
2. The インラインの解析 shall リンクと画像の括弧を、強調の区切りより強く結び付ける。強調がリンクの境をまたぐ解釈を採らない。
3. When コードスパン、オートリンク、生の HTML の起動文字が、内容の中で前から順に現れる, the インラインの解析 shall 先に始まるものを先に採る
4. The インラインの解析 shall バックスラッシュのエスケープを、コードスパン、オートリンク、生の HTML の外で、ほかのすべての構造より先に適用する

### Requirement 15: 行と文字の扱い
**Objective:** As a 利用者, I want コンテナの中の複数の行にわたる内容と、不正なバイト列を含む内容が、正しく解析されてほしい, so that 引用やリストの中の文章でも、範囲と構造が原文と一致する

#### Acceptance Criteria
1. The インラインの解析 shall 複数の行にわたる内容を、行の記録に従い、行の内容だけを順に読んで解析する
2. The インラインの解析 shall コンテナのプレフィックスと、段落の続きの行の先頭の空白の中のバイトを、起動文字、区切り、構造の中身のどれとしても解釈しない
3. The インラインの解析 shall 遅延継続行の内容を、印のある行の内容と同じ規則で解析する
4. While 不正な UTF-8 の扱いが「置き換えて続ける」である, the インラインの解析 shall 不正なバイト列の極大の部分 1 つを U+FFFD 1 文字として読み、強調の区切りの判定、ラベルの比較、ラベルの文字数の数え方に、その読み方を使う
5. The インラインの解析 shall U+0000 を、区切りの判定とラベルの比較で U+FFFD として扱う
6. While 不正な UTF-8 の扱いが「置き換えて続ける」である, the インラインの解析 shall すべての範囲を、利用者が渡した内容のオフセットで表し、置き換えた写しを作らない
7. When 解析する範囲が UTF-8 として正しい, the インラインの解析 shall 不正な UTF-8 の扱いのどちらの設定でも、同じ木を作る
8. The インラインの解析 shall ASCII の外の文字を、起動文字と構文の区切りとして扱わない。Unicode の空白と句読点は、強調の区切りの判定だけに使う。

### Requirement 16: 資源の上限と失敗の扱い
**Objective:** As a 利用者, I want インラインの解析でも、資源の上限と失敗の扱いがブロックと同じであってほしい, so that 信頼できない入力を、同じ設定で安全に扱える

#### Acceptance Criteria
1. If 入れ子の深さの上限が指定されていて、深さがそれを超えるインラインのノードが要る, then the 解析の入口 shall 資源の上限の超過を返す
2. When すべてのノード（ブロックとインライン）の深さが入れ子の深さの上限以下である, the 解析の入口 shall 上限を理由に失敗しない
3. If ノードの数の上限が指定されていて、解析の途中で作ったノードの数（ブロックとインラインを合わせ、途中で取り除いたものも数える）がそれを超える, then the 解析の入口 shall 資源の上限の超過を返す
4. While ノードの数の上限が指定されている, the 解析の入口 shall 成功して返す文書のノードの数（ブロックとインラインを合わせた数）を、上限以下にする
5. If 木が表せるノードの数を超える、または大きさの計算があふれる, then the 解析の入口 shall 資源の上限の超過を返す
6. If インラインの解析の途中で確保関数が失敗する, then the 解析の入口 shall メモリ不足を返す
7. If インラインの解析が失敗する, then the 解析の入口 shall その解析のために確保したメモリ（ブロックの解析の結果を含む）をすべて解放してから戻り、文書を渡さない
8. The インラインの解析 shall 解析に必要なメモリを、設定の確保関数だけから得る
9. When 解析が成功する, the 解析の入口 shall インラインの解析の途中だけで使う作業用のメモリを解放してから戻る
10. The インラインの解析 shall 失敗を戻り値で伝え、`abort`、`exit`、`longjmp` を使わない

### Requirement 17: 方言の規則を呼ぶ箇所
**Objective:** As a 下流の開発者, I want インラインの解析に、方言の規則を足せる箇所があってほしい, so that dialect-extension が、解析の規則を書き換えずに、方言のインラインを足せる

#### Acceptance Criteria
1. The インラインの解析 shall 起動文字からインラインの構造の解析を始める箇所を 1 か所にまとめ、方言の起動文字とその規則の呼び出しを足せるようにする
2. The インラインの解析 shall 区切りの種類（文字と、対応したときに作るノードの種類）を足せるようにし、方言の区切りを、`*` と `_` と同じ流れ（列を記録する、対応を探す、間の内容を包む）で扱えるようにする
3. The インラインの解析 shall 方言の種類のインラインのノードを、CommonMark の種類のノードと同じ流れで木に加えられるようにする
4. While 方言が指定されていない, the インラインの解析 shall CommonMark 0.31.2 の規則だけで解析する
5. The インラインの解析 shall この spec の時点では、設定の方言の項目の値によって、解析の結果を変えない
6. The インラインの解析 shall 方言を定義して登録する公開 API を持たない

### Requirement 18: 解析に共通の性質
**Objective:** As a 利用者, I want インラインの解析が、どの入力と設定でも、製品が保証する性質を保ってほしい, so that 信頼できない入力や、並行する処理でも安心して使える

#### Acceptance Criteria
1. The 解析の入口 shall インラインの解析を含めた解析の時間を、内容の長さにほぼ比例させる。次の入力でも同じである。多数の対応しない区切りの列。開く区切りと閉じる区切りが多数あって対応が決まりにくい並び。深く入れ子になった強調。深く入れ子になった角括弧と、多数の閉じない角括弧。リンクの dest の中の深く入れ子になった丸括弧。多数の閉じないインラインの形式のリンク（`[a](` の繰り返しなど）。長さの異なる多数の閉じないバッククォートの列。多数の閉じない `<`、コメント、処理命令、宣言、CDATA セクションの開始。多数の `&` と、多数のバックスラッシュ。多数の、定義のない参照と長いラベル。
2. The 解析の入口 shall 解析に使うメモリを、内容の長さにほぼ比例する量に抑える
3. The インラインの解析 shall 再帰を使わず、インラインの入れ子の深さによらず、呼び出しのスタックを一定の量しか使わない
4. The インラインの解析 shall グローバルな変数と静的な可変の状態を持たず、I/O を行わない
5. When 同じ内容と同じ設定が渡される, the 解析の入口 shall 常に同じ木（同じノードの ID、種類、範囲、属性）を作る
6. While 複数のスレッドが、それぞれ別の文書を解析している, the 解析の入口 shall 互いに影響せずに正しい結果を返す
7. The インラインの解析 shall 公開ヘッダに現れず、動的ライブラリの公開シンボルを増やさない

### Requirement 19: 単体テスト
**Objective:** As a Amark の開発者, I want インラインの解析の正しさを、この spec のテストだけで確かめたい, so that 下流の spec が、インラインの構造を信頼して進められる

#### Acceptance Criteria
1. The 単体テスト shall spec.txt（CommonMark 0.31.2）の次の節の例について、インラインの構造（種類、入れ子、属性）が、仕様の期待する結果と一致することを確かめる。Inlines、Code spans、Emphasis and strong emphasis、Links、Images、Autolinks、Raw HTML、Hard line breaks、Soft line breaks、Textual content、Backslash escapes、Entity and numeric character references。エスケープと文字参照を文字に戻した値と、URL の正規化に依存する部分は確かめない。
2. The 単体テスト shall 各種類のインラインのノードについて、ノードと属性の範囲と行番号が、Requirement 2 と各種類の決まりどおりであることを確かめる。3 種類の行末記号、複数の行にわたる構造、コンテナ（ブロッククォートとリスト項目）の中の内容、遅延継続行を含む。
3. The 単体テスト shall 参照の解決（4 つの形式、重なるラベル、後ろにある定義、コンテナの中の定義、一致しないラベル、999 文字の境、case folding）を確かめる
4. The 単体テスト shall 不正な UTF-8 の扱いの 2 つの設定と U+0000 について、区切りの判定と範囲を確かめる
5. The 単体テスト shall 資源の上限（入れ子の深さとノードの数）について、インラインのノードでの境の値を確かめる
6. The 単体テスト shall テストで作ったすべての文書が、syntax-tree の不変条件の検査を通ることを確かめる
7. When 単体テストが、確保と解放を数える確保関数を使い、確保の失敗を各回に注入して解析を実行する, the 解析の入口 shall 成功した場合は文書の解放の後に、失敗した場合は戻った時点で、解放されないメモリを残さない
8. The 単体テスト shall 入れ子が 10 万段の強調と、10 万段の角括弧（画像の入れ子を含む）について、解析と文書の解放が、スタックを使い切らずに終わることを確かめる
9. The 単体テスト shall Requirement 18 の 1 に挙げた入力のそれぞれについて、入力を大きくしても、解析が、長さにほぼ比例する時間で終わることを確かめる
10. The 単体テスト shall 公開 API だけを使うテストで、解析の入口から得た文書のインラインのノードと属性を、たどる API で読めることを確かめる
11. The 単体テスト shall インラインのノードが加わった後も、block-parser の単体テストが確かめるブロックの構造が変わらないことを確かめる
