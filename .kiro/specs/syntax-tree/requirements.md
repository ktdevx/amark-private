# Requirements Document

## Introduction
syntax-tree は、amark の解析結果を表す構文木のデータモデルを作る。Markdown を扱うソフトは、原文の位置を保ったまま構文の構造を知りたい。既存の実装（cmark など）は原文を複製したノードを作るので、元の位置と行末記号が失われやすく、原文の一部を置き換えるような用途に使いにくい。amark の構文木は、原文を複製せず、ノードごとに原文の範囲（バイトのオフセット）と行番号だけを持つ。

この spec は、次の 4 つを用意する。

1. **データモデル**：ブロックとインラインのノードの種類、範囲と行、種類ごとの属性、木の不変条件。
2. **読み出しの公開 API**：木を読み取り専用でたどる関数、診断を読む関数、文書を解放する関数。
3. **公開する型**：解析の設定、エラーの種類、診断と、設定を検査する関数。
4. **内部 API**：解析器と方言が木を作る関数と、不変条件を検査する関数。

この文書で「利用者」は amark を自分のプロジェクトに組み込む人、「解析器の開発者」は block-parser、inline-parser、dialect-extension などこの木を作る側の spec を開発する人を指す。「内容」は利用者が渡す入力のバイト列の全体、「解析する範囲」はそのうち設定で指定した `[start, end)` を指す。「文書」は、1 回の解析の結果（木と診断）をまとめて持つものを指す。

## Boundary Context
- **In scope**:
  - ノードの種類（CommonMark 0.31.2 の全要素）と、方言が定める種類のための ID の空間
  - ノードの範囲と行番号、種類ごとの属性
  - 木の不変条件と、それを検査する関数
  - 木を読み取り専用でたどる公開 API、診断を読む公開 API、文書を解放する公開 API
  - 解析の設定・エラーの種類・診断の公開型と、設定を検査する関数
  - 木を作り、診断を足す内部 API
  - 上の各項目の単体テスト
- **Out of scope**:
  - 解析の規則と、解析の入口となる公開 API（block-parser、inline-parser）。この spec だけでは、利用者は Markdown から木を得られない。
  - 設定の適用（範囲の切り出し、UTF-8 の検査と置換、資源の上限の検査）（block-parser）
  - 範囲から文字列を組み立てること、dest・title・info の意味上の値を得ること（source-text）
  - 方言を定義して規則を登録する公開 API、規則が返した結果を採用するかどうかの判断（dialect-extension）
  - 木を作る・書き換える公開 API（今回の木は読み取り専用である）
  - HTML などへの出力、Markdown の書き出し、用途に固有の処理（翻訳の単位への分割など）
- **Adjacent expectations**:
  - project-foundation の内部の部品（確保関数の抽象、アリーナ、可変長の配列、行の索引）を使う。行番号と行末の定義は、行の索引に合わせる。
  - block-parser と inline-parser は、この spec の内部 API だけで木を作る。どの構文にどの種類と属性を付けるかは、それぞれの解析器が決める。
  - block-parser は、解析の入口でこの spec の「設定を検査する関数」を呼び、検査を通った設定を適用する。「不正な UTF-8 を置き換えて続ける」設定のときに、ノードの範囲が指すバイト列をどれにするか（元の内容か、置き換えた結果か）は、block-parser が決める。
  - dialect-extension は、方言の種類の ID と属性の内容を定め、規則が返した結果をこの spec の「不変条件を検査する関数」で確かめる。この spec は、ID の空間と、方言の属性を木に載せて読み出す手段だけを用意する。
  - source-text は、この spec の属性が返す範囲（dest、title、info など）から意味上の値を作る。
  - 後の段階の候補（markdown-writer、source-edit）を、データモデルを作り直さずに足せるかどうかは、設計の段階で確かめる。

## Requirements

### Requirement 1: ノードの種類
**Objective:** As a 利用者, I want どのノードが何の構文を表すかを種類で見分けたい, so that CommonMark の全要素と方言の要素を、同じ方法で扱える

#### Acceptance Criteria
1. The 構文木 shall すべてのノードに、種類を 1 つだけ持たせる
2. The 構文木 shall CommonMark 0.31.2 のブロックを表す種類として、次のものを持つ。文書、ブロッククォート、リスト、リスト項目、テーマの区切り、見出し、コードブロック、HTML ブロック、段落、リンク参照定義。
3. The 構文木 shall CommonMark 0.31.2 のインラインを表す種類として、次のものを持つ。テキスト、コードスパン、強調、強い強調、リンク、画像、オートリンク、生の HTML、ハードな改行、ソフトな改行、バックスラッシュのエスケープ、文字参照。
4. The 構文木 shall 見出しの 2 つの書き方（ATX と Setext）と、コードブロックの 2 つの書き方（インデントとフェンス）を、種類ではなく属性で区別する
5. The 構文木 shall 空行をノードにしない
6. The 構文木 shall 方言が定める種類を、CommonMark の種類と重ならない ID で表せるようにする
7. When 種類の ID が渡される, the 構文木 shall それが CommonMark の種類か方言の種類かを答える
8. When ノードが渡される, the 構文木 shall そのノードがブロックかインラインかを、方言の種類のノードについても答える
9. The 構文木 shall CommonMark の種類の ID の値を、ライブラリの版が変わっても変えない

### Requirement 2: 範囲と行番号
**Objective:** As a 利用者, I want 各ノードが原文のどこにあるかを知りたい, so that 原文を調べたり、一部だけを置き換えたりできる

#### Acceptance Criteria
1. The 構文木 shall すべてのノードに、原文の範囲を、開始と終了のバイトのオフセットの組 `[start, end)` として持たせる
2. The 構文木 shall オフセットを、解析する範囲の先頭からではなく、内容の先頭から数える
3. The 構文木 shall 長さ 0 の範囲（開始と終了が等しい）を持つノードを表せるようにする
4. The 構文木 shall すべてのノードに、開始行と終了行の番号を持たせる。行は内容の最初の行を 1 として数え、行末は CommonMark の定義（LF、後ろに LF が続かない CR、CR と LF の組）で区切る。
5. The 構文木 shall 開始行を、範囲の開始のオフセットを含む行とする
6. The 構文木 shall 終了行を、範囲の最後のバイトを含む行とする。範囲の長さが 0 のときは、開始行と同じとする。
7. The 構文木 shall 文書のノードの範囲を、解析する範囲と同じにする
8. The 構文木 shall ノードにも属性にも原文のバイトの複製を持たせず、原文の中の位置はすべて範囲で表す
9. The 構文木 shall 内容のバイト列を変更しない

### Requirement 3: 種類ごとの属性
**Objective:** As a 利用者, I want 種類に固有の情報（見出しのレベルなど）を原文を読み直さずに知りたい, so that 構文の細部を自分で解析し直さなくて済む

#### Acceptance Criteria
1. The 構文木 shall 見出しのノードに、レベル（1 から 6）と、書き方（ATX か Setext か）を持たせる
2. The 構文木 shall リストのノードに、箇条書きか番号付きか、およびタイトかルーズかを持たせる
3. Where リストが箇条書きである, the 構文木 shall リストのノードに、記号の文字（`-`、`+`、`*` のどれか）を持たせる
4. Where リストが番号付きである, the 構文木 shall リストのノードに、開始番号と、区切りの文字（`.` か `)` か）を持たせる
5. The 構文木 shall コードブロックのノードに、書き方（インデントかフェンスか）を持たせる
6. Where コードブロックがフェンスである, the 構文木 shall コードブロックのノードに、フェンスの文字（`` ` `` か `~` か）、開始のフェンスの長さ、info の範囲を持たせる
7. The 構文木 shall リンクと画像のノードに、形式（インライン、完全参照、省略参照、ショートカットのどれか）を持たせる
8. Where リンクまたは画像がインラインの形式である, the 構文木 shall そのノードに、dest の範囲と title の範囲を持たせる
9. Where リンクまたは画像が参照の形式（完全参照、省略参照、ショートカット）である, the 構文木 shall そのノードに、参照先のリンク参照定義のノードを持たせる
10. The 構文木 shall リンク参照定義のノードに、ラベルの範囲、dest の範囲、title の範囲を持たせる
11. The 構文木 shall オートリンクのノードに、URI かメールアドレスかを持たせる
12. The 構文木 shall 省略できる部分（title、info、インラインの形式の dest）について、「書かれていない」ことと「書かれているが空である」ことを区別して表す
13. The 構文木 shall 属性が持つ範囲を、ノードの範囲と同じく、内容の先頭から数えたバイトのオフセットで表す
14. Where ノードが方言の種類である, the 構文木 shall そのノードに、方言が定める属性の値を載せられるようにする

### Requirement 4: 木をたどる公開 API
**Objective:** As a 利用者, I want 木を読み取り専用でたどり、各ノードの情報を取り出したい, so that 検査、索引、独自の出力などを木の上に作れる

#### Acceptance Criteria
1. When 文書が渡される, the たどる API shall 木の根（文書のノード）を返す
2. When ノードが渡される, the たどる API shall その親、最初の子、次の兄弟を、それぞれ返す
3. If 求めたノードがない（根の親、子のないノードの最初の子、最後の兄弟の次）, then the たどる API shall 「ノードがない」ことを、どのノードとも区別できる値で返す
4. When ノードが渡される, the たどる API shall その種類、範囲、開始行、終了行を返す
5. When ノードが渡される, the たどる API shall その種類の属性（Requirement 3 のもの）を返す
6. If ノードの種類と合わない属性が求められる, then the たどる API shall 属性がないことを呼び出した側が判別できる形で伝え、未定義の動作を起こさない
7. When 方言の種類のノードが渡される, the たどる API shall 種類の ID と、そのノードに載っている方言の属性の値を返す
8. The たどる API shall 兄弟を原文の順に返す
9. The たどる API shall 親・最初の子・次の兄弟だけを使って、利用者が再帰もスタックも使わずに木の全体を文書の順に走査できるようにする
10. The たどる API shall 親・最初の子・次の兄弟・種類・範囲・行を、木の大きさによらない時間で返す
11. The たどる API shall 文書を変更しない
12. While 複数のスレッドが同じ文書を読んでいる, the たどる API shall どのスレッドにも正しい結果を返す
13. The 公開 API shall ノードを作る・取り除く・書き換える手段を利用者に提供しない
14. The たどる API shall 返したノードと範囲を、その文書が解放されるまで有効に保つ

### Requirement 5: 文書の解放
**Objective:** As a 利用者, I want 使い終わった文書を 1 回の呼び出しで解放したい, so that ノードを個別に管理しなくて済む

#### Acceptance Criteria
1. When 文書の解放が要求される, the 文書 shall その文書のために確保したメモリ（ノード、属性、診断を含む）をすべて解放する
2. The 文書 shall 解放を、その文書を作るときに使われた確保関数で行う
3. When 「文書がない」ことを表す値で解放が要求される, the 文書 shall 何もしない
4. The 文書 shall 解放を、再帰を使わずに行う
5. The 文書 shall 解放のときに内容のバイト列を変更も解放もしない
6. While 複数のスレッドが、それぞれ別の文書を使っている, the 文書 shall 互いに影響せずに正しく動作する

### Requirement 6: 木の不変条件とその検査
**Objective:** As a 解析器の開発者, I want 木が壊れていないことを 1 つの関数で確かめたい, so that 解析器と方言の誤りを、テストとデバッグで早く見つけられる

#### Acceptance Criteria
1. The 不変条件の検査 shall 次の「構造の条件」を確かめる。根が 1 つだけあり、その種類が文書で、親も兄弟も持たないこと。根以外のすべてのノードが、根から親子と兄弟の関係をたどって 1 回だけ現れること。あるノードの子の親が、そのノードであること。
2. The 不変条件の検査 shall 次の「範囲の条件」を確かめる。すべてのノードの範囲が、開始が終了以下で、内容の中にあること。子の範囲が親の範囲の内側にあること。兄弟が重ならず、原文の順に並ぶこと（前の兄弟の終了が、次の兄弟の開始以下である）。
3. The 不変条件の検査 shall すべてのノードの開始行と終了行が、Requirement 2 の定義どおりに範囲と対応していることを確かめる
4. The 不変条件の検査 shall 次の「入れ子の条件」を確かめる。文書の子がブロックであること。インラインのノードの子がインラインであること。
5. The 不変条件の検査 shall 次の「属性の条件」を確かめる。見出しのレベルが 1 から 6（Setext では 1 か 2）であること。属性が持つ範囲が内容の中にあること。インラインの形式のリンクと画像の dest と title、フェンスのコードブロックの info、リンク参照定義のラベル・dest・title の範囲が、そのノードの範囲の内側にあること。参照の形式のリンクと画像の参照先が、同じ文書のリンク参照定義のノードであること。
6. When すべての不変条件が成り立つ木が渡される, the 不変条件の検査 shall 成り立つと報告する
7. If 不変条件が成り立たない, then the 不変条件の検査 shall 成り立たないと報告し、最初に見つけた違反について、違反した条件の種類と、違反したノードを返す
8. When 木の一部（あるノードとその子孫）が指定される, the 不変条件の検査 shall その部分だけを検査する
9. The 不変条件の検査 shall 木を変更せず、メモリを確保せず、再帰を使わない
10. The 不変条件の検査 shall 検査の時間を、検査するノードの数にほぼ比例させる
11. The 不変条件の検査 shall 不変条件が成り立たない木が渡されても、範囲の外のメモリを読まず、必ず終了する
12. The 不変条件の検査 shall 公開ヘッダに現れず、ライブラリの内部とテストからだけ呼べる

### Requirement 7: 木を作る内部 API
**Objective:** As a 解析器の開発者, I want 決まった内部 API だけで木を組み立てたい, so that 木の表し方を知らなくても、不変条件を保った木を作れる

#### Acceptance Criteria
1. When 確保関数、内容（バイト列とその長さ）、解析する範囲、ファイル名（省略できる）が渡される, the 木を作る API shall 根（文書のノード）だけを持つ文書を作る
2. When 親、種類、範囲が渡される, the 木を作る API shall その種類と範囲のノードを作り、親の最後の子として足す
3. The 木を作る API shall ノードの開始行と終了行を、呼び出した側の指定に頼らず、範囲から Requirement 2 の定義どおりに定める
4. The 木を作る API shall 作ったノードに、その種類の属性（Requirement 3 のもの）を設定できるようにする
5. The 木を作る API shall 解析の途中で必要になる次の変更を行えるようにする。ノードの範囲を変える。ノードの種類を変える。ノードを木から取り除く。連続する兄弟を、新しいノードの子として包む。
6. The 木を作る API shall 方言の種類の ID を持つノードを、CommonMark の種類のノードと同じ方法で作れるようにし、ブロックかインラインかの別と、方言の属性の値を設定できるようにする
7. The 木を作る API shall 文書に必要なメモリを、文書を作るときに渡された確保関数だけから得る
8. If 確保が失敗する, then the 木を作る API shall メモリ不足を戻り値で伝え、文書を、解放の API で安全に解放できる状態に保つ
9. If ノードの数が、木が表せる上限を超える, then the 木を作る API shall 資源の上限の超過を戻り値で伝え、ノードを足さない
10. When 解析が失敗して、作りかけの文書の解放が要求される, the 文書 shall 確保したメモリをすべて解放し、解放されないメモリを残さない
11. The 木を作る API shall 作っている途中の木を、不変条件の検査（Requirement 6）に渡せる状態に保つ
12. The 木を作る API shall 公開ヘッダに現れず、動的ライブラリの公開シンボルに含まれない
13. The 木を作る API shall 再帰を使わない

### Requirement 8: 解析の設定
**Objective:** As a 利用者, I want 解析の対象と資源の扱いを 1 つの設定で指定したい, so that 既定の動作のままでも、必要な項目だけを変えても使える

#### Acceptance Criteria
1. The 解析の設定 shall 次の項目を持つ。方言、解析する範囲 `[start, end)`、確保関数、ファイル名、不正な UTF-8 の扱い、資源の上限（入力の大きさ、入れ子の深さ、ノードの数）。
2. The 解析の設定 shall 構文の規則を変える項目（タブ幅、ラベルの上限など）を持たない
3. When 利用者が既定の設定を求める, the 解析の設定 shall 次の値を返す。方言なし（CommonMark だけ）、内容の全体、標準の `malloc` と `free`、不正な UTF-8 はエラー、資源の上限なし。
4. The 解析の設定 shall 解析する範囲について、「内容の全体」を、内容の長さを知らなくても指定できるようにする
5. The 解析の設定 shall 不正な UTF-8 の扱いとして、「エラーにする」と「U+FFFD に置き換えて続ける」の 2 つを選べるようにする
6. The 解析の設定 shall 資源の上限の 3 つの項目（入力の大きさ、入れ子の深さ、ノードの数）のそれぞれについて、「上限なし」と具体的な上限の値を指定できるようにする
7. The 解析の設定 shall ファイル名を省略できるようにする
8. The 解析の設定 shall 確保関数を、確保の関数、解放の関数、両方にそのまま渡される利用者の値の組として指定できるようにする
9. The 解析の設定 shall 方言の項目について、「方言なし」を表せるようにする。方言の中身は dialect-extension が定める。

### Requirement 9: 設定の検査
**Objective:** As a 利用者, I want 設定の誤りを解析の前に知りたい, so that 誤った設定のまま解析して、分かりにくい失敗をすることがない

#### Acceptance Criteria
1. When 設定と内容の長さが渡される, the 設定の検査 shall 設定が正しいかどうかを判定し、正しければ成功を返す
2. When 既定の設定が、任意の内容の長さとともに渡される, the 設定の検査 shall 成功を返す
3. If 確保関数の、確保の関数と解放の関数の片方だけが指定されている, then the 設定の検査 shall 設定の誤りを返す
4. If 解析する範囲の開始が終了より大きい, then the 設定の検査 shall 設定の誤りを返す
5. If 解析する範囲の終了が内容の長さより大きい, then the 設定の検査 shall 設定の誤りを返す
6. When 解析する範囲の開始と終了が等しい, the 設定の検査 shall 成功を返す（空の範囲は正しい設定である）
7. If 不正な UTF-8 の扱いに、定義されていない値が指定されている, then the 設定の検査 shall 設定の誤りを返す
8. The 設定の検査 shall 内容が資源の上限を超えるかどうかを判定しない（上限の検査は解析のときに行う）
9. The 設定の検査 shall メモリを確保せず、設定を変更せず、同じ設定と長さに対して常に同じ結果を返す
10. The 設定の検査 shall 利用者が解析の前に自分で呼べる公開の関数とする

### Requirement 10: エラーの種類
**Objective:** As a 利用者, I want 失敗の原因を種類で見分けたい, so that 原因ごとに適切な対処（入力を直す、設定を直す、上限を上げる、など）を選べる

#### Acceptance Criteria
1. The エラーの種類 shall 成功と、次の 4 つの失敗を、互いに区別できる値で表す。入力の制約違反、設定の誤り、資源の上限の超過、メモリ不足。
2. The エラーの種類 shall 上の 4 つ以外に、Markdown の構文の誤りを表す値を持たない
3. The エラーの種類 shall 各値を、ライブラリの版が変わっても変えない
4. The 公開 API shall 失敗を、戻り値のエラーの種類で伝え、`abort`、`exit`、`longjmp` を使わない

### Requirement 11: 診断
**Objective:** As a 利用者, I want 解析は続いたが注意が要る事柄（方言の規則の不正な結果など）を、位置とともに知りたい, so that 原因の場所を特定して直せる

#### Acceptance Criteria
1. The 診断 shall 1 件ごとに、次の項目を持つ。位置（内容の先頭から数えたバイトのオフセットと、行番号）、重大度、メッセージ、ファイル名。
2. The 診断 shall 重大度として、少なくとも「警告」と「エラー」を区別する
3. The 診断 shall メッセージを、NUL で終わる文字列として返す
4. Where 設定でファイル名が指定されている, the 診断 shall そのファイル名を返す
5. If 設定でファイル名が指定されていない, then the 診断 shall ファイル名が「ない」ことを判別できる形で返す
6. The 文書 shall 0 件以上の診断を、足された順に持つ
7. When 文書が渡される, the 診断を読む API shall 診断の件数を返し、番号を指定して各診断を返す
8. If 件数以上の番号が指定される, then the 診断を読む API shall 診断がないことを判別できる形で伝え、未定義の動作を起こさない
9. The 診断を読む API shall 返したメッセージとファイル名を、その文書が解放されるまで有効に保つ。利用者が設定に渡したファイル名の文字列を、解析の後で解放しても変わらない。
10. When 位置、重大度、メッセージが渡される, the 診断を足す内部 API shall その診断を文書の最後に足し、行番号を位置から定める
11. If 診断のための確保が失敗する, then the 診断を足す内部 API shall メモリ不足を戻り値で伝え、すでにある診断と木を変えない
12. The 診断を足す内部 API shall 公開ヘッダに現れない

### Requirement 12: 公開 API と実装に共通の性質
**Objective:** As a 利用者, I want 公開 API がどの対象の環境でも同じ決まりで使えてほしい, so that 製品が保証する性質（状態を持たない、失敗が局所的、ABI の安定）に頼れる

#### Acceptance Criteria
1. The 公開 API shall 文書とノードを、中身の見えないハンドルとして扱い、木と文書の構造体のレイアウトを公開ヘッダに含めない
2. The 公開ヘッダ shall C99 として、対象のすべてのコンパイラ（MSVC、MinGW、GCC、Clang）で警告なしに取り込め、C++ からも取り込める
3. The 公開ヘッダ shall それだけで取り込め、内部ヘッダを取り込まない
4. The 公開 API shall 関数と型の名前を `amark_` で、マクロと列挙の定数の名前を `AMARK_` で始める
5. Where 動的ライブラリを作る構成である, the ビルド構成 shall この spec が公開する関数だけを公開シンボルに加え、公開シンボルの一覧をそれに合わせる
6. The 構文木の実装 shall グローバルな変数と静的な可変の状態を持たず、I/O を行わない
7. The 構文木の実装 shall 同じ順序の同じ操作に対して、常に同じ木を作る
8. The 構文木の実装 shall 解析の規則に関する知識を持たず、解析器と方言のモジュールに依存しない
9. The 単体テスト shall 次のことを確かめる。すべての種類と属性の設定と読み出し。たどる API による再帰なしの全体の走査。不変条件の各条件について、成り立つ木と、その条件だけを破った木。設定の検査の各条件。診断の追加と読み出し。
10. When 単体テストが、確保と解放を数える確保関数を使い、確保の失敗を各回に注入して実行される, the 構文木の実装 shall 成功した場合も失敗した場合も、文書の解放の後に解放されないメモリを残さない
11. The 単体テスト shall 深さが 10 万段の木について、走査、不変条件の検査、解放が、スタックを使い切らずに終わることを確かめる
