# Requirements Document

## Project Description (Input)
**誰が困っているか**：amark で GFM の表・取り消し線・タスクリスト・脚注などの方言を扱いたい解析器の開発者（後の段階の GFM の spec を書く人）と、方言を使う利用者。

**現状**：block-parser と inline-parser は、方言の規則を差し込む位置を設計の段階で確保しているが、公開 API としては仕上がっていない。方言を足すには本体のコードを変える必要がある。また、方言の規則が不正な結果（範囲が親の外にある、兄弟と重なる、原文の順でない、など）を返すと、木の不変条件が壊れる。

**何を変えるか**：
- 方言（拡張の集合）を表す公開 API を作る。方言は、規則の関数ポインタと規則が使うデータをまとめた const な構造体の集合とし、規則は次の差し込み口に登録する。
  - ブロック：新しいブロックの開始、継続の判定、閉じるときの処理（段落を表に変える、など）
  - インライン：起動文字と、区切りの種類（取り消し線の `~` など）
  - 後処理：木ができた後に、ノードを加えたり種類を変えたりする（タスクリストの印など）
- 方言は、独自のノードの種類と属性を登録できる。
- 規則が返した結果を本体が syntax-tree の不変条件の検査で確かめる。不正なら、その結果を採用せずに診断を出し、木を壊さず、解析はそのまま続ける。
- 方言は状態を持たないか、文書ごとの状態だけを持つ。同じ方言を、並行する別々の解析で使える。
- テスト用の小さな方言で、各差し込み口と検査が動くことを確かめる。

**範囲外**：GFM の各拡張の実装（後の段階で別の spec にする）、規則を設定で変えること（タブ幅などは変えられない）、CommonMark の規則そのもの（block-parser、inline-parser）。

**制約**：方言を使わないとき（CommonMark だけのとき）、結果と性能に影響しない。再帰を使わず、時間がほぼ線形であることを方言の側でも損なわない。

**関係する spec**：上流は block-parser、inline-parser、syntax-tree。下流は後の段階の GFM の spec（表、取り消し線、タスクリスト、脚注、拡張オートリンク）。

## Introduction
dialect-extension は、amark に方言の拡張点を作る。方言は、CommonMark にない構文（GFM の表、取り消し線、タスクリスト、脚注など）を足すための、拡張の集合である。block-parser と inline-parser は、方言の規則を呼ぶ箇所を確保しているが、いまは規則を登録する手段がなく、設定の方言の項目は結果に影響しない。

この spec は、次の 4 つを用意する。

1. **方言を定義する公開 API**：拡張の集合、各拡張の規則、独自のノードの種類と属性を、利用者のコードで定義し、解析の設定に指定する手段。
2. **差し込み口の契約**：ブロック（開始、継続、閉じるとき）、インライン（起動文字、区切りの種類）、後処理のそれぞれで、規則がいつ呼ばれ、何を受け取り、何を返せるか。
3. **結果の検査と診断**：規則が返した結果を本体が確かめ、不正なら採用せずに診断を出して、解析を続ける仕組み。
4. **テスト用の方言**：各差し込み口と検査が動くことを確かめる、テスト専用の小さな方言。

この文書で「利用者」は amark を自分のプロジェクトに組み込む人、「方言の作者」は方言を定義する人（利用者と、後の段階の GFM の spec の開発者）を指す。「方言」は、解析の設定に 1 つ指定する、拡張の集合を指す。「拡張」は、方言を構成する 1 つの単位で、名前、独自のノードの種類、規則を持つ。「規則」は、拡張が差し込み口に登録する関数を指す。「本体」は、amark のうち方言でない部分（解析器と構文木）を指す。「結果」は、規則が 1 回の呼び出しで本体に返すものを指す。「内容」「解析する範囲」「文書」「行末記号」「プレフィックス」「深さ」は、block-parser の requirements.md と同じ意味で使う。「内容の範囲」は、inline-parser の requirements.md と同じ意味で使う。「不変条件」は、syntax-tree の Requirement 6 の条件を指す。

## Boundary Context
- **In scope**:
  - 方言と拡張を定義し、解析の設定に指定する公開 API
  - 独自のノードの種類（ID、ブロックかインラインかの別）と属性の登録
  - 方言の定義の検査（設定の検査の一部として行う）
  - ブロックの差し込み口（開始、継続、閉じるとき）の契約と、規則の呼び出し
  - インラインの差し込み口（起動文字、区切りの種類）の契約と、規則の呼び出し
  - 後処理の差し込み口の契約と、規則の呼び出し
  - 結果の検査、不正な結果を採用しないこと、その診断
  - 文書ごとの状態を方言が持つ手段
  - テスト用の方言と、上の各項目の単体テスト
- **Out of scope**:
  - GFM の各拡張（表、取り消し線、タスクリスト、脚注、拡張オートリンク）の実装。後の段階の別の spec にする。ライブラリは、この spec の時点では、組み込みの方言を 1 つも持たない。
  - CommonMark の規則を設定で変えること。方言は構文を足すもので、タブ幅やラベルの上限などの規則を変える手段を持たない。
  - CommonMark の規則そのもの（block-parser、inline-parser）
  - 木を自由に作る・書き換える公開 API。規則は、結果を返すことと、後処理の決まった操作を求めることだけができる。
  - 方言の種類のノードの意味上の値（source-text が答えるのは、原文のバイト列と、インラインのノードの論理的な文字列だけである）
  - 方言の種類のノードの HTML 出力（後の段階の GFM の spec と spec-conformance が扱う）
  - 規則の実行時間そのものを本体が制限すること。本体は規則を呼ぶ回数を抑え、規則の中の時間は方言の作者の責任とする。
- **Adjacent expectations**:
  - syntax-tree の内部 API だけで木を作り、syntax-tree の「不変条件を検査する関数」で結果を確かめる。方言の種類の ID の空間と、方言の属性を木に載せて読み出す手段は、syntax-tree のものを使う。利用者は、方言の種類のノードを、syntax-tree のたどる API で読む。
  - syntax-tree の「設定の検査」に、方言の定義の検査を足す。これまで方言の項目には誤りとなる値がなかったが、この spec の後は、不正な方言の定義が設定の誤りになる。
  - block-parser と inline-parser が確保した箇所に、規則の呼び出しを足す。方言が指定されていないときの結果は変えない。
  - 資源の上限（入れ子の深さ、ノードの数）は、block-parser と inline-parser の定義のまま、方言の種類のノードにも適用する。
  - 後の段階の GFM の spec は、この spec の公開 API だけで各拡張を定義する。この spec の契約で GFM の各拡張を表せるかどうかは、設計の段階で確かめる。
  - spec-conformance は、方言を指定しない解析が spec.txt の全例を通ることと、全体の性質（決定性、並行性など）を確かめる。この spec は、方言に関わる部分を単体テストで確かめる。

## Requirements

### Requirement 1: 方言の定義と指定
**Objective:** As a 方言の作者, I want 拡張の集合を自分のコードで定義して、解析の設定に指定したい, so that 本体のコードを変えずに、CommonMark にない構文を足せる

#### Acceptance Criteria
1. The 公開 API shall 方言を、0 個以上の拡張の、順序のある集合として定義できるようにする
2. The 公開 API shall 拡張ごとに、次のものを定義できるようにする。名前、独自のノードの種類（Requirement 2）、ブロックの規則（Requirement 4 から 6）、インラインの規則（Requirement 7）、区切りの種類（Requirement 8）、後処理の規則（Requirement 9）、文書ごとの状態を作る・捨てる関数（Requirement 12）。
3. The 公開 API shall 名前のほかの項目を、どれも省略できるようにする（インラインの規則だけを持つ拡張、後処理の規則だけを持つ拡張などを定義できる）
4. When 方言が解析の設定に指定されて、解析が行われる, the 解析 shall その方言のすべての拡張の規則を、この文書の契約に従って呼ぶ
5. The 本体 shall 方言の定義を変更せず、解析が終わった後に方言の定義への参照を文書に残さない（利用者は、解析の後で、文書を解放する前に方言の定義を捨ててよい）
6. The 公開 API shall 方言の定義が、差し込み口の契約のどの版に向けて書かれたかを、本体が判別できるようにする
7. The 公開 API shall 利用者が、ライブラリを変更も再ビルドもせずに、公開ヘッダだけを使って方言を定義できるようにする
8. The ライブラリ shall この spec の時点では、組み込みの方言を持たない

### Requirement 2: 独自のノードの種類と属性
**Objective:** As a 方言の作者, I want 方言に固有のノードの種類と属性を登録したい, so that 利用者が、方言の要素を CommonMark の要素と同じ方法で木から読める

#### Acceptance Criteria
1. The 公開 API shall 拡張が、独自のノードの種類を 0 個以上登録できるようにする
2. The 公開 API shall 種類ごとに、次のものを登録できるようにする。ID（syntax-tree が方言のために空けた ID の空間の値）と、ブロックかインラインかの別。
3. Where 種類がブロックである, the 公開 API shall その種類が、ブロックを子に持てるコンテナか、ブロックを子に持たないリーフかを登録できるようにする
4. When 規則の結果が採用されて、方言の種類のノードが木に加わる, the 本体 shall そのノードに、登録された ID と別（ブロックかインラインか）を持たせる
5. When 規則の結果が、ノードの属性の値（バイト列）を伴う, the 本体 shall その値の写しを文書に持たせ、syntax-tree のたどる API で読めるようにする
6. The 本体 shall 属性の値の中身を解釈せず、検査しない（中身の形式は、方言の作者が決める）
7. If 規則の結果が、その方言に登録されていない種類の ID を使う, then the 結果の検査 shall その結果を不正とする
8. If 規則の結果が、種類の別と合わない位置にノードを置く（インラインの種類を文書の子にする、ブロックの種類をインラインの子にする、リーフにブロックの子を持たせる）, then the 結果の検査 shall その結果を不正とする
9. Where 種類がブロックである, the 公開 API shall その種類のブロックが、空行で閉じるか、空行でも続くかを登録できるようにし、空行でも続くコンテナについては、空行で消費する桁の数（CommonMark のリスト項目の内容の字下げにあたる数）も登録できるようにする

### Requirement 3: 方言の定義の検査
**Objective:** As a 利用者, I want 方言の定義の誤りを解析の前に知りたい, so that 誤った定義のまま解析して、分かりにくい結果になることがない

#### Acceptance Criteria
1. When 方言を指定した設定が渡される, the 設定の検査 shall 方言の定義が正しいかどうかを判定し、解析の入口も同じ判定を、解析を始める前に行う
2. If 方言の定義が、本体の対応しない版の契約に向けて書かれている, then the 設定の検査 shall 設定の誤りを返す
3. If 拡張に名前がない, then the 設定の検査 shall 設定の誤りを返す
4. If 登録された種類の ID が、方言のための ID の空間の外にある, then the 設定の検査 shall 設定の誤りを返す
5. If 同じ種類の ID が、1 つの方言の中で 2 回以上登録されている, then the 設定の検査 shall 設定の誤りを返す
6. If 規則または区切りの種類が、その方言に登録されていない種類の ID を、作るノードの種類として指定している, then the 設定の検査 shall 設定の誤りを返す
7. If 規則または区切りの種類が、差し込み口と合わない別の種類を指定している（ブロックの規則がインラインの種類を、インラインの規則と区切りの種類がブロックの種類を指定している）, then the 設定の検査 shall 設定の誤りを返す
8. If 区切りの種類の定義が Requirement 8 の条件を満たさない, then the 設定の検査 shall 設定の誤りを返す
9. If 文書ごとの状態を作る関数と捨てる関数の片方だけが指定されている, then the 設定の検査 shall 設定の誤りを返す
10. When 拡張が 0 個の方言が指定される, the 設定の検査 shall 成功を返す
11. When 拡張が 0 個の方言を指定した解析が行われる, the 解析 shall 方言を指定しないときと同じ結果を返す
12. If 方言の定義が誤っている, then the 解析の入口 shall 設定の誤りを返し、文書を返さず、どの規則も呼ばない
13. The 設定の検査 shall 方言の定義の検査で、規則を呼ばず、メモリを確保せず、同じ定義に対して常に同じ結果を返す
14. If 空行で消費する桁の数が、空行でも続くコンテナでない種類で 0 でない、または公開の上限を超える, then the 設定の検査 shall 設定の誤りを返す

### Requirement 4: ブロックの開始の規則
**Objective:** As a 方言の作者, I want 行の中の、新しいブロックが始まりうる位置で、方言のブロックを開きたい, so that CommonMark にないブロック（脚注の定義など）を足せる

#### Acceptance Criteria
1. When ブロックの解析が、新しいブロックの開始を判定する位置に来る, the ブロックの解析 shall CommonMark のブロックの開始を判定する前に、方言の開始の規則を、拡張の順に呼ぶ
2. The ブロックの解析 shall 開始の規則に、次のものを読み取り専用で渡す。内容、その行の範囲、判定する位置（プレフィックスの後ろ）とその桁、いちばん内側の開いているブロックの種類、その位置が段落の続きになりうるかどうか。
3. The 開始の規則の契約 shall 規則が、次のどちらかを返せるようにする。「開始しない」。「開始する」と、その行のうち開始の印として消費する範囲。開くブロックの種類（その拡張が登録したブロックの種類）は、規則の登録で指定する。
4. When 開始の規則が「開始しない」を返す, the ブロックの解析 shall 次の拡張の規則を呼び、どの規則も開始しなければ、CommonMark の規則でその位置を判定する
5. When 開始の規則が「開始する」を返して、結果が検査を通る, the ブロックの解析 shall その種類のブロックを、CommonMark のブロックと同じ流れで開く（段落を割り込めるときは段落を閉じ、開いているコンテナの子にする）
6. The 公開 API shall 開始の規則ごとに、その規則が開くブロックの種類と、その規則が段落に割り込めるかどうかを登録できるようにする
7. While 判定する位置が段落の続きになりうる, the ブロックの解析 shall 段落に割り込めない開始の規則を呼ばない
8. When 開いたブロックがコンテナである, the ブロックの解析 shall 消費した範囲の後ろで、新しいブロックの開始の判定を続ける
9. When 開いたブロックがリーフである, the ブロックの解析 shall その行の残りを、そのブロックの最初の行の内容とする
10. If 「開始する」の結果が、次のどれかにあたる, then the 結果の検査 shall その結果を不正とする。消費する範囲が、判定する位置から始まっていない。消費する範囲が、その行の外に出る。コンテナを開くのに、消費する範囲の長さが 0 である。
11. If 開始の規則の結果が不正である, then the ブロックの解析 shall その規則が「開始しない」を返したものとして続ける
12. While コードブロックまたは HTML ブロックの中の行を処理している, the ブロックの解析 shall 開始の規則を呼ばない

### Requirement 5: ブロックの継続の規則
**Objective:** As a 方言の作者, I want 開いている方言のブロックが次の行でも続くかどうかを決めたい, so that 複数の行にまたがる方言のブロックを表せる

#### Acceptance Criteria
1. When 方言の種類のブロックが開いていて、空行でない次の行を処理する, the ブロックの解析 shall そのブロックを開いた拡張の継続の規則を、その行について 1 回だけ呼ぶ
2. The ブロックの解析 shall 継続の規則に、次のものを読み取り専用で渡す。内容、その行の範囲、判定する位置とその桁、開いているブロックの種類と範囲。
3. The 継続の規則の契約 shall 規則が、次のどちらかを返せるようにする。「続かない」。「続く」と、その行のうちプレフィックスとして消費する範囲。
4. When 継続の規則が「続く」を返して、結果が検査を通る, the ブロックの解析 shall そのブロックを開いたままにし、消費した範囲の後ろから、内側のブロックの照合を続ける
5. When 継続の規則が「続かない」を返す, the ブロックの解析 shall CommonMark のコンテナが続かないときと同じ流れで扱う（内側に開いている段落があり、その行が怠惰な継続行にあたれば、段落を続ける。そうでなければ、そのブロックと内側のブロックを閉じる）
6. When 方言の種類のブロックが開いていて、次の行が（判定する位置から後ろで）空行である, the ブロックの解析 shall 継続の規則を呼ばず、その種類の登録（Requirement 2 の 9）に従って、そのブロックを閉じるか続ける。続けるときは、CommonMark の子を持つリスト項目と同じく、空白が登録した桁の数以上あればその桁の数だけを、足りなければ空白のすべてを消費する（リーフと、桁の数が 0 の種類は何も消費しない）
7. Where 拡張が、登録したブロックの種類について継続の規則を持たない, the ブロックの解析 shall その種類のブロックを、空行でない次の行で「続かない」ものとして扱う
8. If 「続く」の結果が、次のどれかにあたる, then the 結果の検査 shall その結果を不正とする。消費する範囲が、判定する位置から始まっていない。消費する範囲が、その行の外に出る。
9. If 継続の規則の結果が不正である, then the ブロックの解析 shall その規則が「続かない」を返したものとして続ける
10. When 内容の終わりに達する, the ブロックの解析 shall 開いている方言の種類のブロックを、CommonMark のブロックと同じ順で閉じる
11. The ブロックの解析 shall 方言の種類のブロックの範囲と行を、CommonMark のブロックと同じ決まりで定める（開始の位置から、そのブロックに属する最後の行の内容の終わりまで）

### Requirement 6: ブロックを閉じるときの規則
**Objective:** As a 方言の作者, I want ブロックが閉じるときに、その中身を見て、種類や構造を決めたい, so that 段落を表に変えるなど、全部の行を見ないと決まらないブロックを表せる

#### Acceptance Criteria
1. When 方言の種類のブロックが閉じる, the ブロックの解析 shall そのブロックを開いた拡張の、閉じるときの規則を 1 回だけ呼ぶ
2. When 段落が閉じる（リンク参照定義を取り出した後に、段落として残る部分がある）, the ブロックの解析 shall 残った段落について、段落を閉じるときの規則を、拡張の順に、どれかが「置き換える」を返すまで呼ぶ
3. The ブロックの解析 shall 閉じるときの規則に、次のものを読み取り専用で渡す。内容、閉じるブロックの種類と範囲、そのブロックの各行の範囲と、各行の内容が始まる位置。
4. The 閉じるときの規則の契約 shall 規則が、次のどちらかを返せるようにする。「そのままにする」。「置き換える」と、置き換えの内容。
5. The 閉じるときの規則の契約 shall 方言の種類のブロックの置き換えの内容として、次のものを指定できるようにする。そのブロックの属性の値。そのブロックがリーフであれば、インラインとして解析する範囲。
6. The 閉じるときの規則の契約 shall 段落の置き換えの内容として、段落の範囲を、原文の順に並ぶ 1 つ以上のブロックに分けることを指定できるようにする。各ブロックは、段落のまま残す部分か、その拡張が登録した種類のブロックである。登録した種類のブロックには、次のものを指定できる。属性の値。子孫にするブロック（その拡張が登録した種類）の範囲、属性、親子の関係。リーフであれば、インラインとして解析する範囲。
7. When 置き換えが検査を通る, the ブロックの解析 shall 置き換えの内容のとおりに木を作る。段落のまま残す部分は、CommonMark の段落として扱い、その内容をインラインとして解析する。
8. When 置き換えが、インラインとして解析する範囲を指定している, the インラインの解析 shall その範囲を、段落の内容の範囲と同じ規則で解析し、できたインラインのノードを、その範囲を指定されたブロックの子にする
9. Where インラインとして解析する範囲が複数の行にまたがる, the インラインの解析 shall 続きの行のプレフィックスと先頭の空白を、段落と同じく内容に含めない
10. If 置き換えが、次のどれかにあたる, then the 結果の検査 shall その結果を不正とする。どれかのブロックの範囲が、閉じるブロックの範囲の外に出る。子の範囲が親の範囲の外に出る。兄弟の範囲が重なるか、原文の順に並んでいない。インラインとして解析する範囲が、それを持つブロックの範囲の外に出る。インラインとして解析する範囲を、コンテナまたはブロックを子に持つブロックに指定している。段落の置き換えの、段落のまま残す部分が、行の途中で始まるか終わる。
11. If 閉じるときの規則の結果が不正である, then the ブロックの解析 shall その置き換えを一部も採用せず、そのブロックを、規則が「そのままにする」を返したものとして閉じる
12. The ブロックの解析 shall 段落と方言の種類のほかのブロック（見出し、コードブロックなど）について、閉じるときの規則を呼ばない
13. The ブロックの解析 shall リンク参照定義の取り出しと Setext 見出しの判定を、段落を閉じるときの規則によって変えない

### Requirement 7: インラインの起動文字の規則
**Objective:** As a 方言の作者, I want 決めた文字が現れた位置で、方言のインラインのノードを作りたい, so that CommonMark にないインライン（脚注の参照など）を足せる

#### Acceptance Criteria
1. The 公開 API shall 拡張が、インラインの規則を、起動文字（1 バイトの ASCII の文字）および、その規則が作るノードの種類（その拡張が登録したインラインの種類）と組にして登録できるようにする
2. When インラインの解析が、内容の範囲の中で、登録された起動文字に来る, the インラインの解析 shall CommonMark の規則でその文字を扱う前に、その文字に登録された規則を、拡張の順に呼ぶ
3. The インラインの解析 shall インラインの規則に、次のものを読み取り専用で渡す。内容、起動文字の位置、いま解析している内容の範囲（その行の内容の終わりと、内容の範囲の全体の終わりが分かるもの）。
4. The インラインの規則の契約 shall 規則が、次のどちらかを返せるようにする。「作らない」。「作る」と、ノードの範囲、属性の値。
5. When インラインの規則が「作らない」を返す, the インラインの解析 shall 次の拡張の規則を呼び、どの規則も作らなければ、CommonMark の規則でその文字を扱う（CommonMark の起動文字でなければ、テキストにする）
6. When インラインの規則が「作る」を返して、結果が検査を通る, the インラインの解析 shall その範囲を子のないノード 1 つにし、ノードの範囲の終わりから解析を続ける
7. If 「作る」の結果が、次のどれかにあたる, then the 結果の検査 shall その結果を不正とする。ノードの範囲が、起動文字の位置から始まっていない。ノードの範囲の長さが 0 である。ノードの範囲が、いま解析している内容の範囲の外に出る。ノードの範囲が、続きの行のプレフィックスの途中で終わる。
8. If インラインの規則の結果が不正である, then the インラインの解析 shall その規則が「作らない」を返したものとして続ける
9. While コードスパン、オートリンク、生の HTML、リンクの dest と title の中を走査している, the インラインの解析 shall インラインの規則を呼ばない（CommonMark の起動文字と同じ扱いである）
10. The インラインの解析 shall バックスラッシュでエスケープされた文字の位置で、インラインの規則を呼ばない
11. The インラインの解析 shall 1 回の解析で、1 つの起動文字の位置につき、各規則を 1 回までしか呼ばない

### Requirement 8: 区切りの種類
**Objective:** As a 方言の作者, I want 開く印と閉じる印で内容を挟む構文（取り消し線の `~` など）を、規則の関数を書かずに登録したい, so that 強調と同じ入れ子の扱いを、方言の区切りでも得られる

#### Acceptance Criteria
1. The 公開 API shall 拡張が、区切りの種類を、次のものの組として登録できるようにする。区切りの文字（1 バイトの ASCII の句読点）、対応に使える列の長さ（1 から 4 のうちの 1 つ以上）、対応したときに作るノードの種類（その拡張が登録したインラインの種類）。
2. When インラインの解析が、登録された区切りの文字の列に来る, the インラインの解析 shall その列が開けるか・閉じられるかを、`*` の列と同じ決まり（左側と右側の区切りの列の判定）で定める
3. When 閉じられる列と、その前にある同じ種類の開ける列が、同じ長さで、その長さが登録された長さのどれかである, the インラインの解析 shall 2 つの列を対応させ、開く列の始まりから閉じる列の終わりまでを、登録された種類のノード 1 つにし、間の内容をその子にする
4. The インラインの解析 shall 方言の区切りの対応を、強調と同じ流れ（閉じる列を前から順に処理し、いちばん近い開く列と対応させ、間に残った区切りをテキストにする）で定め、強調・リンク・ほかの方言の区切りとの入れ子を、強調どうしと同じ決まりで扱う
5. When 区切りの文字の列が、どの列とも対応しない（長さが登録された長さでないものを含む）, the インラインの解析 shall その列をテキストにする
6. If 区切りの文字が、次のどれかにあたる, then the 設定の検査 shall 設定の誤りを返す。ASCII の句読点でない。CommonMark の起動文字である（`` \ ` & < * _ [ ] ! ``）。同じ方言の中で、ほかの区切りの種類またはインラインの規則の起動文字として登録されている。
7. If 対応に使える列の長さが 1 つも指定されていないか、1 から 4 でない長さを含む, then the 設定の検査 shall 設定の誤りを返す
8. If 1 つの方言に登録された区切りの種類の数が、本体が扱える上限を超える, then the 設定の検査 shall 設定の誤りを返す
9. The 公開 API shall 本体が扱える区切りの種類の数の上限を、公開ヘッダで示す
10. The インラインの解析 shall 方言の区切りが大量に並ぶ入力でも、時間を入力の長さにほぼ比例させる

### Requirement 9: 後処理の規則
**Objective:** As a 方言の作者, I want ブロックとインラインの解析が終わった木を見て、ノードを加えたり種類を変えたりしたい, so that 木の形を見ないと決まらない構文（タスクリストの印など）を表せる

#### Acceptance Criteria
1. When ブロックの解析とインラインの解析が終わる, the 解析 shall 各拡張の後処理の規則を、拡張の順に、1 つの文書につき 1 回ずつ呼ぶ
2. The 解析 shall 後処理の規則が、syntax-tree のたどる API で、その時点の木の全体を読めるようにする
3. The 後処理の契約 shall 規則が、次の操作を、1 回の呼び出しの中で何回でも求められるようにする。ノードの種類を、その拡張が登録した同じ別（ブロックかインラインか）の種類に変える。方言の種類のノードの属性の値を設定する。テキストのノード、またはその拡張が登録した種類のノードの範囲を、いまの範囲の内側に縮める。指定したノードの子として、その拡張が登録した種類の、子のないノードを加える。テキストのノードを、指定した位置で 2 つのテキストのノードに分ける。
4. When 操作が求められる, the 解析 shall その操作を検査し、検査を通れば木に適用して成功を、通らなければ木を変えずに不正であることを、規則に返す
5. When ノードを加える操作が検査を通る, the 解析 shall そのノードを、兄弟が原文の順に並ぶ位置に置く
6. If 操作が、次のどれかにあたる, then the 結果の検査 shall その操作を不正とする。その文書のノードでないものを指定している。適用すると不変条件のどれかが成り立たなくなる（範囲が親の外に出る、兄弟と重なる、子の範囲が縮めた範囲の外に残る、など）。文書のノードまたはリンク参照定義のノードを変える。テキストでも、その拡張が登録した種類でもないノードの範囲を縮める。子を持てない種類のノード、またはその別の子を持てない種類のノードに、子を加える。種類を、登録されていない種類、CommonMark の種類、または別（ブロックかインラインか）の違う種類に変える。子を持つノードの種類を、その子の別（ブロックかインラインか）を持てない種類に変える。テキストのノードを、その範囲の端または外で、もしくは UTF-8 の 1 文字の途中で分ける。
7. If 操作が不正である, then the 解析 shall その操作だけを採用せず、それまでに適用した操作を保ち、後処理を続ける
8. The 後処理の契約 shall 規則に、ノードを取り除く操作と、兄弟の順を入れ替える操作を与えない
9. When すべての後処理が終わる, the 解析 shall すべての不変条件が成り立つ文書を返す
10. The 解析 shall 後処理の操作で加わるノードにも、ノードの数の上限を適用する

### Requirement 10: 結果の検査と、不正な結果の扱い
**Objective:** As a 利用者, I want 方言の規則に誤りがあっても、木が壊れず、解析が最後まで進んでほしい, so that 自分や第三者が書いた方言を、木の不変条件に頼ったまま使える

#### Acceptance Criteria
1. The 本体 shall 規則が返したすべての結果と、後処理のすべての操作を、木に反映する前に検査する
2. The 結果の検査 shall 各差し込み口の条件（Requirement 2、4 から 7、9）に加えて、結果を採用した後の木が、syntax-tree の不変条件（構造、範囲、行、入れ子の各条件）を満たすことを確かめる
3. If 結果が不正である, then the 本体 shall その結果を一部も木に反映せず、診断を 1 件足し（Requirement 11）、各差し込み口で定めた扱いで解析を続ける
4. If 規則が、契約で定めていない値を返す, then the 結果の検査 shall その結果を不正とする
5. When 方言を指定した解析が成功する, the 解析 shall 規則が何を返したかによらず、すべての不変条件が成り立つ文書を返す
6. The 本体 shall 規則の不正な結果を、解析の失敗（エラーの種類）にしない
7. The 本体 shall 不正な結果を返した規則を、その後も契約どおりに呼び続ける（規則や拡張を途中で無効にしない）
8. The 結果の検査 shall 規則が返した範囲や ID がどんな値でも、内容と文書の外のメモリを読まず、必ず終了する
9. The 結果の検査 shall 1 つの結果の検査の時間を、その結果が含むノードの数にほぼ比例させ、後処理の 1 つの操作の検査の時間を、対象のノードの子孫の数によらないものにし、再帰を使わない
10. When 規則が、メモリ不足で続けられないことを伝える, the 解析 shall メモリ不足を返し、確保したものをすべて解放し、文書を返さない
11. If 資源の上限（入れ子の深さ、ノードの数）が、方言の種類のノードによって超えられる, then the 解析 shall CommonMark のノードで超えたときと同じく、資源の上限の超過を返し、文書を返さない
12. The 本体 shall 不正とした結果のノードを、ノードの数の上限に数えない（上限と比べるのは、返す木のノードの数である）

### Requirement 11: 不正な結果の診断
**Objective:** As a 方言の作者, I want 自分の規則のどの結果が、なぜ採用されなかったかを知りたい, so that 規則の誤りを見つけて直せる

#### Acceptance Criteria
1. When 結果または後処理の操作が不正とされる, the 本体 shall 文書に診断を 1 件足す
2. The 診断 shall 位置として、その規則が呼ばれた位置（ブロックの開始と継続では判定する位置、閉じるときは閉じるブロックの開始、インラインでは起動文字の位置、後処理では操作の対象のノードの開始）を持つ
3. The 診断 shall 重大度を「エラー」とする
4. The 診断 shall メッセージに、次の 3 つを含める。拡張の名前、差し込み口の種類（ブロックの開始、継続、閉じるとき、インライン、後処理）、不正とした理由の種類（範囲が外に出る、兄弟と重なる、順でない、登録されていない種類、など）。
5. The 本体 shall 診断を、不正な結果が見つかった順に足す
6. When 同じ内容、同じ設定、同じ方言で解析が繰り返される, the 解析 shall 同じ診断を同じ順に返す
7. If 診断を足すための確保が失敗する, then the 解析 shall メモリ不足を返し、文書を返さない
8. While 方言が指定されていない, the 解析 shall この spec が定める診断を 1 件も足さない
9. When すべての結果が検査を通る, the 解析 shall この spec が定める診断を 1 件も足さない

### Requirement 12: 規則への入力、所有権、文書ごとの状態
**Objective:** As a 方言の作者, I want 規則が何を読めて、何を持ち続けてよいかが決まっていてほしい, so that 同じ方言を、並行する別々の解析で安全に使える

#### Acceptance Criteria
1. The 本体 shall 規則に、内容と木を読み取り専用で渡し、規則が内容と木を直接書き換える手段を与えない
2. The 本体 shall 規則が返した結果（範囲、種類、属性の値、置き換えの内容）を、採用するときに文書へ写し、規則の呼び出しの後で、規則が返したメモリを参照しない
3. Where 拡張が、文書ごとの状態を作る関数と捨てる関数を持つ, the 解析 shall 解析の初めに状態を作る関数を 1 回呼び、その拡張のすべての規則の呼び出しに、その状態を渡す
4. Where 拡張が、文書ごとの状態を作る関数と捨てる関数を持つ, the 解析 shall 解析の入口から戻る前に、成功した場合も失敗した場合も、状態を捨てる関数を 1 回だけ呼ぶ
5. The 解析 shall 文書ごとの状態を作る関数に、その解析の確保関数を渡し、方言がそれを使って状態を確保できるようにする
6. If 状態を作る関数が失敗を伝える, then the 解析 shall メモリ不足を返し、すでに作った状態をすべて捨て、文書を返さない
7. The 解析 shall ある解析のために作った状態を、ほかの解析の規則の呼び出しに渡さない
8. While 複数のスレッドが、同じ方言の定義を使って、それぞれ別の内容を解析している, the 解析 shall どのスレッドにも、1 つのスレッドで解析したときと同じ結果を返す（方言の規則が、文書ごとの状態のほかに可変の状態を持たないことを前提とする）
9. The 公開ヘッダ shall 方言の作者が守る決まりを文書として示す。規則は、文書ごとの状態のほかに可変の状態を持たない。規則は I/O を行わず、`abort`、`exit`、`longjmp` を使わない。規則は、同じ入力に対して同じ結果を返す。規則は、渡されたものを呼び出しの後で参照しない。
10. The 本体 shall 規則を呼ぶ順序と回数を、内容、設定、方言の定義だけで決める

### Requirement 13: 方言を使わないとき、および製品の性質の維持
**Objective:** As a 利用者, I want 方言を使わないときに何も変わらず、方言を使うときも製品が保証する性質が保たれてほしい, so that 拡張点が加わっても、これまでの結果と性能に頼れる

#### Acceptance Criteria
1. While 方言が指定されていない, the 解析 shall この spec の前と同じ木と診断を返す
2. While 方言が指定されていない, the 解析 shall 方言のための確保を 1 回も行わない（同じ入力に対する確保の回数が、この spec の前と変わらない）
3. While 方言が指定されている, the 解析 shall どの規則も結果を出さなかった部分について、方言を指定しないときと同じ木を作る
4. The 本体 shall 規則を呼ぶ回数を、次の範囲に抑える。開始の規則は、行の中の判定する位置 1 つにつき、規則ごとに 1 回まで。継続の規則は、開いているブロックと、空行でない行の組 1 つにつき 1 回。空行では呼ばない。閉じるときの規則は、閉じるブロック 1 つにつき、規則ごとに 1 回まで。インラインの規則は、起動文字の位置 1 つにつき、規則ごとに 1 回まで。後処理の規則は、文書 1 つにつき 1 回。
5. While すべての規則が、渡された行または範囲の長さにほぼ比例する時間で戻る, the 解析 shall 全体の時間を、入力の長さにほぼ比例させる（拡張の数と規則の数は定数とみなす）
6. The 本体 shall 規則の呼び出し、結果の検査、結果の採用、後処理の操作の適用を、再帰を使わずに行う
7. If 方言を指定した解析が失敗する, then the 解析 shall 確保したものをすべて解放し、部分的な文書を返さない
8. When 同じ内容、同じ設定、同じ方言で解析が繰り返される, the 解析 shall 同じ木を返す（方言の規則が、同じ入力に対して同じ結果を返すことを前提とする）
9. The 本体 shall 方言を指定した解析でも、内容のバイト列を変更せず、グローバルな変数と静的な可変の状態を持たず、I/O を行わない
10. The 本体 shall 方言のために必要なメモリを、その解析の確保関数だけから得る

### Requirement 14: 公開 API に共通の性質
**Objective:** As a 利用者, I want 方言の公開 API が、ほかの公開 API と同じ決まりで使えてほしい, so that 対象のどの環境でも、同じ方法で方言を定義できる

#### Acceptance Criteria
1. The 公開 API shall 方言に関わる関数と型の名前を `amark_` で、マクロと列挙の定数の名前を `AMARK_` で始める
2. The 公開ヘッダ shall C99 として、対象のすべてのコンパイラ（MSVC、MinGW、GCC、Clang）で警告なしに取り込め、C++ からも取り込め、それだけで取り込め、内部ヘッダを取り込まない
3. The 公開 API shall 方言の定義を、静的な const のデータとして書けるようにする（定義のための確保も、登録のための関数の呼び出しも要らない）
4. The 公開 API shall 文書とノードを、これまでと同じく中身の見えないハンドルとして規則に渡し、木と文書の構造体のレイアウトを公開ヘッダに含めない
5. The 公開 API shall 木を作る内部 API と、不変条件を検査する関数を、公開しない
6. Where 動的ライブラリを作る構成である, the ビルド構成 shall この spec が公開する関数だけを公開シンボルに加え、公開シンボルの一覧をそれに合わせる
7. The 公開 API shall 失敗を戻り値のエラーの種類で伝え、新しいエラーの種類を足さない（方言の定義の誤りは「設定の誤り」である）

### Requirement 15: テスト用の方言と単体テスト
**Objective:** As a 解析器の開発者, I want 小さなテスト用の方言で、各差し込み口と検査が動くことを確かめたい, so that 後の段階の GFM の spec が、確かめられた契約の上に拡張を書ける

#### Acceptance Criteria
1. The テスト用の方言 shall 公開 API だけを使って定義し、次のものを少なくとも 1 つずつ持つ。コンテナのブロックの種類とその開始・継続の規則。リーフのブロックの種類とその開始・継続・閉じるときの規則。段落を閉じるときの規則（段落の一部を方言のブロックに置き換え、子孫のブロックと、インラインとして解析する範囲を指定するもの）。インラインの起動文字の規則。区切りの種類。後処理の規則（Requirement 9 の各操作を使うもの）。文書ごとの状態。
2. The テスト用の方言 shall テストのコードにだけ置き、ライブラリとその公開シンボルに含めない
3. The 単体テスト shall テスト用の方言を指定した解析で、各差し込み口の正しい結果が木に反映されること（種類、別、範囲、行、属性の値、親子の関係）と、できた木が不変条件の検査を通ることを確かめる
4. The 単体テスト shall 不正な結果を返す規則を使って、Requirement 2、4 から 7、9 の不正とする条件のそれぞれについて、次の 4 つを確かめる。その結果が木に反映されない。定めた位置・重大度・メッセージの診断が 1 件足される。解析が成功し、残りの内容が解析される。できた木が不変条件の検査を通る。
5. The 単体テスト shall Requirement 3 と Requirement 8 の、設定の誤りとなる条件のそれぞれについて、設定の検査と解析の入口が設定の誤りを返すことを確かめる
6. The 単体テスト shall 方言を指定しない解析と、拡張が 0 個の方言を指定した解析と、どの規則も結果を出さない方言を指定した解析が、同じ木を返すことを確かめる
7. The 単体テスト shall 方言を指定しない解析の確保の回数が、方言の規則の呼び出しを足す前と変わらないことを確かめる
8. When 単体テストが、確保と解放を数える確保関数を使い、確保の失敗を各回に注入して、テスト用の方言を指定した解析を実行する, the 解析 shall 成功した場合も失敗した場合も、解放されないメモリを残さず、文書ごとの状態を捨てる関数を、作る関数が成功した回数と同じ回数だけ呼ぶ
9. The 単体テスト shall 同じ方言の定義を使った解析を繰り返して、木と診断が同じになることと、文書ごとの状態が解析の間で共有されないことを確かめる
10. The 単体テスト shall 方言のコンテナを 10 万段に入れ子にした入力（入れ子の深さの上限なし）と、方言の区切りを大量に並べた入力について、解析、不変条件の検査、解放が、スタックを使い切らずに終わることを確かめる
11. The 単体テスト shall 方言の区切りと強調・リンクの入れ子、方言のコンテナの中の怠惰な継続行、方言のブロックによる段落への割り込み、空行で閉じる種類と空行でも続く種類のブロックを、それぞれ確かめる
12. The 単体テスト shall 不正な結果を返し続ける規則と、ノードの数の上限を指定した解析で、返す木のノードの数が上限以下なら解析が成功することを確かめる
