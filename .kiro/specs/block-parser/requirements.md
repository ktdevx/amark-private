# Requirements Document

## Project Description (Input)
**誰が困っているか**：amark を自分のプロジェクトに組み込む利用者と、block-parser の結果を使う下流の spec（inline-parser、source-text、dialect-extension）の開発者。

**現在の状況**：syntax-tree（データモデルと木を作る内部 API）と unicode-tables（case folding）はできているが、Markdown の入力から木を得る手段がない。CommonMark のブロック構造（コンテナと遅延継続行、リーフの開始と終了、タブの桁）を、仕様どおりに、入力の長さにほぼ比例する時間で、再帰を使わずに解析する部分が要る。しかも原文を複製せず、範囲として残さなければならない。

**何を変えるか**：
- 解析の入口となる公開 API を用意する。入力のバイト列と設定を受け取り、文書かエラーを返す。設定（範囲 `[start, end)`、UTF-8 の扱い（エラーか U+FFFD への置換か）、資源の上限、確保関数、ファイル名）を検査して適用する。失敗したときは確保したものをすべて解放し、部分的な木を返さない。
- 行を分割し、行末記号（LF、CR、CRLF）は入力のまま保つ。タブを桁で扱い（タブ幅 4）、タブの一部だけを消費した場合の残りの桁を記録する。
- コンテナ（ブロッククォート、リスト項目）と遅延継続行、リーフ（テーマの区切り、ATX 見出し、Setext 見出し、インデントされたコードブロック、フェンスのコードブロック、7 種類の HTML ブロック、段落、空行）を解析し、リストのタイトとルーズを判定する。
- リンク参照定義を解析し、ラベルを正規化し（case folding、空白の畳み込み、999 文字の上限）、正規化したラベルをキーとする定義の表をアリーナに作る。
- 行ごとのプレフィックスの情報を記録し（source-text が使う）、インライン解析に渡す内容の範囲を用意する（inline-parser が使う）。
- 資源の上限（入れ子の深さ、ノードの数、入力の大きさ）を検査する。
- 方言の差し込み口（ブロックの開始と継続）の位置を設計の段階で確保する。

**方針**：cmark と同じく、行ごとに開いているコンテナとの一致を確かめ、新しいブロックを開始し、内容を追加する。開いているブロックは明示的なスタックで管理し、リンク参照定義は段落を閉じるときに取り出す。

**範囲外**：インライン構造（inline-parser）、文字列の組み立て（source-text）、差し込み口の公開 API と結果の検査（dialect-extension）、spec.txt 全体を通すことの確認（spec-conformance。ただしブロックに関わる例はこの spec の単体テストで確かめる）、BOM の除去とフロントマター（利用者が範囲で除く）、規則を設定で変えること。

**制約**：再帰を使わない。時間は入力の長さにほぼ比例する。グローバルな状態を持たない。対象は CommonMark 0.31.2。上流は syntax-tree、unicode-tables、project-foundation。
