# Requirements Document

## Project Description (Input)
**誰が困っているか**：amark を自分のプロジェクトに組み込む利用者と、ノードの文字列を使う下流の spec（spec-conformance）の開発者。

**現在の状況**：ノードは原文の範囲しか持たない。そのため利用者は、範囲の中にあるコンテナのプレフィックス（`> ` やリストの字下げ）、タブの一部だけが消費された残り、エスケープ、文字参照を、自分で処理しなければならない。これは仕様の細部を知らないと正しく書けない。block-parser は行ごとのプレフィックスの情報（内容が始まる位置と、補う空白の数）を記録しており、inline-parser は dest、title などの範囲を属性として持つ。

**何を変えるか**：
- ノードの範囲から、論理的な文字列を組み立てる API を用意する。
  - コンテナのプレフィックスを除く。
  - タブの残りの桁を空白で補う。
  - 行の境目を `\n` にする。
  - コードブロックやコードスパンなど、種類ごとの決まり（コードスパンの前後の空白 1 つの除去など）に従う。
- 意味上の値を得る API を用意する。エスケープと文字参照を文字に戻した、リンクの dest と title、コードブロックの info 文字列、テキストの内容。
- 結果は、呼び出す側が渡すバッファか、確保関数で作る文字列で返す。どちらも原文は変更しない。
- 範囲そのもの（原文のバイト列）を、そのまま取り出せるようにする。原文を完全に復元するために使う。
- 単体テストを用意する。

**方針**：block-parser が記録した行ごとの「内容が始まる位置と、補う空白の数」を使い、行を順につなぐ。エスケープと文字参照は unicode-tables の実体名の表を使って戻す。処理は 1 回の走査で行う。境界の候補は、論理的な文字列を組み立てること（プレフィックス、タブ、改行）と、意味上の値を得ること（エスケープ、文字参照）。

**範囲外**：URL のパーセントエンコードや HTML のエスケープなど、出力の形式に固有の処理（出力する側の責任）。原文の置き換え、翻訳の単位への分割（利用者側）。木を書き換えること、Markdown を書き直すこと。

**制約**：入力を変更しない。状態を持たない。結果を書き出すバッファは、呼び出す側が渡すか、確保関数で作る。上流は block-parser（行ごとのプレフィックスの記録）、syntax-tree、unicode-tables。inline-parser とは同じ範囲を扱う隣接の spec。

## Introduction
source-text は、ノードの範囲から、利用者がそのまま使える文字列を作る公開 API を用意する。inline-parser まででは、利用者が受け取るのは範囲だけである。範囲の中には、コンテナのプレフィックス、一部だけが消費されたタブ、バックスラッシュのエスケープ、文字参照がそのまま残っており、利用者は CommonMark の細部を自分で処理しなければならない。この spec で、利用者は、仕様の細部を知らなくても、コードの中身、リンク先、題、テキストを文字列として受け取れるようになる。

この spec は、次の 4 つを用意する。

1. **原文のバイト列の取り出し**：ノードの範囲にあたる原文のバイト列を、複製せずにそのまま返す。
2. **論理的な文字列**：ノードが、コンテナの外の行頭に書かれていたとしたときの文字列を作る。プレフィックスを除き、タブの残りの桁を空白で補い、行末記号を `\n` にする。
3. **意味上の値**：種類ごとの決まりに従った値を作る。コードブロックとコードスパンの中身、テキストとエスケープと文字参照が表す文字、オートリンクの中身、リンクと画像とリンク参照定義の dest と title、コードブロックの info。
4. **結果の受け渡し**：2 と 3 の結果を、呼び出す側が渡すバッファに書くか、確保関数で作った文字列として返す。

この文書で「利用者」は amark を自分のプロジェクトに組み込む人、「下流の開発者」は spec-conformance を開発する人を指す。「内容」「解析する範囲」「文書」「行末記号」「プレフィックス」「桁」は、block-parser の requirements.md と同じ意味で使う。「行の内容」は、inline-parser の requirements.md と同じ意味で使う（各行で、行の記録が「内容が始まる位置」とする位置から、行末記号の直前まで）。「空白」は、断らない限りスペース（U+0020）とタブ（U+0009）を指す。「コンテナ」は、文書、ブロッククォート、リスト、リスト項目のノードを指す。「文字列の取り出し」は、この spec が用意する公開の関数の全体を指す。「答えられない」は、失敗ではなく、求められたものがその呼び出しでは定まらないことを指す（Requirement 11）。

## Boundary Context
- **In scope**:
  - ノードの範囲にあたる原文のバイト列を、そのまま取り出すこと
  - コンテナでないノードの、論理的な文字列を組み立てること（プレフィックス、タブの残りの桁、行末記号）
  - コードブロックの中身と、コードスパンの中身を作ること
  - バックスラッシュのエスケープと文字参照を、文字に戻すこと
  - テキスト、バックスラッシュのエスケープ、文字参照、オートリンクの値を作ること
  - リンクと画像（インラインの形式）、リンク参照定義の dest と title、コードブロックの info の値を作ること
  - 結果を、呼び出す側のバッファか、確保関数で作る文字列で返すこと
  - 上の各項目の単体テスト
- **Out of scope**:
  - URL の正規化とパーセントエンコード、HTML のエスケープ、オートリンクのメールアドレスに `mailto:` を付けることなど、出力の形式に固有の処理（出力する側の責任。テスト用の HTML 出力では spec-conformance が扱う）
  - 子を持つノード（段落、見出し、強調、リンク、画像など）について、子の値をつないだ文字列を作ること。画像の代替テキストの組み立てを含む（出力する側の責任）。利用者は、木をたどり、子のそれぞれの値をつなぐ。
  - リンクのラベルを正規化した文字列を返すこと（ラベルの正規化は block-parser の内部の手段で、公開しない）
  - info を、言語の名前とそのほかの部分に分けること（利用者側）
  - 原文の置き換え、翻訳の単位への分割（利用者側。原文の差し替えの補助 API は、後の段階の候補である）
  - 木を書き換えること、木から Markdown を書き出すこと
  - コンテナのノードの論理的な文字列（Requirement 2 の 9）
  - 内容を読み込むこと、書き出すこと（I/O）
- **Adjacent expectations**:
  - block-parser の行の記録（各行の「内容が始まる位置」と「補う空白の数」）を使う。プレフィックスとインデントの規則を、この spec は自分で持たない。
  - syntax-tree のたどる API が返す範囲と属性（dest、title、info の範囲、コードブロックの書き方、リンクの形式）と、inline-parser が定めるインラインのノードの範囲を、そのまま使う。この spec は、範囲を定め直さない。
  - unicode-tables の実体名の参照を、文字参照を文字に戻すために使う。
  - 利用者は、文書を解放するまで、内容のバイト列を変更も解放もしない（block-parser の解析の入口と同じ約束である）。この spec の関数は、文書を通して内容を読む。
  - 参照の形式のリンクと画像の dest と title は、利用者が、syntax-tree のたどる API で参照先のリンク参照定義を得て、その定義について求める（Requirement 7 の 5）。
  - spec-conformance は、この spec の値から HTML を作り、spec.txt の全例と比べる。この spec は、spec.txt の全例を通すことまでは確かめない。
  - dialect-extension が方言のノードを足した後も、この spec の関数は、CommonMark の種類のノードについて同じ結果を返す。方言の種類のノードについて、この spec が答えるのは、原文のバイト列（Requirement 1）と、インラインのノードの論理的な文字列（Requirement 2）だけである。

## Requirements

### Requirement 1: 原文のバイト列の取り出し
**Objective:** As a 利用者, I want ノードの範囲にあたる原文のバイト列を、そのまま受け取りたい, so that 変えない部分を、書式も行末記号も原文のまま残せる

#### Acceptance Criteria
1. When 文書とノードが渡される, the 文字列の取り出し shall そのノードの範囲にあたる、内容の中のバイト列の位置と長さを返す
2. The 文字列の取り出し shall 返すバイト列を、内容のバイト列と 1 バイトも違わないものにする。プレフィックス、タブ、行末記号、U+0000、不正なバイト列を、変えずに含める。
3. The 文字列の取り出し shall 原文のバイト列を複製せず、メモリを確保しない
4. The 文字列の取り出し shall コンテナと方言の種類を含む、すべての種類のノードについて、原文のバイト列を返す
5. When 文書のノード（根）が渡される, the 文字列の取り出し shall 解析する範囲の全体にあたるバイト列を返す
6. When ノードの範囲の長さが 0 である, the 文字列の取り出し shall 成功として、長さ 0 を返す
7. The 文字列の取り出し shall 返したバイト列の位置を、文書が解放されるまで、かつ利用者が内容を保っている間、使えるものにする

### Requirement 2: 論理的な文字列
**Objective:** As a 利用者, I want ノードが、コンテナの外の行頭に書かれていたとしたときの文字列を受け取りたい, so that 引用やリストの中にあるノードでも、プレフィックスとタブの規則を自分で処理せずに、原文の書き方を読める

#### Acceptance Criteria
1. When コンテナでないブロックのノード（テーマの区切り、見出し、コードブロック、HTML ブロック、段落、リンク参照定義）または CommonMark の種類のインラインのノードが渡される, the 論理的な文字列の組み立て shall そのノードの範囲のうち、行の内容にあたる部分を、原文の順につないだ文字列を作る
2. The 論理的な文字列の組み立て shall ノードの最初の行について、ノードの範囲の開始から、その行の内容の終わり（範囲がその行の中で終わるときは、範囲の終了）までを読む
3. The 論理的な文字列の組み立て shall 2 行目から後ろの行について、行の記録が「内容が始まる位置」とする位置から読み、その前にあるコンテナのプレフィックスと、ブロックの規則が除くインデントを、結果に含めない
4. When 読み始める位置が、行の記録が「内容が始まる位置」とする位置と同じで、その行の「補う空白の数」が 0 でない, the 論理的な文字列の組み立て shall その数のスペースを出し、その位置にあるタブを出さない
5. The 論理的な文字列の組み立て shall 4 にあたらないタブを、スペースに変えずに、タブのまま出す
6. The 論理的な文字列の組み立て shall ノードの範囲に含まれる行末記号のそれぞれを、その種類（LF、CR、CR と LF の組）によらず、`\n`（U+000A）1 つにする
7. The 論理的な文字列の組み立て shall 行の内容の中の、行末の空白、バックスラッシュのエスケープ、文字参照、構文の区切り（フェンス、`#`、括弧、バッククォートなど）を、書かれたまま出す
8. The 論理的な文字列の組み立て shall 遅延継続行を、印のある行と同じ決まりで読む
9. If コンテナのノードが渡される, then the 論理的な文字列の組み立て shall 「答えられない」を返す
10. When 方言の種類のインラインのノードが渡される, the 論理的な文字列の組み立て shall 1 から 8 と同じ決まりで文字列を作る
11. If 方言の種類のブロックのノードが渡される, then the 論理的な文字列の組み立て shall 「答えられない」を返す
12. When ノードの範囲が 1 つの行の中に収まり、タブの残りの桁、U+0000、不正なバイト列を含まない, the 論理的な文字列の組み立て shall 原文のバイト列（Requirement 1）と同じ文字列を作る

### Requirement 3: コードブロックの中身
**Objective:** As a 利用者, I want コードブロックのコードの部分だけを、文字列として受け取りたい, so that フェンスとインデントの規則を知らなくても、コードをそのまま使える

#### Acceptance Criteria
1. When コードブロックのノードが渡される, the 意味上の値 shall そのコードブロックのコードの各行について、行の内容と、その後ろの `\n` 1 つを、原文の順につないだ文字列を作る
2. The 意味上の値 shall フェンスのコードブロックのコードの行を、開始のフェンスの行の次の行から、閉じるフェンスの行の前の行（閉じるフェンスがなければ、そのコードブロックに属する最後の行）までとし、フェンスの行と info を結果に含めない
3. The 意味上の値 shall インデントされたコードブロックのコードの行を、そのノードの範囲にかかるすべての行とし、途中の空行を含める
4. The 意味上の値 shall コードの各行から、コンテナのプレフィックスと、ブロックの規則が除くインデント（インデントされたコードブロックの 4 桁、フェンスのコードブロックで開始のフェンスのインデントの分まで）を除き、それより後ろのインデントを残す
5. The 意味上の値 shall タブの残りの桁を、Requirement 2 の 4 と 5 と同じ決まりで扱う
6. The 意味上の値 shall コードの最後の行が、原文で行末記号を持たなくても、その後ろに `\n` を出す
7. When コードの行が 1 つもない（開始のフェンスの直後に閉じるフェンスがある、または開始のフェンスの行でコードブロックが終わる）, the 意味上の値 shall 成功として、長さ 0 の文字列を作る
8. The 意味上の値 shall コードの中のバックスラッシュと `&` を、エスケープと文字参照として解釈せず、書かれたまま出す
9. The 意味上の値 shall コードの行の、行末の空白を、書かれたまま出す

### Requirement 4: コードスパンの中身
**Objective:** As a 利用者, I want コードスパンの中身を、仕様の決まりで整えた文字列として受け取りたい, so that バッククォートの数え方と空白の規則を、自分で処理しなくて済む

#### Acceptance Criteria
1. When コードスパンのノードが渡される, the 意味上の値 shall 開く列と閉じる列のバッククォートを除いた中身から、文字列を作る
2. The 意味上の値 shall 中身に含まれる行末記号のそれぞれを、その種類によらず、スペース 1 つにする
3. The 意味上の値 shall 複数の行にわたる中身について、行の内容だけを読み、コンテナのプレフィックスと、段落の続きの行の先頭の空白を、結果に含めない
4. When 2 を適用した後の中身が、スペースで始まり、スペースで終わり、スペースでない文字を 1 つ以上含む, the 意味上の値 shall 先頭と末尾から、スペースを 1 つずつ除く
5. If 2 を適用した後の中身が、スペースだけからなる, then the 意味上の値 shall スペースを除かない
6. The 意味上の値 shall 4 で除くもののほかの空白（途中の連続するスペース、タブ、2 つ目から後ろの先頭と末尾のスペース）を、書かれたまま出す
7. The 意味上の値 shall 中身の中のバックスラッシュと `&` を、エスケープと文字参照として解釈せず、書かれたまま出す

### Requirement 5: エスケープと文字参照を文字に戻す決まり
**Objective:** As a 利用者, I want バックスラッシュのエスケープと文字参照が、どの値でも同じ決まりで文字に戻ってほしい, so that 値を得る場所によって結果が食い違わない

#### Acceptance Criteria
1. When バックスラッシュの直後に ASCII の句読点が続く, the 意味上の値 shall バックスラッシュを除き、その句読点を出す
2. If バックスラッシュの直後が ASCII の句読点でない、またはバックスラッシュが読む範囲の最後のバイトである, then the 意味上の値 shall そのバックスラッシュを、書かれたまま出す
3. When `&`、unicode-tables の実体名の参照で見つかる名前、`;` がこの順に並ぶ, the 意味上の値 shall その並びの代わりに、実体が表す 1 つまたは 2 つのコードポイントを UTF-8 で出す
4. When `&#`、1 から 7 桁の 10 進の数字、`;` がこの順に並ぶ, the 意味上の値 shall その並びの代わりに、その数を値とするコードポイントを UTF-8 で出す
5. When `&#x` または `&#X`、1 から 6 桁の 16 進の数字、`;` がこの順に並ぶ, the 意味上の値 shall その並びの代わりに、その数を値とするコードポイントを UTF-8 で出す
6. If 数値の文字参照の値が、0、サロゲート（U+D800 から U+DFFF）、または U+10FFFF より大きい, then the 意味上の値 shall その並びの代わりに、U+FFFD を出す
7. If `&` で始まる並びが、3 から 5 のどれにも合わない（`;` がない、名前が実体名の表にない、桁が多すぎる、など）, then the 意味上の値 shall その `&` を、書かれたまま出す
8. The 意味上の値 shall 実体名の大文字と小文字を区別する
9. The 意味上の値 shall 文字に戻した結果を、もう一度エスケープや文字参照として解釈しない（`&amp;lt;` は `&lt;` に、`\&amp;` は `&amp;` になる）
10. The 意味上の値 shall エスケープされたバックスラッシュの次のバイトを、新しいエスケープの始まりとして読む（`\\*` は `\*` になる）
11. The 意味上の値 shall この決まりを、テキストの部分の値（Requirement 6）、dest と title の値（Requirement 7）、info の値（Requirement 8）に、同じように適用する

### Requirement 6: テキスト、エスケープ、文字参照、オートリンクの値
**Objective:** As a 利用者, I want 子を持たないインラインのノードが表す文字を、ノードごとに受け取りたい, so that 木をたどりながら値をつなぐだけで、本文の文字列を組み立てられる

#### Acceptance Criteria
1. When テキストのノードが渡される, the 意味上の値 shall そのノードの範囲のバイト列を、書かれたまま出す（Requirement 9 の文字の扱いだけを適用する）
2. When バックスラッシュのエスケープのノードが渡される, the 意味上の値 shall エスケープされた句読点 1 文字を出す
3. When 文字参照のノードが渡される, the 意味上の値 shall Requirement 5 の 3 から 6 の決まりで、その参照が表す文字を出す
4. When オートリンクのノードが渡される, the 意味上の値 shall `<` と `>` を除いた中身を、書かれたまま出す。中身の中のバックスラッシュと `&` を、エスケープと文字参照として解釈しない。メールアドレスに `mailto:` を付けない。
5. The 意味上の値 shall テキストのノードの値で、バックスラッシュと `&` を解釈しない（inline-parser が、エスケープと文字参照にあたる部分を、別のノードにしている）
6. If この requirement と Requirement 3、4 が挙げる種類（テキスト、バックスラッシュのエスケープ、文字参照、オートリンク、コードブロック、コードスパン）のどれでもないノードが渡される, then the 意味上の値 shall ノードの値について「答えられない」を返す

### Requirement 7: dest と title の値
**Objective:** As a 利用者, I want リンク、画像、リンク参照定義のリンク先と題を、エスケープと文字参照を文字に戻した文字列として受け取りたい, so that 山括弧、引用符、エスケープの規則を知らなくても、リンク先と題をそのまま使える

#### Acceptance Criteria
1. When インラインの形式のリンクまたは画像のノードが渡され、dest が書かれている, the 意味上の値 shall dest の範囲のバイト列に、Requirement 5 の決まりを適用した文字列を作る
2. When インラインの形式のリンクまたは画像のノードが渡され、title が書かれている, the 意味上の値 shall title の範囲のバイト列に、Requirement 5 の決まりを適用した文字列を作る
3. When リンク参照定義のノードが渡される, the 意味上の値 shall その定義の dest と、書かれていれば title について、1 と 2 と同じ決まりで文字列を作る
4. The 意味上の値 shall dest と title を囲む区切り（山括弧、引用符、丸括弧）を、結果に含めない
5. If 参照の形式（完全参照、省略参照、ショートカット）のリンクまたは画像のノードについて、dest または title が求められる, then the 意味上の値 shall 「答えられない」を返す。利用者は、参照先のリンク参照定義について求める。
6. If dest または title が書かれていない, then the 意味上の値 shall 「答えられない」を返す
7. When dest または title が、書かれているが空である（`<>`、`""` など）, the 意味上の値 shall 成功として、長さ 0 の文字列を作る
8. The 意味上の値 shall 複数の行にわたる title について、行の内容だけを読み、コンテナのプレフィックスと、続きの行の先頭の空白を結果に含めず、行末記号のそれぞれを `\n` 1 つにする
9. The 意味上の値 shall dest の値に、パーセントエンコードも、その解除も、そのほかの URL の正規化も行わない
10. The 意味上の値 shall dest と title の中の、エスケープでも文字参照でもない文字（空白、対応している丸括弧など）を、書かれたまま出す
11. When 利用者が、リンクまたは画像の dest と title を得る, the 意味上の値 shall 「書かれていない」と「書かれているが空である」の区別を、syntax-tree のたどる API が返す区別と一致させる

### Requirement 8: info の値
**Objective:** As a 利用者, I want フェンスのコードブロックの info を、エスケープと文字参照を文字に戻した文字列として受け取りたい, so that 言語の名前などを、原文の書き方によらずに比べられる

#### Acceptance Criteria
1. When フェンスのコードブロックのノードが渡され、info が書かれている, the 意味上の値 shall info の範囲のバイト列に、Requirement 5 の決まりを適用した文字列を作る
2. The 意味上の値 shall info の全体を 1 つの文字列として返し、最初の語とそのほかの部分に分けない
3. The 意味上の値 shall info の途中の空白を、書かれたまま出す（前後の空白は、info の範囲に含まれていない）
4. If info が書かれていない、またはノードがフェンスのコードブロックでない, then the 意味上の値 shall 「答えられない」を返す

### Requirement 9: 文字の扱い
**Objective:** As a 利用者, I want 論理的な文字列と意味上の値が、どの入力でも、そのまま文字列として扱えるものであってほしい, so that 信頼できない入力から得た値を、検査し直さずに使える

#### Acceptance Criteria
1. The 文字列の取り出し shall 論理的な文字列と意味上の値で、原文の U+0000 のそれぞれを、U+FFFD にする
2. While 不正な UTF-8 の扱いが「置き換えて続ける」である, the 文字列の取り出し shall 論理的な文字列と意味上の値で、不正なバイト列の極大の部分 1 つを、U+FFFD 1 文字にする。極大の部分の区切り方は、解析と同じにする。
3. The 文字列の取り出し shall 論理的な文字列と意味上の値を、U+0000 を含まない、正しい UTF-8 にする
4. The 文字列の取り出し shall 1 と 2 の置き換えを、原文のバイト列の取り出し（Requirement 1）には適用しない
5. When ノードの範囲が、U+0000 も不正なバイト列も含まない, the 文字列の取り出し shall 不正な UTF-8 の扱いのどちらの設定で解析した文書でも、同じ結果を作る
6. The 文字列の取り出し shall 1、2 と Requirement 5 の 6 のほかに、文字を置き換えない。ASCII の外の文字、制御文字、U+FEFF を、書かれたまま出す。
7. The 文字列の取り出し shall Unicode の正規化、大文字と小文字の変換、空白の畳み込みを行わない

### Requirement 10: 結果の受け渡し
**Objective:** As a 利用者, I want 結果を、自分のバッファで受け取るか、確保された文字列で受け取るかを選びたい, so that メモリの確保を自分で管理する場合も、手軽に使う場合も、同じ値を得られる

#### Acceptance Criteria
1. The 文字列の取り出し shall 論理的な文字列と、意味上の値のそれぞれについて、呼び出す側が渡すバッファに書く方法と、確保関数で作った文字列を返す方法の、両方を用意する
2. The 文字列の取り出し shall 2 つの方法で、同じノードについて、同じバイト列を結果とする
3. When バッファとその大きさが渡され、結果がバッファに収まる, the 文字列の取り出し shall 結果をバッファに書き、結果の長さ（バイト数）を伝える
4. If 結果がバッファに収まらない, then the 文字列の取り出し shall バッファの大きさを超えて書かず、収まらなかったことと、必要な大きさを伝える
5. When バッファが渡されず、大きさだけが尋ねられる, the 文字列の取り出し shall 何も書かずに、必要な大きさを伝える
6. When 利用者が、伝えられた必要な大きさのバッファを渡して、同じ文書の同じノードについて呼び直す, the 文字列の取り出し shall 結果をバッファに書いて成功する
7. The 文字列の取り出し shall バッファに書く方法で、メモリを確保しない
8. When 確保関数で作る方法が呼ばれる, the 文字列の取り出し shall 文書を作ったときの設定の確保関数で、結果の文字列を確保し、その文字列と長さを返す
9. The 文字列の取り出し shall 確保関数で作った文字列を、文書とは別に、利用者が解放するものとし、文書を作ったときの設定の確保関数を通して解放する手段を用意する
10. The 文字列の取り出し shall 確保関数で作った文字列を、長さ 0 のときも含めて、終端の NUL を持つ文字列とする
11. If 確保関数で作る方法で、確保が失敗する, then the 文字列の取り出し shall メモリ不足を返し、確保したものを残さず、文字列を返さない
12. If 結果の大きさの計算が、表せる範囲を超える, then the 文字列の取り出し shall 資源の上限の超過を返し、何も書かない
13. The 文字列の取り出し shall どちらの方法でも、文書と内容のバイト列を変更しない

### Requirement 11: 答えられない呼び出しと失敗
**Objective:** As a 利用者, I want 求めたものがないときと、失敗したときを、決まった形で区別して受け取りたい, so that 種類を確かめ忘れた呼び出しでも、未定義の動作にならず、原因を見分けられる

#### Acceptance Criteria
1. If 文書が「ない」ことを表す値である、ノードの ID がその文書のノードを指さない、または結果を受け取る場所が「ない」ことを表す値である, then the 文字列の取り出し shall 「答えられない」を返し、未定義の動作を起こさない
2. If ノードが、求められたものを持つ種類（および書き方、形式）でない, then the 文字列の取り出し shall 「答えられない」を返す
3. If 求められた部分（dest、title、info）が書かれていない, then the 文字列の取り出し shall 「答えられない」を返す
4. When 「答えられない」を返す, the 文字列の取り出し shall バッファと、結果を受け取る場所を変えず、メモリを確保しない
5. The 文字列の取り出し shall 「答えられない」、バッファに収まらなかったこと、メモリ不足、資源の上限の超過、成功を、呼び出す側が互いに区別できる形で返す
6. The 文字列の取り出し shall 長さ 0 の結果を、成功として返し、「答えられない」と区別できるようにする
7. The 文字列の取り出し shall 解析の入口が成功として返したどの文書の、どのノードについても、成功、「答えられない」、バッファに収まらなかったこと、メモリ不足、資源の上限の超過のどれかで戻り、Markdown の中身を理由に失敗しない
8. The 文字列の取り出し shall 失敗を戻り値で伝え、プログラムを終了させない

### Requirement 12: 文字列の取り出しに共通の性質
**Objective:** As a 利用者, I want 文字列の取り出しが、どの入力と設定でも、製品が保証する性質を保ってほしい, so that 信頼できない入力や、並行する処理でも安心して使える

#### Acceptance Criteria
1. The 文字列の取り出し shall 1 回の呼び出しの時間を、読む範囲の長さにほぼ比例させる。文書の大きさ、行の数、ノードの数、入れ子の深さによらない。多数の `&` とバックスラッシュ、多数の短い行、深いコンテナの中の範囲でも同じである。
2. The 文字列の取り出し shall 原文のバイト列の取り出し（Requirement 1）を、範囲の長さによらない時間で行う
3. The 文字列の取り出し shall 再帰を使わず、呼び出しのスタックを一定の量しか使わない
4. The 文字列の取り出し shall グローバルな変数と静的な可変の状態を持たず、I/O を行わない
5. The 文字列の取り出し shall 文書に状態を残さず、同じ文書の同じノードについて、何度呼ばれても同じ結果を返す
6. While 複数のスレッドが、変更されなくなった同じ文書について、文字列の取り出しとたどる API を同時に呼んでいる, the 文字列の取り出し shall 互いに影響せずに正しい結果を返す。確保関数で作る方法では、設定の確保関数が同時に呼ばれてよいことを前提とする。
7. The 文字列の取り出し shall 構文の規則を設定で変えられるようにしない（タブ幅 4、コードスパンの空白の決まりなどは固定である）
8. The 文字列の取り出し shall 公開ヘッダに宣言された公開の関数とし、名前を `amark_` で始め、構造体のレイアウトを公開しない
9. The 公開ヘッダ shall この spec の宣言を加えた後も、C99 として対象のすべてのコンパイラで警告なしに取り込め、C++ からも取り込める
10. Where 動的ライブラリを作る構成である, the ビルド構成 shall この spec が公開する関数だけを公開シンボルに加え、公開シンボルの一覧をそれに合わせる
11. The 文字列の取り出し shall 解析の結果（ノードの ID、種類、範囲、属性、診断）を変えない

### Requirement 13: 単体テスト
**Objective:** As a Amark の開発者, I want 文字列の取り出しの正しさを、この spec のテストだけで確かめたい, so that spec-conformance が、値を信頼して HTML を作れる

#### Acceptance Criteria
1. The 単体テスト shall spec.txt（CommonMark 0.31.2）の次の節の例について、この spec の値（コードブロックとコードスパンの中身、テキストとエスケープと文字参照の値、dest、title、info）が、仕様の期待する結果（HTML のエスケープと URL のパーセントエンコードを施す前の文字列）と一致することを確かめる。Tabs、Backslash escapes、Entity and numeric character references、Indented code blocks、Fenced code blocks、Link reference definitions、Code spans、Links、Images、Autolinks。
2. The 単体テスト shall 論理的な文字列について、次の場合を確かめる。ブロッククォートとリスト項目の中のノード、入れ子のコンテナ、遅延継続行、タブの残りの桁が 1 から 3 の場合、3 種類の行末記号、行末記号のない最後の行、複数の行にわたるインラインのノード。
3. The 単体テスト shall コンテナでないブロックの種類と、インラインの種類のそれぞれについて、論理的な文字列を確かめ、コンテナのノードが「答えられない」になることを確かめる
4. The 単体テスト shall すべての種類のノードについて、原文のバイト列が、内容の中のその範囲と同じであることを確かめ、文書のノードの原文のバイト列が、解析する範囲の全体であることを確かめる
5. The 単体テスト shall エスケープと文字参照を文字に戻す決まりの、各条件とその境の値を確かめる。すべての ASCII の句読点、句読点でない文字の前のバックスラッシュ、末尾のバックスラッシュ、2 つのコードポイントを表す実体名、表にない名前、`;` のない並び、桁の数の境（10 進の 7 桁と 8 桁、16 進の 6 桁と 7 桁）、値が 0、サロゲート、U+10FFFF、U+110000 の数値の文字参照。
6. The 単体テスト shall dest と title について、「書かれていない」「書かれているが空である」「書かれている」の 3 つの場合と、参照の形式のリンクで「答えられない」になること、参照先の定義から値を得られることを確かめる
7. The 単体テスト shall U+0000 と、不正な UTF-8 の扱いの 2 つの設定について、論理的な文字列と意味上の値が正しい UTF-8 になること、原文のバイト列が変わらないことを確かめる
8. The 単体テスト shall 結果の受け渡しについて、次のことを確かめる。大きさだけを尋ねる呼び出し。必要な大きさより 1 小さいバッファと、ちょうどの大きさのバッファ。バッファの大きさを超えて書かれないこと。2 つの方法の結果が一致すること。長さ 0 の結果。
9. The 単体テスト shall 答えられない呼び出し（Requirement 11 の 1 から 3 の各条件）で、バッファと結果を受け取る場所が変わらないことを確かめる
10. When 単体テストが、確保と解放を数える確保関数を使い、確保の失敗を各回に注入して、確保関数で作る方法を実行する, the 文字列の取り出し shall 成功した場合は文字列と文書の解放の後に、失敗した場合は戻った時点と文書の解放の後に、解放されないメモリを残さない
11. The 単体テスト shall バッファに書く方法と、原文のバイト列の取り出しが、確保関数を 1 回も呼ばないことを確かめる
12. The 単体テスト shall 多数の文字参照とバックスラッシュを含む範囲、多数の行にわたる範囲、入れ子が 10 万段のブロッククォートの中のノードについて、文字列の取り出しが、読む範囲の長さにほぼ比例する時間で、スタックを使い切らずに終わることを確かめる
13. The 単体テスト shall 公開 API だけを使うテストで、解析の入口から得た文書をたどり、各ノードの値を得られることを確かめる
14. The 単体テスト shall 文字列の取り出しの前後で、内容のバイト列と、木（ノードの ID、種類、範囲、属性）が変わらないことを確かめる
