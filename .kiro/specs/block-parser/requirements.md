# Requirements Document

## Project Description (Input)
**誰が困っているか**：amark を自分のプロジェクトに組み込む利用者と、block-parser の結果を使う下流の spec（inline-parser、source-text、dialect-extension）の開発者。

**現在の状況**：syntax-tree（データモデルと木を作る内部 API）と unicode-tables（case folding）はできているが、Markdown の入力から木を得る手段がない。CommonMark のブロック構造（コンテナと遅延継続行、リーフの開始と終了、タブの桁）を、仕様どおりに、入力の長さにほぼ比例する時間で、再帰を使わずに解析する部分が要る。しかも原文を複製せず、範囲として残さなければならない。

**何を変えるか**：
- 解析の入口となる公開 API を用意する。入力のバイト列と設定を受け取り、文書かエラーを返す。設定（範囲 `[start, end)`、UTF-8 の扱い（エラーか U+FFFD への置換か）、資源の上限、確保関数、ファイル名）を検査して適用する。失敗したときは確保したものをすべて解放し、部分的な木を返さない。
- 行を分割し、行末記号（LF、CR、CRLF）は入力のまま保つ。タブを桁で扱い（タブ幅 4）、タブの一部だけを消費した場合の残りの桁を記録する。
- コンテナ（ブロッククォート、リスト項目）と遅延継続行、リーフ（テーマの区切り、ATX 見出し、Setext 見出し、インデントされたコードブロック、フェンスのコードブロック、7 種類の HTML ブロック、段落、空行）を解析し、リストのタイトとルーズを判定する。
- リンク参照定義を解析し、ラベルを正規化し（case folding、空白の畳み込み、999 文字の上限）、正規化したラベルをキーとする定義の表をアリーナに作る。
- 行ごとのプレフィックスの情報を記録し（source-text が使う）、インライン解析に渡す内容の範囲を用意する（inline-parser が使う）。
- 資源の上限（入れ子の深さ、ノードの数、入力の大きさ）を検査する。
- 方言の差し込み口（ブロックの開始と継続）の位置を設計の段階で確保する。

**方針**：cmark と同じく、行ごとに開いているコンテナとの一致を確かめ、新しいブロックを開始し、内容を追加する。開いているブロックは明示的なスタックで管理し、リンク参照定義は段落を閉じるときに取り出す。

**範囲外**：インライン構造（inline-parser）、文字列の組み立て（source-text）、差し込み口の公開 API と結果の検査（dialect-extension）、spec.txt 全体を通すことの確認（spec-conformance。ただしブロックに関わる例はこの spec の単体テストで確かめる）、BOM の除去とフロントマター（利用者が範囲で除く）、規則を設定で変えること。

**制約**：再帰を使わない。時間は入力の長さにほぼ比例する。グローバルな状態を持たない。対象は CommonMark 0.31.2。上流は syntax-tree、unicode-tables、project-foundation。

## Introduction
block-parser は、amark の解析の入口と、CommonMark 0.31.2 のブロック構造の解析を作る。syntax-tree と unicode-tables まででは、利用者は Markdown から木を得られない。この spec で、利用者は内容と設定を渡して文書を受け取れるようになる。

この spec は、次の 5 つを用意する。

1. **解析の入口**：内容と設定を受け取り、文書かエラーを返す公開 API。設定（解析する範囲、UTF-8 の扱い、資源の上限、確保関数、ファイル名）を検査して適用する。
2. **ブロックの解析**：コンテナ（ブロッククォート、リスト、リスト項目）とリーフ（テーマの区切り、見出し、コードブロック、HTML ブロック、段落）を認識し、範囲と属性を持つノードにする。
3. **リンク参照定義**：定義を認識してノードにし、ラベルを正規化して、定義の表を作る。
4. **行の記録**：各行について、コンテナのプレフィックスとインデントを除いた「内容が始まる位置」と、タブの残りの桁を記録する。
5. **インラインの解析に渡す内容**：段落と見出しについて、インラインとして解析する部分の範囲を用意する。

この文書で「利用者」は amark を自分のプロジェクトに組み込む人、「下流の開発者」は inline-parser、source-text、dialect-extension を開発する人を指す。「内容」は利用者が渡す入力のバイト列の全体、「解析する範囲」はそのうち設定で指定した `[start, end)` を指す。「文書」は 1 回の解析の結果（木と診断）をまとめて持つものを指す。「行末記号」は LF、後ろに LF が続かない CR、CR と LF の組を指す。「空白」は、断らない限りスペース（U+0020）とタブ（U+0009）を指す。「桁」は、タブを幅 4 のタブ位置まで進むものとして数えた、行の中の位置を指す。「プレフィックス」は、行のうち、コンテナの印（ブロッククォートの `>` と、リスト項目の印または字下げ）にあたる部分を指す。「深さ」は、文書のノードを 0 とし、子を親より 1 大きくした数を指す。

## Boundary Context
- **In scope**:
  - 解析の入口となる公開 API と、設定の適用（範囲、UTF-8 の扱い、資源の上限、確保関数、ファイル名）
  - 行の分割と、タブの桁の扱い
  - コンテナとリーフの認識、遅延継続行、リストのタイトとルーズの判定
  - 各ブロックのノードの範囲と属性を定めること
  - リンク参照定義の認識、ラベルの正規化、定義の表と、ラベルから定義を引く内部の手段
  - 行の記録と、インラインの解析に渡す内容の範囲（どちらも内部の手段）
  - 方言の規則を呼ぶ箇所（ブロックの開始と継続）を確保すること
  - 上の各項目の単体テスト。spec.txt のブロックに関わる節の例を含む。
- **Out of scope**:
  - インラインの構造（inline-parser）。この spec が終わった時点では、解析の入口が返す文書は、ブロックのノードだけを持つ。
  - 範囲から文字列を組み立てること、エスケープと文字参照を文字に戻すこと、dest・title・info の意味上の値を得ること（source-text）
  - 方言を定義して規則を登録する公開 API、規則を呼び出す契約、規則が返した結果の検査と診断（dialect-extension）
  - spec.txt の全例を HTML と比べて確かめること、全体の性質（病的な入力、原文の復元、並行性）の総合のテスト（spec-conformance）
  - BOM の除去と、フロントマターなど本文の外側の解析。利用者が、解析する範囲の指定で除く。BOM は除かれず、ほかの文字と同じに扱われる。
  - 構文の規則を設定で変えること（タブ幅 4、ラベルの上限 999 文字などは固定である）
  - 内容を読み込むこと（I/O）
- **Adjacent expectations**:
  - syntax-tree の内部 API だけで木を作り、設定の検査は syntax-tree の関数に任せる。この spec は、検査を通った設定を適用する。
  - unicode-tables の case folding を、ラベルの正規化に使う。project-foundation の部品（アリーナ、配列、行の索引、UTF-8 の検査）を使う。
  - 利用者は、文書を解放するまで、内容のバイト列を変更も解放もしない。文書は内容を複製せず、範囲で指すだけである。
  - inline-parser は、この spec の解析の入口に、インラインの解析を足す。そのとき、この spec が用意する「インラインの解析に渡す内容」「定義の表」「行の記録」を使う。入れ子の深さとノードの数の上限は、同じ数え方でインラインのノードにも適用する。
  - inline-parser と source-text は、「置き換えて続ける」設定のとき、内容の中の不正なバイト列を自分で U+FFFD として読む。この spec は、置き換えた写しを作らない。
  - source-text は、行の記録から論理的な文字列を組み立てる。この spec は記録を作るだけで、文字列は作らない。
  - dialect-extension は、この spec が確保した箇所に、方言の規則の呼び出しを足す。この spec の時点では、設定の方言の項目は解析の結果に影響しない。

## Requirements

### Requirement 1: 解析の入口
**Objective:** As a 利用者, I want 内容と設定を渡して文書を受け取りたい, so that 1 回の呼び出しで Markdown の構造を得られる

#### Acceptance Criteria
1. When 内容（バイト列とその長さ）と設定が渡される, the 解析の入口 shall 解析する範囲を解析し、成功を返して、文書を呼び出した側に渡す
2. When 設定が省略される, the 解析の入口 shall 既定の設定（CommonMark だけ、内容の全体、標準の確保関数、不正な UTF-8 はエラー、資源の上限なし）で解析する
3. The 解析の入口 shall UTF-8 として正しい解析する範囲を、その中身にかかわらず文書にし、Markdown の構文を理由に失敗しない
4. When 解析する範囲が空である, the 解析の入口 shall 成功を返し、文書のノードだけを持つ文書を渡す
5. When 長さが 0 の内容が渡される, the 解析の入口 shall 内容のバイト列が「ない」ことを表す値であっても、成功を返す
6. If 長さが 0 でないのに、内容のバイト列が「ない」ことを表す値である, then the 解析の入口 shall 入力の制約違反を返し、未定義の動作を起こさない
7. The 解析の入口 shall 文書のノードの範囲を、解析する範囲と同じにする
8. The 解析の入口 shall 成功して返した文書を、syntax-tree のたどる API と解放の API でそのまま使えるものにし、その木を syntax-tree の不変条件がすべて成り立つものにする
9. The 解析の入口 shall 内容のバイト列を変更せず、複製しない
10. The 解析の入口 shall 解析の結果を、syntax-tree のエラーの種類（成功、入力の制約違反、設定の誤り、資源の上限の超過、メモリ不足）のどれか 1 つで返す
11. The 解析の入口 shall 公開ヘッダに宣言された公開の関数とし、名前を `amark_` で始める

### Requirement 2: 設定の適用
**Objective:** As a 利用者, I want 設定した範囲、UTF-8 の扱い、確保関数、ファイル名が解析にそのまま反映されてほしい, so that 本文の外側を除いたり、信頼できない入力を扱ったりできる

#### Acceptance Criteria
1. If syntax-tree の設定の検査が設定の誤りを返す設定が渡される, then the 解析の入口 shall 設定の誤りを返し、メモリを確保しない
2. The 解析の入口 shall 解析する範囲の外のバイトを、Markdown として解釈しない
3. The 解析の入口 shall 解析する範囲の先頭を行の先頭（桁 0）として、範囲の末尾を最後の行の終わりとして扱う
4. The 解析の入口 shall ノードと属性の範囲を、内容の先頭から数えたオフセットで表し、行番号を、内容の最初の行を 1 として数える。解析する範囲の開始が 0 でなくても同じである。
5. The 解析の入口 shall UTF-8 の検査を、解析する範囲のバイト列だけに対して行い、範囲の外のバイトが不正でも失敗しない
6. If 不正な UTF-8 の扱いが「エラーにする」で、解析する範囲に不正な UTF-8 がある, then the 解析の入口 shall 入力の制約違反を返す
7. When 不正な UTF-8 の扱いが「置き換えて続ける」で、解析する範囲に不正な UTF-8 がある, the 解析の入口 shall 不正なバイト列の極大の部分 1 つを U+FFFD 1 文字として扱って解析を続け、成功を返す
8. While 不正な UTF-8 の扱いが「置き換えて続ける」である, the 解析の入口 shall すべての範囲を、利用者が渡した内容のオフセットで表し、置き換えた写しを作らない
9. When 解析する範囲が UTF-8 として正しい, the 解析の入口 shall 不正な UTF-8 の扱いのどちらの設定でも、同じ木を作る
10. The 解析の入口 shall 解析に必要なメモリを、設定の確保関数だけから得る
11. Where 設定でファイル名が指定されている, the 解析の入口 shall 文書の診断がそのファイル名を返すようにする

### Requirement 3: 資源の上限
**Objective:** As a 利用者, I want 信頼できない入力が使う資源を、設定した上限で抑えたい, so that 悪意のある入力で、メモリや時間を使い切られない

#### Acceptance Criteria
1. If 入力の大きさの上限が指定されていて、内容の全体の長さがそれを超える, then the 解析の入口 shall 資源の上限の超過を返し、メモリを確保しない
2. When 内容の全体の長さが入力の大きさの上限と等しい, the 解析の入口 shall 上限を理由に失敗しない
3. If 入れ子の深さの上限が指定されていて、深さがそれを超えるノードが要る, then the 解析の入口 shall 資源の上限の超過を返す
4. When すべてのノードの深さが入れ子の深さの上限以下である, the 解析の入口 shall 上限を理由に失敗しない
5. If ノードの数の上限が指定されていて、解析の途中で作ったノードの数（文書のノードを含み、途中で取り除いたものも数える）がそれを超える, then the 解析の入口 shall 資源の上限の超過を返す
6. While ノードの数の上限が指定されている, the 解析の入口 shall 成功して返す文書のノードの数を、上限以下にする
7. While 資源の上限のある項目が「上限なし」である, the 解析の入口 shall その項目を理由に失敗しない
8. If 木が表せるノードの数を超える、または大きさの計算があふれる, then the 解析の入口 shall 資源の上限の超過を返す
9. If 設定の誤りと、入力の大きさの上限の超過と、不正な UTF-8 のうち複数が同時に当てはまる, then the 解析の入口 shall 設定の誤り、入力の大きさの上限の超過、入力の制約違反の順で、最初に当てはまるものを返す

### Requirement 4: 失敗の扱い
**Objective:** As a 利用者, I want 失敗したときに何も残らないでほしい, so that 後始末を自分で書かなくて済み、壊れた木を誤って使うことがない

#### Acceptance Criteria
1. If 解析が失敗する, then the 解析の入口 shall その解析のために確保したメモリをすべて解放してから戻る
2. If 解析が失敗する, then the 解析の入口 shall 文書を渡さず、文書を受け取る場所に「文書がない」ことを表す値を入れる
3. If 確保関数が失敗する, then the 解析の入口 shall メモリ不足を返す
4. The 解析の入口 shall 失敗を戻り値で伝え、`abort`、`exit`、`longjmp` を使わない
5. When 解析が成功する, the 解析の入口 shall 解析の途中だけで使う作業用のメモリを解放してから戻り、残りのメモリを文書の解放ですべて解放できるようにする

### Requirement 5: 行とタブ
**Objective:** As a 利用者, I want 行末記号とタブが入力のまま保たれ、仕様どおりに解釈されてほしい, so that 行末記号やタブの使い方が混ざった文書でも、範囲が原文と一致する

#### Acceptance Criteria
1. The ブロックの解析 shall 解析する範囲を、行末記号（LF、後ろに LF が続かない CR、CR と LF の組）で行に分ける
2. When 解析する範囲が行末記号で終わらない, the ブロックの解析 shall 最後の行を、行末記号のない行として扱う
3. The ブロックの解析 shall 行末記号の種類が混ざった内容を、それぞれの行末記号のまま扱い、どの範囲も行末記号の組（CR と LF）の途中で区切らない
4. The ブロックの解析 shall ブロックの構造を決めるときに、タブを、幅 4 のタブ位置まで進む空白として扱う。タブ位置は、行の先頭からの桁で数える。
5. When プレフィックスまたはインデントが、タブの桁の一部だけを消費する, the ブロックの解析 shall 残りの桁を、後に続く内容のインデントとして数える
6. The ブロックの解析 shall U+0000 と、U+FFFD として扱う不正なバイト列を、空白でも行末記号でもない文字として扱う
7. The ブロックの解析 shall スペース、タブ、行末記号のほかの文字（Unicode の空白を含む）を、インデントと空行の判定で空白として扱わない

### Requirement 6: ブロックのノードの範囲
**Objective:** As a 利用者, I want 各ブロックのノードの範囲が、決まった規則で原文に対応してほしい, so that 範囲を使って原文を調べたり、一部だけを置き換えたりできる

#### Acceptance Criteria
1. The ブロックの解析 shall ブロックのノードの範囲の開始を、そのブロックの最初の行で、外側のコンテナのプレフィックスとインデントの後の、そのブロックの最初のバイトとする
2. The ブロックの解析 shall ブロックのノードの範囲の終了を、そのブロックに属する最後の行の、行末記号の直前とする。行末の空白は範囲に含む。ただし、リーフのブロックに属する最後の行の長さが 0（行の内容の終わりが行の開始と同じ）であるときは、その行の行末記号の直後とする（解析する範囲の終わりを越えない。範囲が CR と LF の間で終わるときは CR の直後）。
3. The ブロックの解析 shall ブロッククォートの範囲を、最初の `>` から始め、そのブロッククォートの `>` を持つ行と遅延継続行のうち、最後の行で終える
4. The ブロックの解析 shall リスト項目の範囲を、項目の印の最初のバイトから始め、印のある行の終わりと、最後の子の終了のうち、後ろのほうで終える。子の範囲に含まれない後ろの空行は含まない。
5. The ブロックの解析 shall リストの範囲を、最初の項目の開始から、最後の項目の終了までとする
6. The ブロックの解析 shall インデントされたコードブロックの範囲を、最初の行の、インデントの 4 桁の後のバイトから始め、最後の空行でない行で終える。タブがインデントの 4 桁の境をまたぐときは、そのタブから始める。
7. The ブロックの解析 shall フェンスのコードブロックの範囲を、開始のフェンスの最初のバイトから始め、閉じるフェンスがあればその行で、なければそのコードブロックに属する最後の行で終える。終わりの位置は 2 による（最後の行の長さが 0 なら、その行の行末記号の直後）。
8. The ブロックの解析 shall HTML ブロックの範囲を、最初の行の、外側のコンテナのプレフィックスの後のバイト（インデントを含む）から始め、そのブロックに属する最後の行で終える。終わりの位置は 2 による（最後の行の長さが 0 なら、その行の行末記号の直後）。
9. The ブロックの解析 shall Setext 見出しの範囲に、下線の行を含める
10. The ブロックの解析 shall 段落の範囲を、最初の行の内容の最初の空白でないバイトから始める
11. The ブロックの解析 shall 空行について、ノードを作らない
12. The ブロックの解析 shall 兄弟のブロックのノードを、原文の順に、重ならないように並べる

### Requirement 7: ブロッククォートと遅延継続行
**Objective:** As a 利用者, I want ブロッククォートが仕様どおりに認識されてほしい, so that 引用の入れ子と、印を省いた続きの行を正しく扱える

#### Acceptance Criteria
1. When CommonMark 0.31.2 のブロッククォートの印の規則（5.1 節）に合う行が現れる, the ブロックの解析 shall ブロッククォートのノードを作り、印の後の内容を、その子のブロックとして解析する
2. While ブロッククォートが開いている, when 次の行がその印を持つ, the ブロックの解析 shall その行の印の後の内容を、同じブロッククォートの続きとして解析する
3. While 開いているコンテナの中で段落が続いている, when 次の行が、コンテナの印を欠くが段落の続きになる行（遅延継続行）である, the ブロックの解析 shall その行を、その段落の続きとして、段落とそれを含むコンテナの範囲に含める
4. When 遅延継続行の条件に合わず、開いているコンテナの印も持たない行が現れる, the ブロックの解析 shall 印の合わないコンテナと、その中のブロックを閉じる
5. The ブロックの解析 shall ブロッククォートの入れ子を、深さによらず、同じ規則で扱う

### Requirement 8: リストとリスト項目
**Objective:** As a 利用者, I want リストとその項目が、種類・番号・詰まり方とともに得られてほしい, so that リストの構造を、原文を読み直さずに扱える

#### Acceptance Criteria
1. When CommonMark 0.31.2 のリスト項目の規則（5.2 節）に合う、箇条書きの印（`-`、`+`、`*`）または番号付きの印（1 から 9 桁の数字と、`.` か `)`）が現れる, the ブロックの解析 shall リスト項目のノードを作り、印の後の内容を、その子のブロックとして解析する
2. The ブロックの解析 shall リスト項目の続きの行を、仕様の定める内容の字下げ（印の幅と、その後の空白から決まる桁）で判定する
3. When 印の後が空白だけの行でリスト項目が始まる, the ブロックの解析 shall 子のないリスト項目を作れるようにし、仕様の定める規則（空の項目は段落を中断しない、最初の行が空の項目は空行 1 行までしか続かない）に従う
4. While 段落が続いている, when 番号付きの印が現れる, the ブロックの解析 shall 番号が 1 で、項目が空でないときに限って、段落を中断してリストを始める
5. The ブロックの解析 shall 連続するリスト項目のうち、同じ種類の印（箇条書きなら同じ文字、番号付きなら同じ区切りの文字）を持つものを、1 つのリストのノードの子にまとめる
6. When 印の種類が前の項目と異なるリスト項目が現れる, the ブロックの解析 shall 新しいリストのノードを始める
7. The ブロックの解析 shall リストのノードに、箇条書きか番号付きかを設定する。箇条書きなら記号の文字を、番号付きなら最初の項目の番号と区切りの文字を設定する。
8. The ブロックの解析 shall リストのタイトとルーズを、CommonMark 0.31.2 の定義（5.3 節）に従って判定し、リストのノードに設定する。項目の間に空行があるとき、または項目の直接の子のブロックの間に空行があるときに、ルーズとする。
9. The ブロックの解析 shall 入れ子のリストの中の空行だけを理由に、外側のリストをルーズにしない
10. The ブロックの解析 shall リストとリスト項目の入れ子を、深さによらず、同じ規則で扱う

### Requirement 9: テーマの区切りと見出し
**Objective:** As a 利用者, I want テーマの区切りと 2 つの書き方の見出しが、レベルとともに得られてほしい, so that 文書の章立てを取り出せる

#### Acceptance Criteria
1. When CommonMark 0.31.2 のテーマの区切りの規則（4.1 節）に合う行が現れる, the ブロックの解析 shall テーマの区切りのノードを作る
2. When CommonMark 0.31.2 の ATX 見出しの規則（4.2 節）に合う行が現れる, the ブロックの解析 shall 見出しのノードを作り、レベル（`#` の数、1 から 6）と、書き方が ATX であることを設定する
3. While 段落が続いている, when CommonMark 0.31.2 の Setext 見出しの下線の規則（4.3 節）に合う行が現れる, the ブロックの解析 shall その段落を見出しのノードにし、レベル（`=` なら 1、`-` なら 2）と、書き方が Setext であることを設定する
4. When 行が、Setext 見出しの下線と、テーマの区切りまたはリスト項目の両方に解釈できる, the ブロックの解析 shall 仕様の定める優先の順に従って、どれか 1 つに決める
5. If 下線の行の前の段落が、リンク参照定義だけでできていて、段落の内容が残らない, then the ブロックの解析 shall 見出しを作らず、下線の行を、仕様に従って別のブロックとして解析する
6. The ブロックの解析 shall 遅延継続行を、Setext 見出しの下線として扱わない

### Requirement 10: コードブロック
**Objective:** As a 利用者, I want 2 つの書き方のコードブロックが、フェンスと info とともに得られてほしい, so that コードの部分を、ほかの内容と区別して扱える

#### Acceptance Criteria
1. When CommonMark 0.31.2 のインデントされたコードブロックの規則（4.4 節）に合う行が現れる, the ブロックの解析 shall コードブロックのノードを作り、書き方がインデントであることを設定する
2. The ブロックの解析 shall インデントされたコードブロックで、段落を中断しない。段落の続きになる行は、4 桁以上インデントされていても段落に含める。
3. The ブロックの解析 shall インデントされたコードブロックに、途中の空行を含め、前後の空行を含めない
4. When CommonMark 0.31.2 のフェンスのコードブロックの規則（4.5 節）に合う開始のフェンスが現れる, the ブロックの解析 shall コードブロックのノードを作り、書き方がフェンスであること、フェンスの文字（`` ` `` か `~`）、開始のフェンスの長さを設定する
5. Where 開始のフェンスの後に info がある, the ブロックの解析 shall info の範囲を、前後の空白を除いた部分として設定する
6. If 開始のフェンスの後が空白だけである, then the ブロックの解析 shall info を「書かれていない」として設定する
7. When 開始のフェンスと同じ文字で、長さが開始のフェンス以上の、閉じるフェンスの規則に合う行が現れる, the ブロックの解析 shall そのコードブロックを閉じる
8. If 閉じるフェンスが現れない, then the ブロックの解析 shall コードブロックを、それを含むコンテナの終わりか、解析する範囲の終わりで閉じる
9. The ブロックの解析 shall コードブロックの中の行を、ほかのブロックとして解釈せず、コードブロックのノードに子を作らない

### Requirement 11: HTML ブロック
**Objective:** As a 利用者, I want HTML ブロックが、仕様の 7 種類の条件どおりに得られてほしい, so that 生の HTML の部分を、Markdown として解釈せずに扱える

#### Acceptance Criteria
1. When CommonMark 0.31.2 の HTML ブロックの 7 種類の開始条件（4.6 節）のどれかに合う行が現れる, the ブロックの解析 shall HTML ブロックのノードを作る
2. The ブロックの解析 shall HTML ブロックを、その開始条件に対応する終了条件に合う行（その行を含む）で閉じる
3. If 終了条件に合う行が現れない, then the ブロックの解析 shall HTML ブロックを、それを含むコンテナの終わりか、解析する範囲の終わりで閉じる
4. The ブロックの解析 shall 7 番目の開始条件で、段落を中断しない
5. The ブロックの解析 shall 開始条件のタグの名前を、ASCII の大文字と小文字を区別せずに比べる
6. The ブロックの解析 shall HTML ブロックの中の行を、ほかのブロックとして解釈せず、HTML ブロックのノードに子を作らない

### Requirement 12: 段落
**Objective:** As a 利用者, I want ほかのどのブロックにもならない行が、段落として得られてほしい, so that 本文をまとまりごとに扱える

#### Acceptance Criteria
1. When ほかのブロックの開始にならない、空行でない行が現れる, the ブロックの解析 shall 段落のノードを作る
2. While 段落が続いている, when 段落を中断するブロックの開始にならない、空行でない行が現れる, the ブロックの解析 shall その行を段落の続きとする
3. When 段落の後に空行が現れる, the ブロックの解析 shall 段落を閉じる
4. The ブロックの解析 shall 段落を中断できるブロックと、できないブロックを、CommonMark 0.31.2 の規則に従って区別する
5. The ブロックの解析 shall 段落のノードに、ブロックの子を作らない

### Requirement 13: リンク参照定義
**Objective:** As a 利用者, I want リンク参照定義が、ラベル・dest・title の範囲とともにノードとして得られてほしい, so that 定義の位置と中身を、原文を読み直さずに扱える

#### Acceptance Criteria
1. When 段落が閉じる, the ブロックの解析 shall 段落の先頭から、CommonMark 0.31.2 のリンク参照定義の規則（4.7 節）に合う定義を、合わなくなるまで順に取り出す
2. The ブロックの解析 shall 取り出した定義のそれぞれを、リンク参照定義のノードにし、段落があった位置に、原文の順に置く
3. When 定義を取り出した後に段落の内容が残る, the ブロックの解析 shall 残りを段落のノードとし、その範囲を残りの内容から始める
4. If 定義を取り出した後に段落の内容が残らない, then the ブロックの解析 shall 段落のノードを作らない
5. The ブロックの解析 shall リンク参照定義のノードに、ラベルの範囲（角括弧の内側）、dest の範囲（山括弧で囲む書き方では山括弧の内側）、title の範囲（引用符または丸括弧の内側）を設定する
6. If 定義に title がない, then the ブロックの解析 shall title を「書かれていない」として設定する
7. When dest が `<>` である、または title の区切りの内側が空である, the ブロックの解析 shall それを「書かれているが空である」として設定する
8. The ブロックの解析 shall 複数の行にわたる定義（ラベル、dest の前、title の前、title の中で改行するもの）を、仕様の規則に従って 1 つの定義として認識する
9. If title にあたる部分が規則に合わないが、dest までで行が終わっている, then the ブロックの解析 shall title のない定義として認識し、title にあたる行を段落の内容に残す
10. If ラベルが 999 文字を超える、またはラベルに空白と行末記号でない文字が 1 つもない, then the ブロックの解析 shall それを定義として認識しない
11. The ブロックの解析 shall リンク参照定義で、段落を中断しない
12. The ブロックの解析 shall コンテナ（ブロッククォート、リスト項目）の中の定義も、同じ規則で認識し、そのコンテナの子にする

### Requirement 14: ラベルの正規化と定義の表
**Objective:** As a 下流の開発者, I want ラベルから、それが指すリンク参照定義を引きたい, so that inline-parser が、参照の形式のリンクと画像を解決できる

#### Acceptance Criteria
1. The ラベルの正規化 shall ラベルを、次の手順で正規化する。前後の空白と行末記号を除く。途中に連続する空白と行末記号を、スペース 1 つにする。Unicode の case folding（unicode-tables のもの）を行う。
2. The ラベルの正規化 shall 複数の行にわたるラベルの中にあるコンテナのプレフィックスを、ラベルの内容として扱わない
3. The ラベルの正規化 shall ラベルの中のバックスラッシュのエスケープと文字参照を、文字に戻さずに、書かれたとおりの文字として比べる
4. The ラベルの正規化 shall U+0000 と、U+FFFD として扱う不正なバイト列を、U+FFFD として比べる
5. The 定義の表 shall 文書の中のすべてのリンク参照定義を、それがどのコンテナの中にあっても、正規化したラベルで引けるようにする
6. When 正規化したラベルが同じ定義が複数ある, the 定義の表 shall 原文で最初に現れた定義を返す。後の定義も、ノードとしては木に残す。
7. When ラベル（原文の範囲）が渡される, the 定義の表 shall それを正規化し、一致する定義のノードを返す
8. If 一致する定義がない, then the 定義の表 shall 「ない」ことを、どのノードとも区別できる値で返す
9. The 定義の表 shall 定義の数を N として、表を作る時間を N log N とラベルの長さの積に比例する範囲に、1 回の検索の時間を log N とラベルの長さの積に比例する範囲に収める。ラベルがどのような集まりでも（最悪の場合でも）同じである。
10. The 定義の表 shall 文書が解放されるまで使え、文書の解放でともに解放される
11. The ラベルの正規化 shall inline-parser が、リンクのラベルの比較に同じ手順を使えるようにする
12. The 定義の表とラベルの正規化 shall 公開ヘッダに現れず、ライブラリの内部とテストからだけ呼べる

### Requirement 15: 行の記録
**Objective:** As a 下流の開発者, I want 各行のどこからがブロックの内容で、タブの桁がいくつ残っているかを知りたい, so that source-text と inline-parser が、プレフィックスとインデントの規則を自分で解析し直さなくて済む

#### Acceptance Criteria
1. The 行の記録 shall 解析する範囲の各行について、その行が属する最も内側のブロックの内容が始まる位置（内容の先頭から数えたオフセット）を持つ
2. The 行の記録 shall 内容が始まる位置を、コンテナのプレフィックスと、ブロックの規則が除くインデント（インデントされたコードブロックの 4 桁、フェンスのコードブロックで開始のフェンスのインデントの分、段落の行の先頭の空白）の後とする
3. When 内容が始まる位置の直前で、タブの桁の一部だけが消費されている, the 行の記録 shall そのタブを内容が始まる位置とし、残りの桁の数（内容の前に補う空白の数）を持つ
4. If タブの桁が残っていない, then the 行の記録 shall 補う空白の数を 0 とする
5. The 行の記録 shall 遅延継続行について、コンテナの印が欠けていても、内容が始まる位置を正しく持つ
6. When 行番号が渡される, the 行の記録 shall その行の記録を、行の数によらない時間で返す
7. The 行の記録 shall 文書が解放されるまで使え、文書の解放でともに解放される
8. The 行の記録 shall 原文のバイトを複製しない
9. The 行の記録 shall 公開ヘッダに現れず、ライブラリの内部とテストからだけ呼べる

### Requirement 16: インラインの解析に渡す内容
**Objective:** As a 下流の開発者, I want 段落と見出しのうち、インラインとして解析する部分の範囲を受け取りたい, so that inline-parser が、ブロックの規則を知らなくても、内容だけを解析できる

#### Acceptance Criteria
1. The ブロックの解析 shall 段落と見出しのノードのそれぞれについて、インラインとして解析する内容の範囲を、解析の後で得られるようにする
2. The ブロックの解析 shall 段落の内容の範囲を、最初の行の最初の空白でないバイトから、最後の行の最後の空白でないバイトの直後までとする
3. The ブロックの解析 shall ATX 見出しの内容の範囲を、開始の `#` の列とその後の空白、閉じる `#` の列とその前の空白、行末の空白を除いた部分とする
4. When ATX 見出しに内容がない, the ブロックの解析 shall 長さ 0 の内容の範囲を返す
5. The ブロックの解析 shall Setext 見出しの内容の範囲を、下線の行を除き、段落と同じ決まりで定める
6. The ブロックの解析 shall 内容の範囲を、そのノードの範囲の内側にする
7. The ブロックの解析 shall 複数の行にわたる内容について、inline-parser が、行の記録を使って、各行の内容の部分だけを順に読めるようにする
8. The ブロックの解析 shall 内容を得られるノードを、文書の順にたどれるようにする
9. The ブロックの解析 shall この手段を公開ヘッダに出さない

### Requirement 17: 方言の規則を呼ぶ箇所
**Objective:** As a 下流の開発者, I want ブロックの解析に、方言の規則を足せる箇所があってほしい, so that dialect-extension が、解析の規則を書き換えずに、方言のブロックを足せる

#### Acceptance Criteria
1. The ブロックの解析 shall 新しいブロックの開始を判定する箇所と、開いているブロックの継続を判定する箇所を、それぞれ 1 か所にまとめ、方言の規則の呼び出しを足せるようにする
2. The ブロックの解析 shall 方言の種類のブロックのノードを、CommonMark の種類のブロックと同じ流れ（開く、続ける、閉じる）で扱えるようにする
3. While 方言が指定されていない, the ブロックの解析 shall CommonMark 0.31.2 の規則だけで解析する
4. The ブロックの解析 shall この spec の時点では、設定の方言の項目の値によって、解析の結果を変えない
5. The ブロックの解析 shall 方言を定義して登録する公開 API を持たない

### Requirement 18: 解析に共通の性質
**Objective:** As a 利用者, I want 解析が、どの入力と設定でも、製品が保証する性質を保ってほしい, so that 信頼できない入力や、並行する処理でも安心して使える

#### Acceptance Criteria
1. The 解析の入口 shall 解析の時間を、内容の長さにほぼ比例させる。深い入れ子、多数の遅延継続行、長い行、多数のリンク参照定義、閉じないフェンスや HTML ブロックを含む入力でも同じである。
2. The 解析の入口 shall 解析に使うメモリを、内容の長さにほぼ比例する量に抑える
3. The 解析の入口 shall 再帰を使わず、入れ子の深さによらず、呼び出しのスタックを一定の量しか使わない
4. The 解析の入口 shall グローバルな変数と静的な可変の状態を持たず、I/O を行わない
5. When 同じ内容と同じ設定が渡される, the 解析の入口 shall 常に同じ木（同じノードの ID、種類、範囲、属性）を作る
6. While 複数のスレッドが、それぞれ別の文書を解析している, the 解析の入口 shall 互いに影響せずに正しい結果を返す
7. Where 動的ライブラリを作る構成である, the ビルド構成 shall この spec が公開する関数だけを公開シンボルに加え、公開シンボルの一覧をそれに合わせる
8. The 公開ヘッダ shall 解析の入口の宣言を加えた後も、C99 として対象のすべてのコンパイラで警告なしに取り込め、C++ からも取り込める

### Requirement 19: 単体テスト
**Objective:** As a Amark の開発者, I want ブロックの解析の正しさを、この spec のテストだけで確かめたい, so that 下流の spec が、ブロックの構造を信頼して進められる

#### Acceptance Criteria
1. The 単体テスト shall spec.txt（CommonMark 0.31.2）の次の節の例について、ブロックの構造（種類、入れ子、属性）が、仕様の期待する結果と一致することを確かめる。Tabs、Thematic breaks、ATX headings、Setext headings、Indented code blocks、Fenced code blocks、HTML blocks、Link reference definitions、Paragraphs、Blank lines、Block quotes、List items、Lists。インラインの構造に依存する部分は確かめない。
2. The 単体テスト shall 各種類のブロックについて、ノードの範囲と行番号が Requirement 6 の決まりどおりであることを確かめる。3 種類の行末記号と、行末記号のない最後の行を含む。
3. The 単体テスト shall 設定の適用（解析する範囲、UTF-8 の扱いの 2 つの設定、資源の上限の 3 つの項目とその境の値、ファイル名）と、失敗の順（Requirement 3 の 9）を確かめる
4. The 単体テスト shall ラベルの正規化、定義の表（重なるラベル、コンテナの中の定義、999 文字の境）、行の記録（プレフィックス、タブの残りの桁、遅延継続行）、インラインの解析に渡す内容の範囲を確かめる
5. The 単体テスト shall テストで作ったすべての文書が、syntax-tree の不変条件の検査を通ることを確かめる
6. When 単体テストが、確保と解放を数える確保関数を使い、確保の失敗を各回に注入して解析を実行する, the 解析の入口 shall 成功した場合は文書の解放の後に、失敗した場合は戻った時点で、解放されないメモリを残さない
7. The 単体テスト shall 入れ子が 10 万段のブロッククォートと、入れ子が 10 万段のリストについて、解析と文書の解放が、スタックを使い切らずに終わることを確かめる
8. The 単体テスト shall 公開 API だけを使うテストで、解析の入口から得た文書を、たどる API で読めることを確かめる
